## 2. Backend — private-profile endpoints (private-profile capability)

- [x] 2.1 Add `PrivateProfileRepository` (`backend/ktor/.../user/PrivateProfileRepository.kt`) mirroring `HideDistanceRepository`: a single-statement write on the bounded JDBC dispatcher (docs/11 §3.2) + an own-row self-read. The write SQL carries the **`// @allow-privacy-write: user_settings`** annotation (the column IS on the privacy-flag-write allowlist — the reserved Settings-flow writer). Two write shapes: opt-IN → `UPDATE users SET private_profile_opt_in = TRUE WHERE id = ?`; opt-OUT → `UPDATE users SET private_profile_opt_in = FALSE, privacy_flip_scheduled_at = NULL WHERE id = ?` (the grace-clear, task 3). The self-read `SELECT private_profile_opt_in FROM users WHERE id = ?` carries `@AllowMissingBlockJoin` (own-row read; precedent `HideDistanceRepository.SQL_SELECT` / `JdbcUserProfileReader.SQL_SELF`). **Marker placement:** the `@allow-privacy-write` marker is FUNCTION-SCOPED (the Detekt rule scans only the enclosing function's text), so it MUST sit inside the repository write function — use the SQL-comment form `-- @allow-privacy-write: user_settings` within the query string (precedent `PrivacyFlipWorker.kt:103`) or a `// @allow-privacy-write: user_settings` Kotlin comment inside that function; a marker on an unrelated function does NOT exempt the write.
- [x] 2.2 Add request/response DTOs (`PrivateProfileUpdateRequest { privateProfile: Boolean }`, `PrivateProfileResponse { privateProfile: Boolean }`, `PrivateProfileStateResponse { privateProfile: Boolean, premium: Boolean }`) mirroring the `HideDistance*` DTOs — bare camelCase, non-nullable single field (missing/non-boolean → `400`).
