## Why

When a user toggles their profile to private (or back to public), the change does not apply instantly — a **72-hour privacy-downgrade grace window** schedules the flip via `users.privacy_flip_scheduled_at`, and a background worker applies it when the deadline passes (the column + its partial index shipped at V2; the read path already honors it — [`backend/ktor/.../user/JdbcUserProfileReader.kt`](../../../backend/ktor/src/main/kotlin/id/nearyou/app/user/JdbcUserProfileReader.kt) short-circuits the privacy state while `privacy_flip_scheduled_at` is in the future). There is **no admin surface to see who is currently inside that window**. Two operational gaps result: (1) support cannot answer "why is my profile still private / went public?" tickets without raw SQL against the Supabase dashboard; (2) a **stuck row** — `privacy_flip_scheduled_at` already past `NOW()` but never cleared — is an invisible **webhook-handler / worker bug signal** (a row the worker failed to apply, or a mass-scheduling event), with no way to spot it. This change ships the read-only **Privacy Flip Monitor** ([`docs/07-Operations.md` § Core Features → "Privacy Flip Monitor"](../../../docs/07-Operations.md), admin mockup board **frame 17** per [`docs/11-Engineering-Standards.md` § 3.6](../../../docs/11-Engineering-Standards.md)).

It is the **fourth instance of the established read-only-admin-viewer pattern** — after `admin-actions-log-viewer`, `admin-rejected-identifiers-viewer`, and the in-flight `admin-block-registry` ([PR #264](https://github.com/aditrioka/nearyou-id/pull/264)). It clones `admin-rejected-identifiers-viewer` end-to-end and reinforces the pattern rather than introducing a new one.

## What Changes

- **New read-only route `GET /admin/privacy-flips`**, wired INSIDE the existing `admin-login` session + CSRF gate (`authenticate(ADMIN_AUTH_NAME)`; any valid admin session, not role-restricted — matching `admin-actions-log-viewer` / `admin-rejected-identifiers-viewer`), rendering a monitor table over the `users` rows with a scheduled privacy flip. The implementation mirrors the shipped `admin-rejected-identifiers-viewer` end-to-end.
- **Scans `WHERE privacy_flip_scheduled_at IS NOT NULL`** — served by the **existing purpose-built partial index** `users_privacy_flip_idx ON users (privacy_flip_scheduled_at) WHERE privacy_flip_scheduled_at IS NOT NULL` (V2) — and **classifies each row into two buckets**: **IN_WINDOW** (`NOW() < privacy_flip_scheduled_at` — the canonical 72h-window predicate; the row is mid-grace, with countdown remaining) and **OVERDUE** (`privacy_flip_scheduled_at <= NOW()` — past deadline but the worker has not cleared it; a stuck-row / webhook-bug signal). The OVERDUE branch is **deliberately OUTSIDE** the canonical window predicate; the monitor query adds it on top of the docs predicate (frame 17).
- **Ascending order `privacy_flip_scheduled_at ASC, id ASC`** via a **keyset cursor over `(privacy_flip_scheduled_at, id)`** (no SQL `OFFSET`) — so the most-overdue / soonest-deadline rows surface first (the anomaly-spotting orientation), DIVERGING intentionally from the newest-first DESC ordering of the sibling viewers.
- **Composable, AND-combined, parameterized filters**: `status` (`in_window` / `overdue`) and an optional `q` per-user lookup (UUID → `id = ?`; non-UUID → exact case-insensitive `LOWER(username) = LOWER(?)`, served by `users_username_lower_idx`) for the support-ticket path.
- **Per-status count summary** (in-window total vs overdue total) for the current filter scope — the **overdue count is the key anomaly signal** (stuck rows / mass-scheduling events).
- Each row displays the user's **username** (deep-linked to the SHIPPED `/admin/users?q=` lookup, frame 5), **display_name**, current **privacy state** (`private_profile_opt_in`), the scheduled **flip timestamp**, and the **IN_WINDOW / OVERDUE** status with time-remaining / overdue-by.
- **HTML-escapes every rendered value** — and here escaping is **load-bearing, not merely defense-in-depth**: unlike `rejected_identifiers` (hex hash + CHECK enums), this view renders user-controlled free text (`username`, `display_name`). Supports **HTMX partial-swap** (`HX-Request` → `#privacy-flips-table` fragment) with a plain-`GET` progressive-enhancement fallback.
- **PII discipline**: surfaces only identity (`username` / `display_name` / `id`) + the privacy/flip state; it surfaces **no location** (no `display_location`, no coordinates — none is read) and cross-links only to the SHIPPED `/admin/users?q=` lookup, **not** the in-flight `/admin/users/{id}` profile page ([PR #251](https://github.com/aditrioka/nearyou-id/pull/251)) — avoiding coupling.
- **Strictly read-only** (explicit negative-guard requirement): the route writes **zero** `admin_actions_log` rows, mutates no `users` row, clears no scheduled flip, and wires no `POST`/`PUT`/`PATCH`/`DELETE` handler. Anomalies are escalated to a worker fix out-of-band (frame 17: "anomali dieskalasi ke perbaikan worker").
- **No Flyway migration, no new dependencies.** The column + partial index shipped at V2 — the change's migration footprint is empty, fully disjoint from the in-flight admin PRs #251 and #264.

## Capabilities

### New Capabilities

- `admin-privacy-flip-monitor`: the read-only admin Privacy Flip Monitor (`GET /admin/privacy-flips`) — authenticated, any-admin-role monitor table over `users` rows with a scheduled privacy flip, with IN_WINDOW / OVERDUE classification, ascending keyset pagination over `(privacy_flip_scheduled_at, id)`, composable `status` / `q` filters, an in-window-vs-overdue count summary (stuck-row spike detection), HTML-escaped HTMX rendering with plain-GET fallback, identity-only PII discipline, and the explicit read-only / mutation-unmapped requirements.

## Impact

- **Code**: `:backend:ktor` `admin` package — new `routes/AdminPrivacyFlipsRoute.kt` (`get("/privacy-flips")`) mounted inside the existing `authenticate(ADMIN_AUTH_NAME)` block in `AdminModule.kt`; a read-only repository/keyset query over `users WHERE privacy_flip_scheduled_at IS NOT NULL` in a new `admin/privacyflips/` sub-package (mirroring `admin/rejectedidentifiers/`); new Pebble templates (full page + `#privacy-flips-table` HTMX fragment) extending the `admin-panel-scaffold` base layout; a one-line nav-link append in the admin base layout / index (the only shared-file touch — additive); Koin wiring. Reuses the keyset-cursor + HTMX-fragment + lenient-filter-parse patterns established by `admin-rejected-identifiers-viewer`.
- **Schema / migrations**: **none**. `users.privacy_flip_scheduled_at` + `users_privacy_flip_idx` shipped at V2; the monitor's hot path is index-served by that existing partial index, so no index is added (see `design.md` D5). Migration footprint disjoint from in-flight admin PRs #251 / #264 (neither adds one either).
- **Lint / invariants**: the `admin` module is exempt from the `visible_*`-view + block-exclusion rules (raw read of `users` permitted, mirroring `admin-user-moderation` / `admin-rejected-identifiers-viewer`). All filter values applied via parameterized JDBC placeholders. No new secret reads, no rate-limit surface (read-only), no new `gradle/libs.versions.toml` pin. The spatial-fuzzing invariant is not engaged — the view reads no location column.
- **Docs**: aligns with [`docs/07-Operations.md` § Core Features](../../../docs/07-Operations.md) — flips "Privacy Flip Monitor" from DESIGN to SHIPPED at archive time; retags admin mockup board frame 17 "Usulan" → "Sudah ada".
