## Why

The push-notification loop is broken in the middle. The backend dispatches FCM pushes (`fcm-push-dispatch`, shipped) and the device acquires + registers its token (`mobile-fcm-token-registration`, shipped — PR [#250](https://github.com/aditrioka/nearyou-id/pull/250)), but the device **never displays an incoming push**: the shipped Android `NearYouFirebaseMessagingService` bridges only `onNewToken`, and there is no iOS Notification Service Extension. Every chat/notification push the backend already sends today silently vanishes on the device. This change closes the loop — render incoming pushes and route the tap into the app — completing the re-engagement surface the rest of the notification stack was built for. Grounded in follow-up issue [#256](https://github.com/aditrioka/nearyou-id/issues/256) and canonical [`docs/04-Architecture.md` § Push Notification Infrastructure](../../../docs/04-Architecture.md) (461–509) + [`docs/03-UX-Design.md` § Notification Content](../../../docs/03-UX-Design.md) (150–181).

A reconciliation pass against the shipped `fcm-push-dispatch` wire (see `design.md` Context) established two facts that shape the change: (1) the **Android** payload is data-only with routing fields (`type`, `actor_user_id`, `target_type`, `target_id`, `body_data`) but **no actor username and no `body_full`** — the client renders from `body_data` (chat = `{conversation_id, preview}`, preview ≤80 cp, server-truncated); (2) the **iOS** payload is a server-built alert body (username already resolved) + `body_full` (= JSON-stringified `body_data`) + `mutable-content`, with **no routing metadata** (`fcm-push-dispatch` punted `aps.category` routing). So a faithful, tappable cross-platform render needs a small **backend MODIFY** to the iOS + Android payloads.

## What Changes

- **Android incoming-push display** — extend the shipped `NearYouFirebaseMessagingService` with `onMessageReceived(RemoteMessage)`: parse the data-only payload (`type`, `actor_username` [new, see below], `target_type`, `target_id`, `body_data`), build a `NotificationCompat` notification on a dedicated channel with type-keyed Bahasa Indonesia copy (`docs/03` §163–176). Default content-private: chat body = "Pesan baru dari {username}" (sender + non-content); the message **preview** (`body_data.preview`, ≤80 cp) is shown **only** when the local content-privacy preference is ON.
- **iOS incoming-push display** — handle the alert-push tap in the main app (`UNUserNotificationCenterDelegate`) → deep-link route (using the routing fields added by the backend MODIFY below), plus a **new Notification Service Extension (NSE) target** that parses `body_full` (= `body_data`) and rewrites the visible body to surface `body_data.preview` per the App-Group content-privacy preference (`docs/04` §488–502).
- **Backend wire MODIFY (`fcm-push-dispatch`)** — (a) the **iOS** payload SHALL additionally carry `type`, `target_type`, `target_id` custom data fields (relaxing the prior "MUST NOT include the same data block as Android" line) so the iOS tap can deep-link, staying under the APNs 4 KB clamp; (b) the **Android** payload SHALL additionally carry `actor_username` (resolved via the existing `ActorUsernameLookup` from `visible_users`, with the same generic-fallback masking already used for the iOS body) so Android renders faithful username-bearing copy without a render-time network call.
- **Default content privacy (safe-by-default)** — the content-privacy preference defaults **OFF** (`docs/03` §178); at OFF the body is the sender+non-content form, never the message preview. The preference STORE + default ship here so display is fully functional at the private default with no UI control.
- **Per-conversation batching** — display-side: max 1 push / 10 s per `conversation_id`; bursts merge into "{n} pesan baru dari {username}" (`docs/04` §484–486). Durable on Android (persisted window); best-effort OS-grouping on iOS.
- **Deep-link tap reuse** — reuse the pure `(type, target_type, target_id, actor_user_id, body_data) → destination` resolver already specified by `mobile-notifications-list` (post → post-detail, `followed` → actor profile, `chat_message` → chat thread by `body_data.conversation_id`, actor-less / reply-target → non-navigating), via the consumed-once nav-signal pattern (`docs/11` §2.2), never an event bus. `actor_user_id` / `target_id` / `conversation_id` are route payload only — never rendered or logged.
- **Flip the deferral guard** — `mobile-fcm-token-registration`'s "Push message display and handling are deferred" requirement (+ its negative-guard scenario) is RENAMED + MODIFIED to record display is now implemented here, so the guard does not orphan once display lands.

Not breaking for clients (additive client glue); the backend MODIFY is additive payload fields (no removed/renamed wire keys, no schema change).

## Capabilities

### New Capabilities
- `mobile-push-message-handling`: the `:mobile:app` device-side receipt, rendering, batching, content-privacy gating, and deep-link tap-through of incoming FCM pushes (Android local-notification render + deep-link route; iOS alert-push delegate route + NSE body rewrite), consuming the shipped+extended `fcm-push-dispatch` payload contract. Includes the local content-privacy preference store (default OFF) the render path and the NSE read.

### Modified Capabilities
- `fcm-push-dispatch`: the iOS payload requirement is MODIFIED to additionally carry `type` / `target_type` / `target_id` routing data fields (for iOS tap deep-linking); the Android payload requirement is MODIFIED to additionally carry `actor_username` (for faithful client-side copy). Both additive, both within the APNs 4 KB clamp.
- `mobile-fcm-token-registration`: the "Push message display and handling are deferred" requirement is flipped (RENAMED + MODIFIED) from *deferred / shall-not-implement* to *implemented by `mobile-push-message-handling`*; its negative-guard scenario adjusted so it no longer fails once the display handler + NSE ship.

## Impact

- **Mobile (`:mobile:app`)** — `androidMain` push package (extend `NearYouFirebaseMessagingService`; notification builder + channel + batching + content-privacy preference store via DataStore; `POST_NOTIFICATIONS` manifest declaration); `iosMain` (push delegate tap handling + App-Group preference mirror); a **new iOS NSE extension target**; `commonMain` (shared deep-link resolver + the pure body-rendering/copy projection + preference seam); `:shared:resources` (notification copy strings). Extends `FcmPushSourceGuardTest`.
- **Backend (`:infra:fcm` / `:backend:ktor`)** — the `FcmDispatcher` iOS + Android payload builders gain the additive fields above + new dispatcher tests (payload-shape + 4 KB clamp still holds). This is a **cross-lane** touch (backend), justified as the dependency for the iOS user-facing capability. No schema / Flyway / API-endpoint change.
- **Cross-layer cohesion (`docs/12`)** — the Settings control row "Tampilkan preview pesan chat di notifikasi" (`docs/03` §178) lives in `mobile-settings`, concurrently edited by in-flight PR [#424](https://github.com/aditrioka/nearyou-id/pull/424) (`mobile-data-export-entry`). The default-OFF preference store + display behavior ship here (functional at safe default); the Settings ROW is declared an explicit deferred requirement (own follow-up) to avoid a `SettingsScreen` squash-merge conflict. The `chat_message` `body_data` shape `{conversation_id, preview}` may also be extended by in-flight `chat-embedded-posts` (PR [#423](https://github.com/aditrioka/nearyou-id/pull/423)) — this change reads only the two canonical keys and tolerates added keys (forward-compat), so no conflict.
- **Operator / human-required (preflight)** — iOS NSE needs an Xcode extension target + App Group capability (`group.id.nearyou.shared`) on both targets + provisioning + the `application-groups` entitlement (`docs/04` §494–502). Live end-to-end push verification additionally needs the operator Firebase client config + APNs `.p8` key (open issue [#258](https://github.com/aditrioka/nearyou-id/issues/258)). Per the PR #250 precedent, the code MUST build + unit-test + assemble **without** this config.
- **No new third-party dependency** — Android `NotificationCompat` (AndroidX, on classpath) + the pinned `firebase-messaging` / FirebaseMessaging Pod / `firebase-admin` (backend); DataStore (pinned).
