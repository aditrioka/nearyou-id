## Why

`:mobile:app` ships only a Material 3 scaffold + placeholder `HomeScreen` today (Mobile #1–#2.5 — [PR #105](https://github.com/aditrioka/nearyou-id/pull/105), [PR #116](https://github.com/aditrioka/nearyou-id/pull/116), [PR #119](https://github.com/aditrioka/nearyou-id/pull/119)). No screen behind that placeholder can talk to the backend until an authenticated session exists. Mobile #3 in [`openspec/project.md`](../../project.md) § Mobile + Admin Scaffolding Priority sequences Google Sign-In as the next step because the entire downstream menu (Mobile #4 age gate, Mobile #5 nearby timeline, every Phase 3+ feature screen) depends on the auth pipeline being able to obtain + persist + attach an RS256 access token to outbound requests. The backend `/signin` endpoint has shipped since 2026-04-20 (`auth-foundation` change archived in `openspec/changes/archive/2026-04-20-auth-foundation/`) but has had no mobile caller wired against it yet — this change closes that gap, end-to-end on both Android and iOS.

## What Changes

- **NEW: First end-to-end mobile auth flow.** `SignInScreen` Voyager screen renders "Masuk dengan Google" CTA → invokes platform Google Sign-In ceremony → exchanges the resulting Google ID token for the backend's RS256 access + refresh pair via `POST /api/v1/auth/signin` (the canonical unified-provider endpoint per [`openspec/specs/auth-signin/spec.md`](../../specs/auth-signin/spec.md), NOT the menu's casual `/auth/signin/google` shorthand) → persists both tokens via the secure store → navigates to `HomeScreen`.
- **NEW: `GoogleSignInClient` expect/actual interface in `:mobile:app` commonMain.** `androidMain` actual uses **Credential Manager API** (`androidx.credentials` + `googleid` helper); `iosMain` actual uses the **Google Sign-In iOS SDK** (`GoogleSignIn` integrated via CocoaPods per the existing iOS framework path). Sealed result type `GoogleSignInResult.Success(idToken, displayName?, email?) | UserCancelled | Failed(message)`. Apple Sign-In on iOS is deferred to a later Mobile #3.5 / #6 change (UX-doc says iOS primary = Apple; menu sequences Google end-to-end first as the substrate-proving change).
- **NEW: `SecureTokenStore` expect/actual interface.** Android actual uses **Preferences DataStore + Tink AEAD encryption** keyed off an Android-Keystore-derived master key (canonical 2026 pattern; `EncryptedSharedPreferences` is officially deprecated as of `androidx.security:security-crypto:1.1.0-alpha07` per [Android Developers reference](https://developer.android.com/reference/androidx/security/crypto/EncryptedSharedPreferences) — propose-time WebSearch surfaced this; design.md Decision 3 captures the substrate shift). iOS actual uses **Keychain Services** (`SecKeychainItem*` with `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`). Stores access token + refresh token + expiration timestamp.
- **NEW: Shared Ktor `HttpClient` for the mobile app.** Configured in `:mobile:app` commonMain with `ContentNegotiation(Json)`, a base-URL plugin reading from env-aware config, and an `Auth` plugin Bearer-token interceptor that (a) attaches `Authorization: Bearer <token>` to non-public requests, (b) on 401 calls `POST /api/v1/auth/refresh` once per request per [`openspec/specs/auth-session/spec.md`](../../specs/auth-session/spec.md) § Rotation, (c) on refresh failure clears the store + redirects to `SignInScreen`. Engine: `ktor-client-okhttp` (Android), `ktor-client-darwin` (iOS).
- **NEW: Environment-aware API base URL.** `expect val apiBaseUrl: String` in commonMain. Android `actual` reads from generated `BuildConfig.API_BASE_URL` (driven by gradle product flavors `dev` / `staging` / `production`); iOS `actual` reads from `NSBundle.mainBundle.objectForInfoDictionaryKey("ApiBaseUrl")` driven by xcconfig schemes. Mobile #3 wires `dev` + `staging` URLs only; `production` plumbing is in place but the URL field stays at a placeholder string until production infra provisioning.
- **NEW: `RootRouterScreen` as Voyager start destination.** Reads `SecureTokenStore` at composition; routes to `HomeScreen` when a valid token exists, otherwise to `SignInScreen`. Generalizes for Mobile #4 (signup interjects between sign-in and Home) and Mobile #5 (`HomeScreen` becomes the timeline).
- **NEW: Bahasa Indonesia user-facing strings.** Add to `:shared:resources/src/commonMain/composeResources/values/strings.xml`: `cta_signin_google`, `signin_screen_title`, `signin_error_no_account` (per Decision 7 — temporary user-facing copy until Mobile #4 swaps for age-gate navigation), `signin_error_banned` (per [`docs/03-UX-Design.md`](../../../docs/03-UX-Design.md) § Suspension UX), `signin_error_network`, `signin_error_token_invalid`, `signin_loading`, `account_separation_disclosure` (per [`docs/03-UX-Design.md`](../../../docs/03-UX-Design.md) § Auth Flow).
- **MODIFIED: `mobile-app-scaffold` negative requirements are selectively lifted.** Mobile #1's spec anticipated this with the carve-out "All such concerns ship in later mobile changes per project.md § Mobile + Admin Scaffolding Priority (#3 Google Sign-In ...)." This change MODIFIES the relevant negative scenarios: Ktor client dep is now permitted in `:mobile:app/build.gradle.kts`; the `SignIn` / `GoogleId` / `signin` / `googleSignIn` / `idToken` / `accessToken` / `refreshToken` / `authToken` grep allowlist is amended to permit references inside this change's added files; the API-base-URL grep allowlist is amended to permit references inside the new `id.nearyou.app.config` package only. `AppleAuth` / `appleSignIn`, `FirebaseMessaging` / `fcmToken`, and `URLSession` / `OkHttpClient` direct usage remain forbidden.
- **NEW: 8 library pins** added to [`gradle/libs.versions.toml`](../../../gradle/libs.versions.toml) — `androidx-credentials`, `androidx-credentials-play-services-auth` + `googleid`, `androidx-datastore-preferences`, `google-tink`, KMP-flavored Ktor client coordinates (`ktor-client-core` non-`-jvm`, `ktor-client-okhttp`, `ktor-client-darwin`, `ktor-client-content-negotiation`, `ktor-serialization-kotlinx-json`, `ktor-client-logging`, `ktor-client-mock` for tests), Google Sign-In iOS SDK (CocoaPods integration). Each gets a row in [`docs/09-Versions.md`](../../../docs/09-Versions.md) Version Decisions table per project pinning policy.
- **NEW: Android gradle product flavors `dev` / `staging` / `production`.** Selected via `KTOR_ENV`-style gradle properties at build time. Inject `API_BASE_URL` BuildConfig field + (later) Google Sign-In OAuth client ID per environment.
- **NEW: iOS xcconfig wiring.** `Staging.xcconfig` + `Production.xcconfig` schemes inject `ApiBaseUrl` into `Info.plist`.
- **NEW: iOS Swift host integrations.** `GoogleService-Info.plist` (or equivalent OAuth client ID config) added to Xcode project; URL scheme registered in `Info.plist`; `application(_:open:options:)` AppDelegate hook routes the OAuth callback back to the GoogleSignIn SDK (canonical iOS Google SDK integration per [Google Sign-In iOS docs](https://developers.google.com/identity/sign-in/ios)).
- **NEW: `FOLLOW_UPS.md` entries.** `mobile-auth-signin-apple-ios` (Apple Sign-In as iOS primary per `docs/03-UX-Design.md` + `docs/04-Architecture.md` Tech Stack — bundled with Mobile #4 wire-up or its own change); `mobile-auth-signin-404-route-to-age-gate` (replace the temporary "no account" error with route-to-age-gate navigation once Mobile #4 ships); `mobile-auth-signin-attestation-fingerprint-hash` (add `device_fingerprint_hash` payload when attestation lands per `docs/06-Security-Privacy.md`); `mobile-auth-signin-logout-wire-up` (wire `POST /api/v1/auth/logout` when Settings screen ships); `mobile-auth-signin-credential-manager-legacy-fallback` (try Credential Manager first + fall back to legacy Google Sign-In on older Android devices per the WebSearch finding); `docs-ios-primary-auth-mobile-3-vs-eventual-state` (covers amending BOTH `docs/03-UX-Design.md` § Auth Flow AND `docs/04-Architecture.md` § Tech Stack table to acknowledge Mobile #3 ships Google iOS as a substrate-proving stopgap before Apple Sign-In iOS lands); `mobile-auth-signin-suspended-user-copy-split` (backend `/signin` currently emits `account_banned` for any `is_banned = TRUE` row without differentiating temporary-suspension vs permanent-ban — Mobile #3 ships the uniform permanent-ban copy as documented in design.md Decision 7; this entry tracks the eventual backend differentiation + mobile copy split per `docs/03-UX-Design.md` § Suspension UX).

See [`design.md`](design.md) § Reconciliation notes for the explicit enumeration of the 5 reconciliation items run against canonical docs before scaffolding.

## Capabilities

### New Capabilities
- `mobile-auth-signin`: end-to-end mobile-side Google Sign-In specification — Google Sign-In ceremony (expect/actual per platform), token persistence (expect/actual per platform), Ktor HTTP client setup with Bearer interceptor + refresh-token rotation handling, `SignInScreen` UI + `RootRouterScreen` routing + `AuthRepository`, error-code mapping from backend HTTP statuses to user-facing strings, environment-aware API base URL resolution.

### Modified Capabilities
- `mobile-app-scaffold`: selectively lift the negative requirements anticipated by Mobile #1 — permit Ktor client dep in mobile sources, permit auth-flow identifiers inside this change's new files, permit env-aware API base URL inside the `id.nearyou.app.config` package. Preserve all other negative requirements (no FCM-token code, no `AppleAuth` identifiers, no direct `URLSession`/`OkHttpClient`/`NSURLSession`/`HttpURLConnection` usage, no backend or infra module deps).
- `shared-resources`: add 8 user-facing Bahasa Indonesia strings to `composeResources/values/strings.xml` for the sign-in flow (`cta_signin_google`, `signin_screen_title`, `signin_error_no_account`, `signin_error_banned`, `signin_error_network`, `signin_error_token_invalid`, `signin_loading`, `account_separation_disclosure`). Preserve byte-identical contents of the 10 foundational strings shipped in Mobile #2 / #2.5.

## Impact

- **Affected modules**: `:mobile:app` (commonMain + androidMain + iosMain — substantial new source); `:shared:resources` (strings.xml additions only); `gradle/libs.versions.toml` (8 new pins per § What Changes); `docs/09-Versions.md` (Version Decisions table additions); `dev/module-descriptions.txt` + root [`README.md`](../../../README.md) (no new modules introduced — `dev/scripts/sync-readme.sh --check` should remain green).
- **Affected backend**: NONE. Backend `/signin`, `/refresh`, and JWKS endpoints are already shipped. This change is mobile-only.
- **Affected infrastructure**: NONE in dev/staging — both envs already expose `POST /api/v1/auth/signin` from the existing Cloud Run staging deploy. Production not yet provisioned.
- **New external dependencies**: Google Sign-In iOS SDK (CocoaPods integration in iOS Xcode project); Google Cloud OAuth client IDs need to be configured per environment (Android + iOS) outside the repo — credential setup runbook lands in this change's `tasks.md` Section 7.
- **Pre-launch tasks affected**: this change does not block any [`docs/08-Roadmap-Risk.md`](../../../docs/08-Roadmap-Risk.md) Pre-Launch checklist items; it unblocks the entire downstream mobile scaffolding sequence — Mobile #4 (age gate / signup), Mobile #5 (first product screen), and every later authenticated mobile surface (Phase 3 feature screens + Phase 4 Premium/billing). In turn, the unblocked sequence carries the pre-launch UAT flow.
- **CI**: existing `ktlintCheck` + `detekt` + `:backend:ktor:test` + `:lint:detekt-rules:test` continue to pass. New `:mobile:app:assembleDebug` and `:mobile:app:linkPodDebugFrameworkIosSimulatorArm64` lanes are exercised in the change's smoke section. Negative-requirement grep step updates land in tasks.md Section 9.
- **Backwards compatibility**: not applicable — this is the first mobile auth wiring; there are no production callers to break.
- **Security posture**: introduces the first mobile-side secret-handling code path. Token-at-rest encryption requirement is canonical per [`docs/05-Implementation.md`](../../../docs/05-Implementation.md) § Authentication Implementation. Defense-in-depth substrates (Tink + Android Keystore for Android; Keychain Services for iOS) align with platform-current best-practice as of 2026-05-28 per propose-time WebSearch.
