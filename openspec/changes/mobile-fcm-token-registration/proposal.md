# Proposal: mobile-fcm-token-registration

## Why

The backend push stack is fully shipped — `POST /api/v1/user/fcm-token` + the `user_fcm_tokens` table (V14) register device tokens, and `FcmDispatcher` (`:infra:fcm`, 414 LOC) dispatches chat-message and notification pushes (`docs/04-Architecture.md` § Push Notification Infrastructure, status line 455: "Server-side push dispatch is **shipped** … as are FCM token registration … Client-side handling is the spec source for mobile push scaffolding"). But `:mobile:app` has **zero** FCM integration today (`grep -ri fcm mobile/**/*.kt` → nothing): the device never acquires or registers a push token, so **no push can ever route to any device**. New-message and new-follower pushes are dispatched into a void.

This change ships the **mobile token-acquisition + registration lifecycle** — the dependency root for the entire push half of the demo. It is the direct mobile consumer of the already-shipped registration endpoint, the same "wire the shipped backend" shape as the mobile profile/timeline screens (mobile-first priority, `openspec/project.md` § Mobile-First to Full-Demo Priority → "Cross-cutting wiring still pending: FCM token registration … sequence each as it gates a demo scenario"). **Mobile-only — no Flyway migration, no backend code.** The heavier push *display/handling* (Android local render after a preference check; iOS Notification Service Extension body rewrite) is the explicit follow-up `mobile-push-message-handling`; this change stops at registration.

## What Changes

- **A platform-free `FcmTokenProvider` seam (commonMain interface + Koin-bound platform actuals)**: the canonical `interface` in `mobile/app/src/commonMain/kotlin/id/nearyou/app/push/FcmTokenProvider.kt` exposing `suspend fun currentToken(): String?` and a `tokenRefreshes: Flow<String>` stream, with an Android actual (Firebase Messaging `firebase-messaging` SDK: `FirebaseMessaging.getInstance().token` + a `FirebaseMessagingService.onNewToken` bridge) and an iOS actual (Firebase Messaging Pod via the existing KMP cocoapods plugin: `Messaging.messaging().token` + the `MessagingDelegate.didReceiveRegistrationToken` bridge). Mirrors the shipped `LocationProvider` / `GoogleSignInGateway` expect/actual idiom (docs/11 § 2.5: prefer `interface` in commonMain + per-platform Koin actuals; the vendor SDK lives ONLY in the platform source sets — commonMain sees only the interface, satisfying the "no vendor SDK outside `:infra:*` / platform boundary" rule).
- **A `FcmTokenRegistrar` orchestrating acquire → register**: a Compose-free, commonMain registrar that, on a session-active transition, calls `FcmTokenProvider.currentToken()`, POSTs it via a `FcmTokenApiClient`, and subscribes to `tokenRefreshes` to re-register on rotation. It is a stateless singleton consuming the **shipped** Ktor `HttpClient` `Auth` plugin for Bearer attachment (MUST NOT reimplement token attachment — same constraint as `mobile-notifications-list`).
- **A `FcmTokenApiClient` issuing the canonical request**: `POST /api/v1/user/fcm-token` with JSON body `{ token, platform, app_version }` (the SHIPPED wire — `backend/ktor/.../user/FcmTokenRoutes.kt` / `FcmTokenRequest.kt`), `platform` ∈ `{"android","ios"}` (matching the backend CHECK), `app_version` from the build config. Maps the responses to a sealed `FcmRegistrationOutcome` (`Registered` from 204; `Rejected(code)` from the closed 400 vocabulary `malformed_body`/`invalid_platform`/`empty_token`/`token_too_long`/`app_version_too_long`, plus `Rejected(unknown)` for an unrecognized code; `Unauthorized` from 401; `TransportError`; and `NoTokenAvailable` when the provider yields no token — e.g. iOS denied authorization).
- **Registration fires on the documented triggers** (`docs/04-Architecture.md` line 469): app first open after sign-in (cold start with a persisted `TokenPair` — the `RootRouterScreen`/`AuthRepository.isAuthenticated()` seam), fresh sign-in success (the `AuthRepository` HTTP-200 seam), and logout→re-login. No registration is attempted while unauthenticated (no token to attach; the endpoint is JWT-gated).
- **New library pins**: Android `com.google.firebase:firebase-messaging` via the Firebase BoM (`com.google.firebase:firebase-bom`) + the `com.google.gms.google-services` Gradle plugin; iOS the `FirebaseMessaging` Pod via the existing `kotlin("native.cocoapods")` block. Each gets a `docs/09-Versions.md` Decisions-Log row; the pre-implementation library re-check (dated WebSearch) runs at `/opsx:apply` kickoff per `openspec/project.md`.

## Capabilities

### New Capabilities

- `mobile-fcm-token-registration`: the mobile push-token acquisition + backend-registration lifecycle — the `FcmTokenProvider` expect/actual seam, the `FcmTokenApiClient` over the shipped `POST /api/v1/user/fcm-token` wire, the `FcmTokenRegistrar` session-active orchestration + token-refresh re-registration, the platform value + app_version sourcing, the no-token-in-logs confidentiality guard, and the explicit deferrals (push display/handling, the contextual notification-permission prompt UX, live end-to-end verification gated on operator Firebase client config).

### Modified Capabilities

- _None._ The registrar attaches as an additive side-effect observer at the existing post-auth seam; it does not change `mobile-auth-signin`'s documented routing/refresh behavior, so no MODIFIED delta is emitted (the trigger requirement lives in the new capability).

## Impact

- **Code** (`:mobile:app` only): new `push/FcmTokenProvider.kt` (commonMain interface) + `androidMain/.../push/AndroidFcmTokenProvider.kt` + `iosMain/.../push/IosFcmTokenProvider.kt`; new `push/FcmTokenApiClient.kt` + `FcmRegistrationOutcome.kt`; new `push/FcmTokenRegistrar.kt`; a token-refresh bridge (`NearYouFirebaseMessagingService` on Android registered in the manifest; the `MessagingDelegate` wiring on iOS); Koin bindings in the common + platform modules; the post-auth trigger wiring at the `AuthRepository`/`RootRouterScreen` seam (additive call, no behavior change). No new screen, no ViewModel (invisible-infra change). No new user-facing strings (no UI surface; the registrar is silent — failures are logged non-confidentially and retried on the next trigger).
- **APIs**: none added or changed — consumes the shipped `POST /api/v1/user/fcm-token` exactly as specified.
- **Dependencies** (`gradle/libs.versions.toml`): Android `firebase-bom` + `firebase-messaging` + the `google-services` plugin; iOS `FirebaseMessaging` Pod. New pins → Decisions-Log rows + apply-phase re-check.
- **External / operator setup** (flagged as a tasks.md Phase-1 sanity check, per the external-dependency rule): the Firebase **client** config files are NOT in the repo — `google-services.json` (Android, per flavor: `dev`/`staging`/`prod`) and `GoogleService-Info.plist` (iOS), tied to the **separate staging Firebase project** (free tier, with its own FCM credentials + a separate APNs `.p8` key per `docs/04-Architecture.md` § 259 "Push: separate Firebase project"). The registrar/provider code builds + unit-tests against `FakeFcmTokenProvider` + `FakeFcmTokenApiClient` WITHOUT live FCM; live end-to-end verification (real device token → real 204) is gated on the operator placing the config files. The code is NOT blocked on the config.
- **Specs**: 1 ADDED capability (above); 0 MODIFIED.
- **Tests**: Compose-free `FcmTokenRegistrarTest` (acquire→register happy path; token-refresh re-registration; 204 `Registered`; each 400 `Rejected(code)` branch; `Unauthorized`; `TransportError` retried-on-next-trigger; no-register-while-unauthenticated); `FcmTokenApiClientTest` (request shape — body fields, platform value, app_version; response→outcome mapping via Ktor `MockEngine`); a Koin-resolution test for the new bindings; the `FcmPushSourceGuardTest` (commonMain Firebase-confinement — the mobile-module enforcement the global `VendorSdkLeakageScanTest` does not provide); and a no-token-in-logs guard across all push files (the `LocationSourceGuardTest` sink set + the `HttpClient` `Logging`-level check).
- **Risk**: low-moderate — invisible-infra wiring behind a shipped endpoint; the riskiest seam (platform FCM SDK token acquisition) is isolated in the per-platform actuals and faked in commonTest. The only true external blocker (operator Firebase config) is verification-only and explicitly does not gate the code.
