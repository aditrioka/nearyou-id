## Context

The admin panel today is a read-only surface: `admin-panel-scaffold` mounts the `/admin/` subtree, `admin-login-argon2-totp` gates it behind an `__Host-admin_session` cookie + per-session CSRF token + `AdminPrincipal(admin_id, role)`, and `admin-actions-log-viewer` renders the `admin_actions_log` audit trail. There is **no write action** — an admin cannot suspend, unban, or otherwise change a user's account state. This change adds the first one.

The ban/suspension data model already exists (`users.is_banned BOOLEAN NOT NULL DEFAULT FALSE`, `users.suspended_until TIMESTAMPTZ` nullable, `users_suspended_idx` partial index — `docs/05-Implementation.md` § users schema). The automated `suspension-unban-worker` already performs the elapse-driven `(is_banned, suspended_until) → (FALSE, NULL)` flip in a batch CTE, attributing audit rows to the `system` sentinel (`system-actor` capability). The `admin_actions_log` table (V16) takes a free-string `action_type VARCHAR(64)` (no CHECK enum), so new action types need no migration. `account_action_applied` is already a valid `notifications.type` (V10). The `AdminAuditLogger` already centralizes parameterized audit-row writes for the auth path, and `AdminCsrfGate.validateCsrf` is the shared CSRF middleware.

So this change is almost entirely composition over shipped primitives: a route, a repository that does one guarded `UPDATE` + one audit `INSERT` (+ one notification `INSERT` on suspend) atomically, two Pebble templates, and two new `AdminAuditLogger` methods. **No Flyway migration, no new dependency.**

## Goals / Non-Goals

**Goals:**
- Ship the admin panel's first state-changing action: suspend (7-day) + manual unban, role-gated and CSRF-gated.
- Make every action atomically auditable to the acting human admin in `admin_actions_log`.
- Establish reusable patterns for the next admin writes: the role gate (incl. a higher-trust tier), the atomic UPDATE-plus-audit transaction, the `{is_banned, suspended_until}` before/after-state shape, and the read-form-field-after-CSRF idiom.
- Compose cleanly with `suspension-unban-worker` (manual unban is its human-triggered sibling) without duplicating or modifying its spec.
- Avoid leaking moderator-internal rationale to the offender (privacy by design on the user-facing notification).

**Non-Goals:**
- Permanent ban *creation*, shadow ban (`is_shadow_banned`), and "warning" actions (separate future actions on the same capability). Note: *lifting* a pre-existing permanent ban IS in scope (via unban, owner/admin-gated).
- Report-Queue-driven moderation (suspend-from-queue) and the full User Management **search / profile / history** page — that is a SEPARATE future capability (`admin-user-management`), NOT a future ADDED requirement of `admin-user-moderation` (D1).
- FCM push on `account_action_applied` (in-app notification only; push deferred — D9).
- Per-admin destructive-action rate-limiting ("20/hour per admin", `docs/07` § Security) — deferred (D11).
- WebAuthn step-up (multi-admin period per `admin-login`).
- Any change to the automated worker, the system sentinel, or the audit-log viewer.

## Decisions

### D1 — New capability `admin-user-moderation` (domain home), not a change-named capability
The repo's convention is **capability = durable domain noun, change = action phrase** (`admin-login` ← `admin-login-argon2-totp`; `system-actor` ← `system-actor-and-worker-audit-rows`). `admin-user-moderation` is the durable home for admin-initiated account-state moderation (the offender's ban/suspension/shadow-ban/warning state). This change adds only the **suspend** + **manual unban** requirements; future account-state actions (permanent-ban creation, shadow ban, warning) extend the SAME capability with ADDED requirements. The shipped spec scope equals the change scope (it does not pre-declare those). **Boundary note:** the User Management *search / profile / history* page (`docs/07` § Core Features) is a DIFFERENT capability (`admin-user-management` — read/browse surface), not a future requirement here; keeping the moderation-actions capability distinct from the user-browse capability prevents a sprawling catch-all.
- *Alternative considered:* a tightly-named `admin-suspend-unban` capability. Rejected — would force ban/shadow-ban into awkwardly-named siblings; the domain-noun convention is established.

### D2 — Route shape: `GET /admin/users` lookup + `POST /admin/users/{id}/suspend` + `POST /admin/users/{id}/unban`
A single `GET /admin/users?q=<uuid|username>` renders the lookup form and (when `q` resolves) the target user's current moderation state + suspend/unban controls. Two `POST` routes carry the actions. This mirrors `admin-actions-log-viewer`'s HTMX-partial-swap + plain-`GET` progressive-enhancement posture (branch on the `HX-Request` header), so the surface works without JavaScript and the filtered URL stays shareable. Both `POST` handlers redirect (303) / `HX-Redirect` back to `GET /admin/users?q={id}` on success so the admin sees the updated state. The `{id}` path segment is parsed as a UUID; a non-UUID `{id}` is a distinct parse site from the GET `q` parameter and is rejected safely (4xx / inline, never 500 — see the malformed-path-identifier requirement). **OQ4 resolved:** the `/admin/users` lookup + `/admin/users/{id}/{suspend,unban}` shape is adopted (no separate `/admin/users/{id}` detail page for the MVP).

### D3 — Two-tier role gate: suspend + unban-of-suspension → owner/admin/moderator; unban-of-**permanent-ban** → owner/admin only
Routine moderation (suspend, and lifting a 7-day suspension) is core `moderator` work, so the three operational roles may do it; `read_only` is view-only and is rejected with **HTTP 403** (not a redirect — the admin is authenticated, just unauthorized). **But lifting a pre-existing PERMANENT ban is a higher-trust, harder-to-undo action** — a permanent ban was a deliberate severe decision — so unban is gated to `owner`/`admin` only WHEN the target is permanently banned (`is_banned = TRUE AND suspended_until IS NULL`); a `moderator` hitting that case gets 403. This mirrors the higher-trust gate `docs/07`:53 places on chat redaction (`role IN ('owner','admin')`). Mechanics: `validateCsrf` first → base role check (`owner`/`admin`/`moderator` else 403, the reusable helper) → for unban, the permanent-ban tier check happens AFTER the `SELECT … FOR UPDATE` of the target's state, inside the transaction, so a moderator rejection writes nothing. This is the first role-gated admin write; the base-role helper is reusable for future writes. **OQ1 resolved** to this two-tier split (the security-lens recommendation; per the user's "apply all" directive).
- *Alternative considered:* a single `owner`/`admin`/`moderator` allow-set for all unban cases. Rejected — it would let a moderator silently reverse a permanent ban, a higher-trust action than routine suspension management.

### D4 — Atomic UPDATE + audit INSERT (+ notification INSERT) in one transaction, owned by `UserModerationRepository`
The user `UPDATE`, its `admin_actions_log` `INSERT`, and (for suspend) the `notifications` `INSERT` execute in a **single JDBC transaction** (one connection, `autoCommit = false`, commit at end, rollback on any exception). If the audit INSERT OR the notification INSERT fails, the user UPDATE rolls back — there is never a state change without its audit row, nor a partial suspend. This matches the `suspension-unban-worker` atomicity contract. It means the repository owns the transaction rather than calling `AdminAuditLogger.insert(...)` (which opens its own connection) — a deliberate divergence from the login/logout/CSRF audit path, where each event is standalone with nothing to be atomic against. The two new `AdminAuditLogger` methods (`logUserSuspended` / `logUserUnbanned`) therefore accept a caller-supplied `Connection` so the audit write joins the repo's transaction.
- *Alternative considered:* reuse `AdminAuditLogger.insert`'s own-connection write (non-atomic). Rejected — a suspend that isn't logged (or a log of a suspend that didn't commit) is exactly the integrity failure the audit trail exists to prevent.

### D5 — `action_type` vocabulary: `user_suspended` / `user_unbanned`
Target-descriptive snake_case, consistent with the existing log vocabulary (`admin_login_success`, `system_unban_applied`, `reserved_username_added`, `admin_chat_redaction`). Distinct from the worker's `system_unban_applied` so the audit log cleanly separates human-triggered from machine-triggered transitions when filtering by `action_type`. (Precedent for adding a new free-string `action_type` with no `admin-actions-log-viewer` MODIFIED delta: `system-actor-and-worker-audit-rows` introduced `system_unban_applied` the same way.)
- *Alternative considered:* `admin_suspend_applied` / `admin_unban_applied` (actor-prefixed). Rejected — the `admin_id` column already records the actor; a target-descriptive `action_type` reads better and matches the `reserved_username_*` style.

### D6 — `before_state` / `after_state` built in Kotlin (`{is_banned, suspended_until}`)
The before/after JSON is constructed in Kotlin via kotlinx.serialization (matching the existing `AdminAuditLogger` pattern) and passed as `?::jsonb`: `{"is_banned": <bool>, "suspended_until": <ISO-8601 Instant.toString() | null>}`. This intentionally differs from the worker's Postgres-native `jsonb_build_object(...)` form — acceptable (different writers, different code paths); `admin-actions-log-viewer` HTML-escapes and renders whatever JSON is present. **Test assertion shape:** `suspended_until` in `before_state`/`after_state` MUST be asserted by parsing the JSON string to an `Instant` and comparing by value with a ±tolerance (mirroring `suspension-unban-worker` spec's timestamptz value-equality rule), NOT by brittle string match — the `≈` in the re-suspend scenarios refers to parsed-instant equality.

### D7 — Suspend semantics, guards, and deliberately-unguarded targets
Suspend sets `is_banned = TRUE`, `suspended_until = NOW() + INTERVAL '7 days'`. Guards (each a spec scenario):
- **Soft-deleted target** (`deleted_at IS NOT NULL`): rejected — no state change, no audit row. A tombstoned account is not moderated.
- **Already permanently banned** (`is_banned = TRUE` AND `suspended_until IS NULL`): rejected — suspending would silently *downgrade* a permanent ban to a 7-day window.
- **Already time-bound suspended**: allowed; the clock resets to `NOW() + 7d`, `before_state` captures the prior expiry. The "already suspended" test keys on `suspended_until IS NULL` (permanent) vs non-null — NOT on `suspended_until > NOW()`. So an **elapsed-but-unswept** window (`is_banned = TRUE`, `suspended_until` in the past, the daily worker hasn't run yet) is still re-suspendable (an implementer must NOT write a `> NOW()` guard that wrongly rejects it).

**Deliberately-unguarded targets** (documented, intentionally NOT special-cased):
- The `system` sentinel is an `admin_users` row, NOT a `public.users` row; `users` and `admin_users` are disjoint ID spaces, so a `users` lookup can never resolve the sentinel — a non-issue, not a guard.
- An admin suspending the `public.users` row that backs *their own* end-user account (admins may also be app users) is possible (self-lockout of the app account, not the admin account); unguarded — the admin can re-unban. Low severity; noted, not blocked.
- No concept of "this user is also an active moderator" exists yet, so there is nothing to guard there.

### D8 — Manual unban semantics
Unban sets `is_banned = FALSE`, `suspended_until = NULL` — lifting **both** a time-bound suspension and a permanent ban (the permanent-ban case role-restricted per D3). Guards:
- **Not currently banned** (`is_banned = FALSE`): no-op — no state change and **no audit row** (the log records only actual transitions); informational "user is not banned" message.
- **Soft-deleted but banned**: unban IS permitted (lifting a ban on a tombstoned row is harmless; `deleted_at` unchanged) — a confirming scenario locks this asymmetry vs suspend (which rejects soft-deleted).

### D9 — Notification on suspend (sanitized reason, no PII leak); none on unban; FCM deferred
On a successful **suspend**, insert one `notifications` row of the existing `account_action_applied` type for the suspended user. **The `body_data.reason` is a SANITIZED, non-free-text code** (this change sets it to the fixed string `"suspension"`), NOT the admin's free-text `reason`: the notification is read by the *suspended end-user*, and echoing a moderator note like "suspected minor, see report #42" would leak moderator-internal rationale and possibly third-party PII to the offender. The free-text `reason` lives ONLY in `admin_actions_log.reason` (admin-only). The catalog shape `{action_type, reason, suspended_until}` (`docs/05`:591) is preserved — `reason` is present but sanitized; this change, as the first writer of `account_action_applied`, defines that semantic. `target_id` is NOT duplicated inside `body_data` (per the catalog), `user_id` = the target user, `actor_user_id` = NULL (the admin is not a `public.users` row). On **manual unban**, insert **no** notification (mirrors `suspension-unban-worker` D5 — no `account_action_lifted` type, and the copy doesn't fit a positive restoration). The notification INSERT joins the suspend transaction (D4). **FCM push is deferred** (the in-app row is the in-band signal). **OQ2 resolved:** include the in-app notification now, with a sanitized reason; defer FCM. A richer user-facing reason taxonomy (beyond the fixed `"suspension"` code) is future work.

### D10 — Minimal target-user lookup (UUID primary, exact case-sensitive username secondary)
`GET /admin/users?q=` resolves `q` as a user UUID first; if not a UUID, an EXACT, case-sensitive `users.username` match. No fuzzy / prefix / paginated search — that is the future `admin-user-management` page. A non-resolving `q` renders an inline "no matching user" state, not a 404. All lookups parameterized; the admin module is exempt from the `visible_*`-view lint, so a direct `FROM users` read is permitted.

### D11 — Defer per-admin destructive-action rate-limiting (deferred-mitigated, not out-of-scope)
`docs/07` § Security specifies "Rate limit destructive actions: 20/hour per admin". This change **defers** that limiter to a focused follow-up (logged in `FOLLOW_UPS.md`, task 11.1) because a correct admin-action limiter needs its own substrate decision (Redis-backed per-admin counter vs a `COUNT(*) admin_actions_log WHERE admin_id=? AND created_at > NOW()-1h` DB check) that would balloon this "first write action" change. **The deferral is mitigated, not a non-risk:** `docs/07`:92 explicitly notes TOTP is phishable (evilginx2), so the project's own threat model contemplates a phished admin session — without the limiter, such a session can mass-suspend (reversibly) at unbounded rate until idle-timeout. The interim mitigations bound the blast radius: CSRF, 30-min idle + 8-hour absolute session caps, IAP network gate, full audit trail, and reversibility (every suspend is undoable via unban). Acceptable for a first-write MVP, but the limiter is tracked as real debt.

## Risks / Trade-offs

- **Phished/compromised admin session mass-suspends (no rate limit yet)** → Deferred-mitigated (D11): CSRF + 30-min idle + 8-hour absolute cap + IAP + complete audit trail + full reversibility. The project's threat model DOES contemplate a phished TOTP session (`docs/07`:92), so this is acknowledged residual risk tracked in `FOLLOW_UPS.md`, not an excluded case.
- **Suspend silently weakening a permanent ban** → Mitigated by the D7 guard rejecting suspend on `is_banned = TRUE AND suspended_until IS NULL`, with a dedicated scenario.
- **Moderator silently reversing a permanent ban** → Mitigated by D3's permanent-ban-unban tier (owner/admin only; moderator → 403), checked inside the transaction so the rejection writes nothing.
- **Non-atomic state vs audit/notification** → Mitigated by D4's single-transaction design + two failure-injection scenarios (audit-INSERT and notification-INSERT failures each roll the UPDATE back).
- **Moderator rationale / third-party PII leaking to the offender via the notification** → Mitigated by D9: the user-facing `body_data.reason` is a sanitized code; the free-text reason is audit-only.
- **`reason` form field silently dropped by the CSRF body-consume** → Mitigated by the read-reason-after-`validateCsrf` contract: the CSRF gate stashes the parsed form parameters in the call attributes (Ktor does NOT re-serve a consumed body without the DoubleReceive plugin, so a second raw `receiveParameters()` would return nothing on the `_csrf`-field path), and the handler reads `reason` via `AdminCsrfGate.formParametersAfterValidation`. A scenario asserts `_csrf` + `reason` in one urlencoded body lands the reason in the audit row. (Apply-time correction: the proposal's "Ktor caches `receiveParameters()`" premise held only with DoubleReceive — an experimental, dependency-adding plugin — so the gate-stash realizes the same contract without a new dependency.)
- **Transition-semantics drift from the worker** → Both reference the canonical `docs/05` § suspension SQL + a design cross-reference; intentionally separate code paths (batch-CTE machine vs single-user human), only the column contract is shared.

## Migration Plan

- **No Flyway migration.** Pure code + templates. `users` columns, `users_suspended_idx`, `admin_actions_log` (free `action_type`), and the `account_action_applied` notification type all already exist.
- **Deploy**: ships in the same Cloud Run image as the rest of `:backend:ktor`. The `/admin/` subtree is already mounted in all envs behind the `admin-login` auth gate (the `KTOR_ENV` scaffold guard was removed by Admin #3), so no mount/env change.
- **Pre-archive smoke (feasible)**: a manual staging branch deploy (`gh workflow run deploy-staging.yml --ref admin-suspend-unban-user-action`) lets the suspend/unban flow be exercised against staging Supabase before the squash-merge, per the project's pre-archive-smoke convention. The smoke script logs in as the seeded admin, suspends a synthetic user, asserts the `admin_actions_log` row + `users.suspended_until` + the notification, then unbans.
- **Rollback**: revert the change's commits — no schema state to unwind. Any `user_suspended` / `user_unbanned` rows already written remain valid audit history.
