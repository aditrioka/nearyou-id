## Why

`:mobile:app` has shipped the read + engage loop (Nearby/Global feeds, post creation, post detail with like + reply, inline card actions) but has **no profile surface**: the Profil bottom-nav section renders `ProfilePlaceholderScreen` ("*Profil segera hadir.*"), there is no way to view another user, and the app has **no follow action at all** — the social-graph half of the product is a visible dead-end. The backend has shipped every endpoint this needs: `GET /api/v1/users/{user_id}` (`user-profile-read`, V-2026-06-09), `POST/DELETE /api/v1/follows/{user_id}` (`follow-system`), `POST/DELETE /api/v1/blocks/{user_id}` (`user-blocking`), and `POST /api/v1/reports` (`reports`). They sit unused by mobile.

This change ships the **mobile Profil screen** — the keystone of the remaining mobile critical path (`openspec/project.md` § Mobile-First to Full-Demo Priority, live-menu row #1). It is the change GitHub issue [#196](https://github.com/aditrioka/nearyou-id/issues/196) (`mobile-profile-section-screen`, label `follow-up`) was reserved for. It directly **unblocks live-menu #2 `mobile-following-timeline-screen`** (which needs a follow action to be meaningful) and adds the **user-level block + report** surface (`docs/02-Product.md` § Block User / Report System). It is a pure mobile feature — **no Flyway migration, no backend code** — wiring already-shipped endpoints, and it completes the feed-card author-identity tap target currently stubbed everywhere with "no profile screen exists yet — issue #196".

## What Changes

- **New `ProfileScreen`** in `:mobile:app` — renders a user's profile from `GET /api/v1/users/{user_id}`: the letter avatar + display name + `@username` handle (reusing the `mobile-post-card` avatar/identity sub-components so treatments cannot drift), `bio` (when present), an actively-Premium badge (`isPremium`), and the follower / following **counts as static numbers** (the list screens are deferred — see below). Loading / not-found / error / refresh states per `mobile-design-system`; all copy via `:shared:resources`.
- **Self vs other rendering from the endpoint's `isSelf`** — the self read (own profile) shows no follow/block/report actions; the other-user read shows a follow/unfollow toggle + a kebab (Blokir / Laporkan). The constant `404 user_not_found` (unknown / shadow-banned / soft-deleted / blocked-either-direction — byte-identical per `user-profile-read`) maps to a single **not-found** state with no direction hint.
- **Self profile fills the Profil bottom-nav section** — `ProfilePlaceholderScreen` is replaced (MODIFIES `mobile-home-tab-host` § "The Profil section renders a deferred placeholder", whose own text says a future change "will MODIFY this requirement to introduce the live surface"). The self profile is rendered **inset-free** in the shell body per the single-`Scaffold` contract; the authenticated self `userId` comes from the session, not a nav arg.
- **Other-user profile is a root-stack overlay route** — a new payload-carrying `ProfileRoute(userId)` pushed onto the **root** back stack (overlaying the tab bar, mirroring `PostDetailRoute`), owning its own back-bar chrome. `@Serializable` + registered in the `navSavedStateConfiguration` polymorphic module (iOS-saveable). The route carries the target **`userId`** as its resource key (necessary for the keyed read; never rendered) and explicitly **no coordinates / no tokens** (design D4).
- **Feed-card author identity becomes a profile tap target** — the shared `mobile-post-card` identity header (avatar + name + handle) gains a hoisted `onOpenProfile` callback (MODIFIES `mobile-post-card`); the Nearby + Global host screens bind it with the **`authorUserId` they already hold in memory** from the timeline DTO (parsed, never rendered, never serialized into the card/`PostDetailRoute` payload), and `mobile-home-tab-host` wires the actual `ProfileRoute(authorUserId)` root-stack push at the call site (MODIFIES `mobile-nearby-timeline`, `mobile-global-timeline`, `mobile-home-tab-host`). This removes the "no profile screen exists yet — issue #196" non-tappable rationale on the card.
- **Follow / unfollow** — optimistic toggle backed by `POST` / `DELETE /api/v1/follows/{id}` (both 204, idempotent); revert on failure; `429` surfaces a churn-rate-limit message; the initial state is `followedByViewer` from the profile read.
- **Block** — kebab "Blokir @{username}" → confirmation modal (`docs/03-UX-Design.md` § Block User UX copy) → `POST /api/v1/blocks/{id}`; on success a toast + **pop back** (the just-blocked profile would collapse to `404` on any re-read; the backend removes follows both directions server-side).
- **Report** — kebab "Laporkan" → reason picker (the 6 user-facing categories) + optional 200-cp note → `POST /api/v1/reports` with `target_type = "user"`; success toast; `409 duplicate_report` → an "already reported" message; self-report is structurally impossible (no kebab on the self read).
- **DTOs mirror the SHIPPED wire** — `UserProfileResponse` is **camelCase** (`userId`, `displayName`, `followerCount`, `followedByViewer`, `isPremium`, `isPrivate`), with `bio` / `isPrivate` **nullable-with-default** (the app-wide `Json { explicitNulls = false }` omits them); the report request body is **snake_case** (`target_type`, `target_id`, `reason_category`, `reason_note`). Casing is generated from the shipped routes, not stale spec JSON.
- **No new Flyway migration; no new library pin** — pure consumption of shipped endpoints; `gradle/libs.versions.toml` untouched.
- **Explicit deferrals** (captured as spec requirements with negative guards + `follow-up` GitHub issues): post-detail author-identity tap (blocked by the `PostDetailRoute` no-author-UUID serialization discipline); follower/following **list** screens (counts shown, not tappable); **edit-profile** (no backend write endpoint shipped); **suspension-countdown** on the profile (not carried by `user-profile-read` by design).

## Capabilities

### New Capabilities
- `mobile-profile`: the `:mobile:app` profile surface — `ProfileScreen` + the payload-carrying `ProfileRoute`, the self-section vs other-overlay rendering, the profile read behind a `ProfileFlow` seam with a sealed `ProfileOutcome`, the follow/unfollow toggle, the block (confirmation modal) + report (reason picker) actions, the pure Compose-free UI-state projection, Koin wiring, the new Bahasa Indonesia strings, the test trio (Robolectric + commonTest + iosTest), and the explicit deferral requirements (post-detail tap, follower/following lists, edit-profile, suspension countdown).

### Modified Capabilities
- `mobile-home-tab-host`: the Profil section renders the **live self `ProfileScreen`** instead of `ProfilePlaceholderScreen`; and the host hoists `onOpenProfile`, wiring a `ProfileRoute(authorUserId)` **root** back-stack push at the `AppEntryProvider` call site (a new host navigation behavior parallel to the existing `onOpenPost` push).
- `mobile-post-card`: the identity header (avatar + display name + @handle) becomes a separate tap target invoking a hoisted `onOpenProfile` callback; the card model still carries **no author UUID** (the host binds the userId by closure), and the whole-card `onOpen` still fires for taps outside the identity region and the two action affordances.
- `mobile-nearby-timeline`: the Nearby card's identity wires a hoisted `onOpenProfile` carrying the `authorUserId` the screen already parses (never rendered, never serialized into the card payload); the screen stays navigation-free.
- `mobile-global-timeline`: the Global card's identity wires the same hoisted `onOpenProfile`.

## Impact

- **Module**: `:mobile:app` only — `screens/profile/ProfileScreen.kt` (replacing `ProfilePlaceholderScreen.kt`), `profile/` ApiClient + repository + DTOs + sealed outcome, `profile/ProfileUiState.kt` projection, `di/MobileModule.kt`, `screens/routing/NavKeys.kt` (`ProfileRoute`) + `AppNavSerialization.kt` polymorphic registration + `AppEntryProvider.kt` mapping & call-site push, `ui/components/PostCard.kt` (identity `onOpenProfile`), `screens/shell/AppShellScreen.kt` (Profil section → self `ProfileScreen`), `screens/timeline/NearbyTimelineScreen.kt` + `GlobalTimelineScreen.kt` (identity callback). `:shared:resources` gains the profile/block/report strings (`SharedStringsCatalogTest` count bumped).
- **Backend**: none — consumes shipped `user-profile-read` / `follow-system` / `user-blocking` / `reports` endpoints. No migration, no new endpoint.
- **Wire contract source of truth**: `backend/ktor/.../user/UserProfileRoutes.kt` (`UserProfileResponse` camelCase), `follow/FollowRoutes.kt` + `block/BlockRoutes.kt` (path-param, 204, no body), `moderation/ReportRoutes.kt` (`{target_type,target_id,reason_category,reason_note}` snake_case) — NOT any stale spec JSON example.
- **Auth**: Bearer + 401 refresh owned by the shipped `HttpClient` `Auth` plugin (not reimplemented). None of these endpoints are per-session soft-capped → no `X-Session-Id` header.
- **PII / safety**: the target `userId` is the route's resource key (necessary for the keyed read), never rendered as a UI string; no coordinates anywhere; `HttpClientFactory` stays at `LogLevel.HEADERS` (no body/token logging).
- **`follow-up` issues**: closes [#196](https://github.com/aditrioka/nearyou-id/issues/196) at archive; opens new `follow-up` issues for the post-detail author-identity tap, the follower/following list screens, edit-profile (pending a backend write endpoint), and the profile suspension-countdown (pending the auth-boundary surface).
- **Standards**: conforms to `docs/11-Engineering-Standards.md` Pattern Registry (state holder, navigation, data layer) with no new pattern introduced — see `design.md` § Standards conformance.
