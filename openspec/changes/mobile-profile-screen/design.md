## Context

`:mobile:app` has shipped the read + engage surfaces (`mobile-nearby-timeline`, `mobile-global-timeline` hosted by `mobile-home-tab-host`; `mobile-post-creation`; `mobile-post-detail` with like + reply; `mobile-inline-post-actions`). The authenticated root is the section shell (`mobile-home-tab-host`: Home / Notifikasi / Profil) where Profil renders `ProfilePlaceholderScreen` and other-user surfaces are reached as root-stack overlays (the `PostDetailRoute` pattern). The backend social graph is fully shipped: profile read, follow, block, report. This change adds the profile surface that consumes them and gives the app its first follow action.

Established mobile patterns this change mirrors (do not re-invent):
- **Screen + ApiClient + Repository-behind-a-`*Flow`-interface + pure Compose-free UI-state projection + Koin singletons** (`mobile-post-detail`, `mobile-nearby-timeline`).
- **Status + `error.code`-driven sealed outcome with no generic fallthrough** (`PostDetailRepository`'s outcomes).
- **Root-back-stack overlay navigation via a payload-carrying `@Serializable` `NavKey`** registered in the polymorphic `navSavedStateConfiguration` (`PostDetailRoute`).
- **Hoisted navigation lambdas keep feed screens navigation-free** (`onOpenPost`, `onSeeGlobal`); the actual back-stack push lives at the `AppEntryProvider` call site, not inside the screen.
- **DTOs generated from the SHIPPED wire, not stale spec JSON** (the PR #128 timeline casing-drift lesson).
- **Shared identity sub-components** — the `mobile-post-card` letter-avatar + display-name + @handle treatments are reused by `PostDetailScreen`'s header so they cannot drift; `ProfileScreen` reuses them too.
- **All UI strings via `:shared:resources` `Res.string.*`**; `SharedStringsCatalogTest` count assertion.
- **Test trio**: Robolectric `*ScreenTest` (Release-excluded), commonTest projection, iosTest flow.

Constraints discovered while scoping (all verified against the shipped specs/source):
- **`GET /api/v1/users/{user_id}` returns camelCase** `UserProfileResponse` with `bio` / `isPrivate` **omitted-when-null** (`Json { explicitNulls = false }`) — client DTO fields must be nullable-with-default. `isPrivate` is **self-only** (absent on other reads). `isPremium` is `true` iff `subscription_status = premium_active`. The `404 user_not_found` body is **constant/byte-identical** across unknown / shadow-banned / soft-deleted / blocked-either-direction — the screen MUST NOT try to distinguish them.
- **Suspension is NOT carried by the profile read** — by design (`user-profile-read` § "Suspension state is NOT carried by this endpoint"): suspension is session-terminating, so a suspended principal is rejected at the auth boundary and can never reach the read. There is no data to render a suspension countdown here.
- **The timeline wire carries `authorUserId`** (a UUID) which the host screens parse but never render or serialize; the card model and `onOpenPost` / `PostDetailRoute` payloads deliberately **exclude** the UUID (PII discipline).
- **`PostDetailRoute` MUST NOT declare the author UUID** (`mobile-post-detail` § route spec) — so post-detail's author identity cannot navigate to a profile without changing that serialization discipline or adding a by-id endpoint; deferred (D6).
- **The report wire** is `{ "target_type", "target_id", "reason_category", "reason_note"? }` (snake_case); `reason_category` ∈ `spam` / `hate_speech_sara` / `harassment` / `adult_content` / `misinformation` / `self_harm` / `csam_suspected` / `other`. The UX reason picker exposes only the **6 user-facing** categories (`docs/03-UX-Design.md` § Report UX); `self_harm` + `csam_suspected` are internal-only and NOT user-pickable (D5).
- **Follow / block endpoints are path-param + 204, no body**; follow+unfollow share a 50 actions/hour limit (`follow-system` § rate limit, `{scope:rate_follow}`), block 30/hr, report 10/hr; the 429 error code is `rate_limited` with a `Retry-After`; report duplicate → `409 reports.duplicate`.

## Goals / Non-Goals

**Goals:**
- A `ProfileScreen` rendering own (self) and other-user profiles from the shipped `GET /api/v1/users/{user_id}`, with the design-system loading / not-found / error / refresh states.
- The first follow action in the app (optimistic toggle), plus user-level block (confirmation modal) and report (reason picker), consuming the shipped endpoints with status/`error.code`-driven sealed outcomes.
- One reachable entry to other-user profiles — the feed-card author identity — so follow is demoable end-to-end (feed → author → follow).
- Replace the Profil-section placeholder with the live self profile.
- Full test parity (Robolectric + commonTest + iosTest) and PII discipline (no UUID rendered, no coordinates, no body/token logging).

**Non-Goals (deferred — see Decisions D6 + the spec's deferral requirements + `follow-up` issues):**
- Post-detail author-identity tap → profile (blocked by the `PostDetailRoute` no-author-UUID discipline).
- Follower / following **list** screens (counts are shown as static numbers; `GET /users/{id}/followers|following` + `social-list-profile-summaries` stay unused on mobile for now).
- **Edit-profile** (bio / display-name / username) — no backend write endpoint is shipped (`user-profile-read` is read-only; Premium username customization is DESIGN-status with no `PATCH /api/v1/user/username`). The mockup "edit profil" frame is not built.
- **Suspension-countdown** state on the profile (no backing data — see Context).
- Hide-distance / privacy toggles + block-list management (those belong to live-menu #5 `mobile-settings-screen`).
- Profile photos (no media-upload capability exists; the letter avatar is the only avatar, as on the cards).

## Decisions

### D1 — Self via the Profil section; other-user via a root-stack `ProfileRoute(userId)` overlay
The SAME `ProfileScreen` composable renders both, parameterized by the resolved profile + an `isSelf` flag (driven by the endpoint's `isSelf`, not a client guess). **Self**: rendered inset-free in the shell body when the Profil section is selected (replacing `ProfilePlaceholderScreen`); the self `userId` is read from the session/auth layer (not a nav arg), and the screen owns no top app bar (the shell renders no top bar on the Profil section per `mobile-home-tab-host`). **Other-user**: a payload-carrying `ProfileRoute(userId)` pushed onto the **root** back stack (overlaying the tab bar, exactly as `PostDetailRoute`), owning its own back-bar chrome. **Alternative considered:** a single nav route for both (self = own id). Rejected: self already has a home (the Profil section) and routing self through an overlay would double the back-stack and the top-bar story; keeping self in-section matches the shell contract. `ProfileRoute` is `@Serializable` and registered in the `navSavedStateConfiguration` polymorphic `SerializersModule` (iOS-saveable), the second payload-carrying route after `PostDetailRoute`.

### D2 — One `ProfileRepository` behind a `ProfileFlow` seam with a sealed `ProfileOutcome`
A single repository exposes `loadProfile(userId)`, `follow(userId)`, `unfollow(userId)`, `block(userId)`, and `report(userId, reasonCategory, note)`, mapping each HTTP status + transport failure to exactly one sealed member — no generic `else`/wildcard, `401` delegated to the `Auth` plugin, `CancellationException` rethrown (never mapped to a network error). `loadProfile` → `ProfileOutcome` (`Loaded(profile)` / `NotFound` / `NetworkError`); `follow`/`unfollow` → `FollowToggleOutcome` (`Followed` / `Unfollowed` / `RateLimited(retryAfterSeconds)` / `TargetGone` / `NetworkError`); `block` → `BlockOutcome` (`Blocked` / `RateLimited(retryAfterSeconds)` / `NetworkError`); `report` → `ReportOutcome` (`Submitted` / `Duplicate` / `RateLimited(retryAfterSeconds)` / `NetworkError`). One cohesive surface → one fake (`FakeProfileFlow`) drives all screen-test paths (the one-repo-per-screen precedent). The ApiClient(s) MAY be split internally (e.g. a profile-read client + a follow/block/report actions client) but are wired as Koin singletons reusing the shared `HttpClient` (no new client, no `X-Session-Id`).

### D3 — `followedByViewer` seeds the toggle; optimistic flip, revert on failure
The follow toggle's initial state is the profile read's `followedByViewer`. A tap flips optimistically and issues `POST` (follow) / `DELETE` (unfollow) — both return 204 idempotently (DELETE is a no-op when no edge exists, never 404). On a non-204 / network failure the local state reverts; `429` reverts AND surfaces the follow-churn rate-limit message (`Retry-After` preserved). The self read never shows the toggle (`isSelf = true`). **Note:** the displayed `followerCount` is the read snapshot; an optimistic follow does NOT mutate the count locally (the count is a raw public aggregate per `user-profile-read` design D1, and a single follow's ±1 on a stale snapshot is not worth a divergence risk) — absolute count accuracy is not promised for a read snapshot, matching the no-live-refresh reality.

### D4 — `ProfileRoute` carries the `userId` resource key only — never coordinates or tokens
`ProfileRoute(userId: String)` carries exactly the target user id — the resource key the keyed read (`GET /users/{userId}`) structurally requires; a profile route without it is impossible. The `userId` is **never rendered** as a UI string (it is used only as the API path param), consistent with the cards' no-UUID-rendered discipline. It MUST NOT carry `latitude`/`longitude` or any token. This is a deliberate, narrow distinction from the `PostDetailRoute` no-author-UUID rule: that rule keeps an *incidental* author id out of a *post*'s payload (the post screen does not need it); here the user id is the *primary* resource key of a *user* route (it is the whole point of the route). The userId is already transmitted on the timeline wire to every client (`authorUserId`), so it is not secret material like a token or location-PII like coordinates. An iOS saved-state round-trip test exercises the `ProfileRoute` serializer.

### D5 — Report reason picker exposes the 6 user-facing categories; maps to the wire enum
The reason picker shows the six `docs/03-UX-Design.md` § Report UX categories — Spam / Ujaran kebencian (SARA) / Pelecehan / Konten dewasa / Misinformasi / Lainnya — each a `:shared:resources` string, mapped to the wire `reason_category` values `spam` / `hate_speech_sara` / `harassment` / `adult_content` / `misinformation` / `other` (a pure, exhaustively-tested enum→wire mapping in commonMain). `self_harm` and `csam_suspected` are valid wire values but are **internal/automated classifications**, NOT user-pickable (no UX-doc category exposes them) — deliberately omitted from the picker. The optional note is a ≤200-Unicode-code-point field gated client-side (the submit disables past 200 cp) to match the server's `≤200` validation; `reason_note` is omitted from the body when blank.

### D6 — Post-detail author-identity tap → profile is DEFERRED; feed cards are the entry point
Feed cards are the entry to other-user profiles: the host screen already holds `authorUserId` in memory (parsed from the timeline DTO, never rendered/serialized), so it can bind a hoisted `onOpenProfile` and build `ProfileRoute(authorUserId)` at the `AppEntryProvider` call site without the UUID ever entering the card model or a serialized card payload. **Post-detail** renders the author identity too, but reaching its author's profile requires the author UUID, which `PostDetailRoute` is spec'd to NOT carry (the serialization discipline). Adding it would relitigate that rule (or need a `GET /posts/{id}` by-id endpoint that does not exist). To keep this keystone focused, post-detail identity-tap is **deferred** to a `follow-up` issue; the card-tap entry is sufficient for the follow demo (feed → author → profile → follow). The card's "no profile screen exists yet — issue #196" non-tappable rationale is removed for the card; the identical comment in `PostDetailScreen.PostHeader` stays (its tap is the deferred item).

### D7 — `ProfileScreen` identity reuses the card avatar/identity sub-components
The profile header's letter avatar + display name + @handle reuse the same `mobile-post-card` sub-components / derivation (`LetterAvatar`, the deterministic-color mapping keyed on `authorUsername`/`username`, the @-handle `stringResource` format) so the identity treatment cannot drift across cards / post-detail / profile. The bio (when non-null) and the Premium badge are profile-specific additions; the badge uses an M3 icon + `stringResource` label (no color-only signal).

### D8 — Block confirms then pops; the count/follow state is not re-fetched
Block is a destructive, modal-confirmed action (`docs/03-UX-Design.md` § Block User UX): kebab → confirmation modal (red "Blokir" / "Batal") → on confirm `POST /api/v1/blocks/{id}`. On 204 the screen shows the success toast and **pops back** (an other-user overlay) — the just-blocked profile would `404` on any re-read and the server has removed follows both directions, so staying on a now-invalid profile is wrong. Block from the self profile is impossible (no kebab on self). Unblock / block-list management is Settings (`mobile-settings-screen`), out of scope.

### D9 — Counts shown as static numbers; list screens deferred
The follower / following counts render as static numbers (`followerCount` / `followingCount` from the read). They are NOT tappable to member lists in this change — the `GET /users/{id}/followers|following` + `social-list-profile-summaries` list screens are a `follow-up`. Rationale: the live-menu row #1 specifies counts, not list screens; the follow demo is reachable via the card-tap entry; and the list screens (paginated, viewer-block-filtered, `akun_dihapus`-placeholder rows) are a cohesive separate surface. The counts therefore carry no click affordance (no dead controls).

## Standards conformance

Per `docs/11-Engineering-Standards.md` (MUST-read, proposal phase) — this change builds on existing Pattern-Registry patterns and introduces **no new pattern**, so no docs/11 amendment is required:
- **State holder (§ 2.2):** `ProfileViewModel` = androidx `ViewModel` in commonMain (JetBrains lifecycle) via `koinViewModel()`, scoped to the Nav3 entry; exposes ONE `StateFlow<ProfileUiState>` via `stateIn(viewModelScope, WhileSubscribed(5_000), initial)`, collected with `collectAsStateWithLifecycle()`. `ProfileUiState` separates initial-load vs refresh fields per `mobile-design-system`; one-shot events (block→pop-back, toasts, the `429`/duplicate banners) are modeled as **nullable state fields cleared via `onXxxShown()`** — NOT `Channel`/`SharedFlow` (the documented anti-pattern). Data work runs in `viewModelScope`, never from composables.
- **Navigation (§ 2.3):** Navigation 3 — `ProfileRoute` added as an `entry<ProfileRoute>` in `appEntryProvider`, registered in the polymorphic `navSavedStateConfiguration`; the existing decorator order (saveable-first, viewModelStore-second) and the root-stack overlay mechanism are reused unchanged. The self profile composes under the Profil section of the shell (no new route).
- **Data layer (§ 2.4 / § Dependency direction):** `ProfileApiClient` (Ktor client + kotlinx.serialization DTOs) + `ProfileRepository` (domain mapping, sealed `*Outcome` at the boundary); the ViewModel talks to `ProfileFlow` (the repository), never the ApiClient. The shared `HttpClient` + `Auth` bearer plugin + base-URL config are reused (no new client). Retries: none hand-rolled; these are user-initiated one-shot mutations.
- **Naming coherence (§ Naming):** `ProfileScreen` / `ProfileViewModel` / `ProfileUiState` / `ProfileRepository` / `ProfileApiClient` / `ProfileRoute` / `ProfileFlow` / `ProfileOutcome`.
- **UI look-and-feel:** conforms to `mobile-design-system` (single-Scaffold inset ownership, M3 icons, Bahasa Indonesia via `:shared:resources`, the loading/refresh + empty/error contract) and the canonical mockup (`nearyou-screens-mockup.html` frame 3 "Profil", per docs/11 § 2.8) consulted at `/opsx:apply`.

## Risks / Trade-offs

- **[Stale follower count]** The count is a read snapshot; an optimistic follow does not bump it (D3). → Accepted: absolute accuracy isn't promised for a read snapshot, the count is a raw public aggregate, and a pull-to-refresh re-reads it. Showing a momentarily-off-by-one count is less bad than a local count that diverges from the server's raw aggregate.
- **[Block-then-stay invalid state]** Staying on a profile you just blocked would `404` on refresh. → D8 pops back on block success; a screen test asserts the pop.
- **[Casing drift]** A future contributor "normalizes" the profile DTO casing and breaks parsing. → commonTest parses against the shipped camelCase wire incl. omitted-`bio`/omitted-`isPrivate` fixtures, and a negative guard asserts a snake_case `user_id` body does NOT populate `userId`.
- **[userId in the serialized back stack]** `ProfileRoute` carries the userId. → D4: the userId is the route's necessary resource key (not coordinate-PII / not a token), already on the timeline wire, never rendered; this is a narrow, documented distinction from the `PostDetailRoute` no-author-UUID rule, not a weakening of it.
- **[Scope size]** Profile read + follow + block + report + the card-tap entry is larger than a single menu item. → It is one cohesive surface ("view and act on a user"), each sub-feature reuses a proven pattern, and the keystone is explicitly the dependency-upstream of the Following feed. The natural split line if review finds it too large is block+report (defer to a kebab-actions follow-up), but a follow-only profile with no safety actions reproduces a different dead-end (you can follow a harasser but not block/report them), so the safety-complete scope is preferred. Lists, edit-profile, post-detail tap, and suspension are already split out.

## Migration Plan

No schema migration (pure consumption of shipped endpoints). No new library pin (`gradle/libs.versions.toml` untouched) → the pre-implementation library re-check gate does not apply. Mobile-only change with no backend/deploy impact → the pre-archive staging smoke step is N/A (mark Section 6 N/A in the archive commit). Rollback is a straight revert of the squash-merged commit; the only surface that visibly regresses is the Profil section (back to the placeholder) and the card identity tap (back to whole-card-open).

## Open Questions

- **Block-then-pop vs block-then-disable** — block pops back (D8). An alternative is to stay and render a "blocked" empty state. Resolved toward pop-back (the profile is now unreadable; nothing meaningful remains), with the toast as the confirmation; revisit if review prefers an in-place blocked state.
