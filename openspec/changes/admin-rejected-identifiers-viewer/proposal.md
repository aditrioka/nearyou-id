## Why

The shipped age gate inserts a hashed identifier into `rejected_identifiers` on every under-18 rejection (`reason = 'age_under_18'`) and after N persistent attestation failures (`reason = 'attestation_persistent_fail'`) to block DOB-shopping / attestation-bypass brute force ([`docs/06-Security-Privacy.md` § Under-18 Bypass Prevention](../../../docs/06-Security-Privacy.md)), but there is **no admin surface to see this table**. Two gaps result: (1) a moderator cannot watch the "`rejected_identifiers` insert rate" / "age gate rejection rate" anomaly signals that [`docs/07-Operations.md` § Operational Dashboard](../../../docs/07-Operations.md) lists — a rejection spike is a brute-force-signup signal; (2) clearing a falsely-rejected legitimate adult so they can re-verify (the "purgeable via legitimate adult re-verification workflow" path in [`docs/05-Implementation.md` § Rejected Identifiers Schema](../../../docs/05-Implementation.md)) is today a raw-SQL `DELETE` a human runs against the Supabase dashboard. This change ships the **read-only audit/triage half** ([`docs/07-Operations.md` § Core Features → "Rejected Identifiers Viewer"](../../../docs/07-Operations.md), [`docs/08-Roadmap-Risk.md` Phase 3.5 #27](../../../docs/08-Roadmap-Risk.md)); the manual-clear write action is a deferred fast-follow.

## What Changes

- **New read-only route `GET /admin/rejected-identifiers`**, wired INSIDE the existing `admin-login` session + CSRF gate (`authenticate(ADMIN_AUTH_NAME)`; any valid admin session, not role-restricted — matching `admin-actions-log-viewer`), rendering a moderator anti-abuse triage table over the `rejected_identifiers` table. The implementation mirrors the shipped `admin-actions-log-viewer` (`GET /admin/actions-log`) end-to-end.
- **Newest-first paginated table** (`rejected_at DESC, id DESC`) via a **keyset cursor over `(rejected_at, id)`** (no SQL `OFFSET`) — mirroring the `admin-actions-log-viewer` pagination contract. Each row displays `identifier_hash` (the one-way SHA-256, rendered as the hash — monospace, never reverse-resolved), `identifier_type`, `reason`, and `rejected_at`.
- **Composable, AND-combined, index-aligned, parameterized filters**: `reason` (`age_under_18` / `attestation_persistent_fail`), `identifier_type` (`google` / `apple`), and a `from`–`to` `rejected_at` date range (inclusive lower, exclusive `< to + 1 day` upper).
- **Per-reason / per-type count summary** for the current filter scope (the anti-abuse aggregate — the new behavior beyond the actions-log precedent), so a moderator can spot a rejection spike at a glance.
- **HTML-escapes every rendered value** and supports **HTMX partial-swap** (`HX-Request` → table fragment) with a plain-`GET` progressive-enhancement fallback. (XSS surface is lower than the actions-log viewer — `rejected_identifiers` has no free-text / client-controlled column — but escaping is applied as defense-in-depth.)
- **PII discipline**: the view displays only the one-way `identifier_hash`; it never attempts to resolve or surface a raw identifier (email / Google `sub` / Apple `sub`) — none is stored, by design ([`docs/06-Security-Privacy.md`](../../../docs/06-Security-Privacy.md): "only the hashed Google/Apple identifier is stored").
- **Strictly read-only** (explicit negative-guard requirement): the route writes **zero** `admin_actions_log` rows, mutates no table, and wires no `POST`/`PUT`/`PATCH`/`DELETE` handler.
- **No Flyway migration, no new dependencies.** The table + index shipped at V3; the change keeps its migration footprint disjoint (no V19 contention with the in-flight `admin-report-queue-viewer`).
- **Explicitly deferred (recorded as spec requirements, not just prose)**: the **manual support-clear action** (admin `DELETE` of a `rejected_identifiers` row to let a falsely-rejected legitimate adult re-verify — role-gated + CSRF-gated + audit-logged + rate-limited) → fast-follow `admin-rejected-identifiers-clear-action`. This change captures it as a positive deferral requirement + a negative guard so the fast-follow has a requirement to MODIFY.
