> **Scope (OQ1 = full in-row enforcement, chosen at review):** the moderation-queue resolution endpoint PERFORMS the enforcement it names (`keep`/`hide` content visibility, `suspend_author_7d`/`ban_author`/`shadow_ban_author` author actions). `delete` + the username resolutions are rejected (out of scope). Suspend is REUSED from `admin-user-moderation`; permanent-ban + shadow-ban are the two new enforcement writes. No Flyway migration. See design Risks: this raises the urgency of the `admin-destructive-action-rate-limit` follow-up — recommend sequencing it next.

## 4. Tests (Kotest — one per spec scenario; do NOT skip any)

- [ ] 4.1 Report status: pending → `actioned` and → `dismissed` set `status`/`reviewed_by`/`reviewed_at` + exactly one `report_resolved` audit row; `reviewed_by` = the acting (session) admin, not a sentinel.
- [ ] 4.2 Queue resolution: pending → `resolved` + `resolution` + `resolved_by`/`resolved_at` + exactly one `moderation_queue_resolved` audit row whose `after_state` records the resolution.
- [ ] 4.3 Content enforcement: `keep` un-hides a `post` (`is_auto_hidden=FALSE`); `hide` hides a `reply` (`post_replies.is_auto_hidden=TRUE`); `keep`/`hide` on a `user` target → `RejectedContentNotApplicable`, no write.
- [ ] 4.4 Author enforcement: `suspend_author_7d` suspends the post author (`is_banned`+`suspended_until`) + inserts `account_action_applied`; `ban_author` (as admin) permanent-bans (`is_banned=TRUE`,`suspended_until=NULL`) + notification; `shadow_ban_author` sets `is_shadow_banned=TRUE`; a `user`-target row resolves the author to the user itself (self-resolution) — e.g. `shadow_ban_author` on a `target_type=user` row flags that user; hard-deleted target → `RejectedAuthorUnresolvable` no write; suspend on an already-permabanned author → `RejectedSuspendGuard`, queue stays `pending`, no audit.
- [ ] 4.5 Ban tier: `moderator` + `ban_author` → `ForbiddenBanTier`, no `users` write, queue stays `pending`, no audit; `admin` + `ban_author` → applied.
- [ ] 4.6 Shadow-ban stealth: `shadow_ban_author` writes NO `notifications` row for the author (count unchanged) + `is_shadow_banned=TRUE` + one audit row; contrast: `suspend_author_7d` inserts exactly one `account_action_applied`.
- [ ] 4.7 Gating: unauth → 302 + no write; missing/invalid CSRF → 403 + `admin_csrf_violation` + no write; **CSRF-before-role** (a `read_only` admin with a bad CSRF token gets the CSRF rejection, not a role rejection); `read_only` role with valid CSRF → role-gated, no write.
- [ ] 4.8 Atomicity: inject an audit-insert failure (as in `UserModerationRepositoryTest`) on a `keep` resolution of an auto-hidden post → full rollback: `is_auto_hidden` stays `TRUE`, queue stays `pending`, no audit row.
- [ ] 4.9 Malformed + out-of-scope + idempotent: malformed `{id}` → 400 no write; `resolution=delete`/`accept_flagged_username`/garbage → rejected by the server-side allowlist, no write, not a 5xx; re-resolve an already-`resolved` row → no enforcement re-performed, no second audit row (count unchanged), `resolution`/`resolved_by` unchanged, no error.
- [ ] 4.10 No cascade: resolve an `auto_hide_3_reports` queue row (`hide`) with 3 `pending` sibling `reports` for the same target → queue `resolved`, all 3 reports stay `pending`.
- [ ] 4.11 In-row controls: a resolvable row renders the resolution form with a CSRF hidden field (inverts the read-viewer "no resolution control"); `reason_note` `<script>` escaped; successful no-JS `POST` → 303 back to `/admin/reports` preserving filters; `HX-Request` → fragment only.
- [ ] 4.12 GET listing unchanged: `GET /admin/reports` writes no audit + mutates nothing; bare `POST /admin/reports` → 405.
- [ ] 4.13 Deferred edit-history filter unchanged: `GET /admin/reports?has_edit_history=true` → 200, ignored.
- [ ] 4.14 Sequential-decision race: resolve a report `actioned` then immediately `dismissed` → the second is a no-op (status stays `actioned`; conditional-`WHERE status='pending'` means the first decision wins).
