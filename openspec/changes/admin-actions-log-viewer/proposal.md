## Why

Admin #1 ([`admin-schema-bootstrap`, PR #107](https://github.com/aditrioka/nearyou-id/pull/107)) shipped the V16 `admin_actions_log` table — eleven columns (`admin_id`, `action_type`, `target_type`, `target_id`, `reason`, `before_state`, `after_state`, `ip`, `user_agent`, `created_at` + PK `id`) and three secondary indexes (`admin_actions_admin_idx (admin_id, created_at DESC)`, `admin_actions_target_idx (target_type, target_id)`, `admin_actions_type_idx (action_type, created_at DESC)`) — designed audit-trail-preserving (`NO ACTION` FK default + role-level `REVOKE UPDATE, DELETE` for `admin_app`). Admin #3 ([`admin-login-argon2-totp`, PR #121](https://github.com/aditrioka/nearyou-id/pull/121)) made the table runtime-exercised: every `admin_login_success` / `admin_login_failure` / `admin_logout` / `admin_csrf_violation` now writes a row, all gated behind the `__Host-admin_session` cookie + CSRF middleware mounted by [`admin-panel-scaffold`](../../specs/admin-panel-scaffold/spec.md) (Pebble + HTMX, `Application.admin()` extension).

What's missing is the surface that makes those rows *useful*: there is no way to read the audit trail from inside the panel. The audit log is written but never displayed. This change ships **Admin #4** in the [`openspec/project.md`](../../project.md) § Mobile + Admin Scaffolding Priority menu — the **first admin business feature**: a read-only, paginated, filterable audit-log viewer at `GET /admin/actions-log`. The spec-source roadmap items are [`docs/07-Operations.md`](../../../docs/07-Operations.md) § Core Features ("**Moderation Actions Log**: immutable, retained 1 year, filter by admin/target/action. Reads `admin_actions_log`.") + § Admin Actions Log (Reference) ("queried in-app via the Moderation Actions Log UI"). Every subsequent admin *write* action (Admin #5 suspend/unban, chat redaction, CSAM handler invocation, feature-flag toggle) depends on an auditable trail being visible — the viewer is the read half that makes the audit-logging contract observable, and reaching it is one of the two objective triggers (alongside Mobile #5) for flipping the scaffolding-priority section back to balanced mode.

## What Changes

**New runtime read surface (ADDED in the `admin-actions-log-viewer` capability):**

- **Audit-log route.** `GET /admin/actions-log` — wired INSIDE the existing `authenticate(ADMIN_AUTH_NAME) { ... }` block in `Application.admin()`, so the session middleware from `admin-login` gates it (302 → `/admin/login` when unauthenticated). Renders a Pebble page extending the shared base layout: a table of `admin_actions_log` rows newest-first (`created_at DESC, id DESC`), each row showing the acting admin (resolved to `display_name` + `email` via a join to `admin_users`), `action_type`, `target_type` / `target_id`, `reason`, `ip`, `user_agent`, and `created_at`. `before_state` / `after_state` JSONB are surfaced on an expandable per-row detail, not inline in the summary row. Every rendered value is HTML-escaped via Pebble's default-on autoescaping — including the client-controlled `user_agent` and free-text `reason` (the highest-risk stored-XSS vectors), not only the JSONB columns.
- **Keyset pagination.** Fixed page size (50 rows). "Older" navigation uses a keyset cursor on `(created_at, id)` (both DESC) rather than SQL `OFFSET` — append-only logs grow unboundedly and offset pagination drifts + degrades; keyset aligns with the DESC indexes and is stable as new rows arrive. The cursor is an opaque `created_at|id` token passed as a query param.
- **Filtering.** Query params compose with AND: `action_type` (exact match, hits `admin_actions_type_idx`), `admin_id` (UUID, hits `admin_actions_admin_idx`), `target_type` + optional `target_id` (hits `admin_actions_target_idx`), and `from` / `to` ISO-8601 dates bounding `created_at` (served by the `created_at DESC` component of whichever equality index the query selects). The filter set is the **union** of the two canonical sources — `docs/07-Operations.md` § Core Features says "filter by admin/target/action"; the scaffolding menu says "action type / admin / date range" — reconciled in `design.md` D2 (each equality filter has a dedicated index; the date range rides the `created_at` index component when paired with one — the standalone date-only query scans+sorts, acceptable for a low-volume audit log per D2's caveat).
- **Safe filter parsing.** Malformed filter inputs (non-UUID `admin_id`, unparseable `from`/`to`, over-long `action_type`) are ignored with the rest of the query proceeding (lenient parse), never a 500 and never interpolated into SQL — all queries are `PreparedStatement`-parameterized. The page size and cursor are clamped to safe bounds.
- **HTMX progressive enhancement.** The filter form submits via `hx-get` swapping only the table fragment (`#actions-log-table`), and the "older" pagination control is an `hx-get` that swaps the same fragment; a plain full-page `GET /admin/actions-log?...` (no `HX-Request` header) renders the whole page identically (works without JS). Same dual-mode philosophy as the `admin-login` login redirect (D3).
- **Read-only posture.** The capability adds **only `GET`** handlers under `/admin/actions-log`. No `POST` / `PUT` / `PATCH` / `DELETE`. DB-level immutability is the `REVOKE UPDATE, DELETE ON admin_actions_log FROM admin_app` enforcement provisioned operationally (per [`docs/07-Operations.md`](../../../docs/07-Operations.md) § Data Access Pattern + [`admin-schema`](../../specs/admin-schema/spec.md) — out of scope here, already documented); this change relies on it rather than re-stating it.
- **No audit-on-read.** Viewing the audit log does NOT itself write an `admin_actions_log` row — reads are not auditable admin actions (consistent with `admin-login`'s decision to route the non-actor `email_not_found` failure to the structured logger, not the in-app audit surface). Rationale in D4.
- **Role access.** Any authenticated admin — including `read_only` — may view the log; the viewer is itself read-only, so the audit trail is transparent to every role rather than gated to `owner` / `admin`. Rationale in D5.

**Out of scope (deferred to focused follow-ups):**

- Admin write actions that *produce* new `action_type` rows (suspend/unban is Admin #5 `admin-suspend-unban-user-action`; chat redaction, CSAM handler, feature-flag toggle, manual referral grant are later changes per `docs/07-Operations.md` § Core Features).
- Deep-linking `target_id` to a target-entity admin detail page (e.g., user-management view) — those target pages do not exist until Admin #5+; the viewer displays `target_type` / `target_id` as text for now.
- CSV / JSON export of filtered results.
- Full-text search over `reason` / `before_state` / `after_state` (the V16 schema ships no GIN index on the JSONB columns; adding one is a separate schema change if the need materializes).
- Retention enforcement / archival job (the "retained 1 year minimum" contract is operational; no pruning worker ships here).
- RLS policies on `admin_actions_log` (deferred per `admin-schema` "RLS policies on admin tables are explicitly out of scope" — the `admin_app` scoped role + IAP are the canonical defenses).
- Real-time / auto-refreshing view (HTMX polling) — manual refresh / re-filter only.

## Capabilities

### New Capabilities

- `admin-actions-log-viewer`: The read-only in-app surface for the `admin_actions_log` audit trail. Owns the `GET /admin/actions-log` route (authenticated, wrapped by the `admin-login` session + CSRF middleware), keyset pagination over `(created_at, id)` DESC, composable index-aligned filters (`action_type` / `admin_id` / `target_type`+`target_id` / `from`+`to` date range), an `admin_users` join for human-readable actor display, HTML-escaped `before_state`/`after_state` detail rendering, HTMX partial-swap with plain-GET progressive-enhancement fallback, and the read-only-no-mutation posture that relies on the operational `REVOKE UPDATE, DELETE … FROM admin_app` for DB immutability. Builds on shipped infrastructure — the V16 schema ([`admin-schema`](../../specs/admin-schema/spec.md)), the auth gate ([`admin-login`](../../specs/admin-login/spec.md)), and the route subtree + base layout ([`admin-panel-scaffold`](../../specs/admin-panel-scaffold/spec.md)). Ships **one** performance-only Flyway migration (`V17` — a `(created_at DESC, id DESC)` keyset index on `admin_actions_log`; see `design.md` D9) and **zero new library pins**.

### Modified Capabilities

- None. The base-layout navigation stub in `admin-panel-scaffold` already anticipates functional links ("placeholder links — no functional pages behind them **until subsequent admin changes ship**"); wiring the "Audit Log" nav link to `/admin/actions-log` is the in-scope realization of that existing requirement, not a spec modification. It is captured as an implementation task, not a `MODIFIED` delta (see `design.md` D6).

## Impact

- `backend/ktor/src/main/kotlin/id/nearyou/app/admin/AdminModule.kt` — construct `AdminActionsLogRepository(dataSource)`; wire `adminActionsLog(repo, csrfHmacKeyProvider)` inside the existing `authenticate(ADMIN_AUTH_NAME) { ... }` block alongside `adminIndex(...)` + `logoutRoute` (threading the same `csrfHmacKeyProvider` already passed to `adminIndex(...)`). No change to the auth/CSRF wiring.
- `backend/ktor/src/main/kotlin/id/nearyou/app/admin/routes/AdminActionsLogRoute.kt` (new) — `fun Route.adminActionsLog(repo, csrfHmacKeyProvider)`: parses + clamps query params, calls the repository, builds the Pebble model (deriving `csrfToken` from the session cookie via `HashUtil.deriveCsrfFromSessionToken` exactly as `AdminIndexRoute` does, so the full-page render carries the layout's CSRF wiring), renders full page vs `#actions-log-table` fragment based on the `HX-Request` header (mirrors `AdminIndexRoute` + the `admin-login` HTMX/plain dual-mode).
- `backend/ktor/src/main/kotlin/id/nearyou/app/admin/actionslog/AdminActionsLogRepository.kt` (new) — `PreparedStatement`-parameterized SELECT against `admin_actions_log` LEFT/INNER JOIN `admin_users`, dynamic WHERE built from the active filter set, keyset cursor predicate, `LIMIT pageSize + 1` (the extra row signals "has older"). Plus `ActionLogRow` / `ActionLogQuery` / `ActionLogCursor` data classes. Admin-module raw-read exemption applies (per [`openspec/project.md`](../../project.md) § Coding Conventions — raw reads allowed in the admin module; `visible_*` + block-join rules do not apply).
- `backend/ktor/src/main/resources/templates/admin/` — `actions-log.peb` (full page extending the shipped base layout `layout.peb`: filter form + table fragment include), `actions-log-table.peb` (the swappable table + pagination fragment, included by both the full page and the HTMX partial response), and the existing `Audit log (stub)` nav entry in `layout.peb` edited to point at `/admin/actions-log` (drop the "(stub)" suffix) rather than a newly-added link.
- `backend/ktor/src/main/resources/db/migration/V17__admin_actions_log_created_idx.sql` (new) — the single performance-only index migration (see `design.md` D9).
- `backend/ktor/src/test/kotlin/id/nearyou/app/admin/` — repository integration tests (`AdminActionsLogRepositoryTest.kt`, DB-tagged; includes the `V17` index-existence assertion) + route tests (`AdminActionsLogRouteTest.kt`, `testApplication`).

**Affected APIs (HTTP surface).**

- `GET /admin/actions-log` — NEW. Authenticated (302 → `/admin/login` without a valid session). Accepts query params `action_type`, `admin_id`, `target_type`, `target_id`, `from`, `to`, `cursor`. Returns the full page on a plain GET; returns only the `#actions-log-table` fragment when `HX-Request: true`.
- No new state-changing endpoints. `POST` / `PUT` / `PATCH` / `DELETE` on `/admin/actions-log` surface as routing-layer 405 (no handler wired) — consistent with `admin-panel-scaffold`'s "Non-GET methods return 405" posture.

**Affected dependencies (`gradle/libs.versions.toml`).**

- None. Pebble + HTMX (Admin #2), the session/CSRF gate (Admin #3), and JDBC `PreparedStatement` are all already on the classpath. No new pin ⇒ the pre-implementation library re-check ([`openspec/project.md`](../../project.md) § Change Delivery Workflow) does NOT apply to this change (the trigger is "new substrate enters the codebase").

**Affected database tables:**

- `admin_actions_log` — first runtime `SELECT`s (read-only; the table has only been written to until now). Queries hit the three V16 indexes plus the new `V17` `admin_actions_created_idx`. No INSERT/UPDATE/DELETE.
- `admin_users` — additional read: join to resolve `admin_id` → `display_name` + `email` for actor display. No write.
- One migration: `V17__admin_actions_log_created_idx.sql` — a single non-partial composite index `admin_actions_created_idx (created_at DESC, id DESC)` serving the default + date-only keyset queries (see `design.md` D9). No column/table/constraint change.

**Affected operational state.**

- The "Audit Log" nav link becomes the first functional entry in the base-layout nav stub — a positively-observable signal that the first admin business feature has landed.
- Pre-archive staging smoke (per [`openspec/project.md`](../../project.md) § Staging deploy timing): authenticate against the staging test admin (provisioned in Admin #3), confirm the `admin_login_success` row written at login is visible in the viewer, exercise each filter + the "older" pagination control.
- **Production-REVOKE pre-condition (cross-change dependency, NOT this change's code).** The `FOLLOW_UPS.md` § `admin-app-revoke-staging-and-prod` entry names Admin #4 as the point where the operational `REVOKE UPDATE, DELETE ON admin_actions_log FROM admin_app` becomes load-bearing — a compromised `admin_app` connection lacking the REVOKE could mutate the audit trail, defeating the immutability invariant. **Staging-side REVOKE is COMPLETE (2026-05-17, [PR #109](https://github.com/aditrioka/nearyou-id/pull/109))**, so the pre-archive staging smoke is unaffected. The viewer itself is read-only and never issues UPDATE/DELETE, so its correctness does not depend on the REVOKE; the dependency is on the production side and is a pre-condition for *deploying any admin code to production*, tracked in that follow-up (production provisioning is deferred to the production-bootstrap milestone, same as Admin #3's secret slots). Surfaced here so the dependency is explicit rather than silently assumed; no new follow-up is filed (the existing entry covers it).

**Downstream unblocks.**

- Admin #5 (`admin-suspend-unban-user-action`) and every later admin write action gain a visible audit trail — the write half can be reviewed via this read half, closing the "audit-logged but unobservable" gap.
- Reaching this change (Admin #4) + Mobile #5 (`mobile-nearby-timeline-screen`) is the objective trigger to flip [`openspec/project.md`](../../project.md) § Mobile + Admin Scaffolding Priority back to balanced mode.
