## Why

The mobile profile screen renders the follower and following counts as **static numbers** — a deliberate "no dead controls" decision in `mobile-profile-screen` (PR #245), which shipped the requirement *"Follower and following counts render as static numbers"* and explicitly deferred the tappable list screens to a follow-up ([#260](https://github.com/aditrioka/nearyou-id/issues/260)). The natural consumer of those counts — paginated follower / following member lists — is the only missing half. The backing backend **already shipped and is currently UNUSED on mobile**: `GET /api/v1/users/{user_id}/followers` and `/following` (`follow-system`), enriched by `social-list-profile-summaries` to embed a profile summary per row with bidirectional viewer-block filtering and keyset pagination. So this is pure `:mobile:app` screen work — **zero backend, no Flyway migration, no new endpoint** — on the profile critical-path.

## What Changes

- **Follower/following counts become tappable** on `ProfileScreen`. Each count navigates to a new follow-lists screen opened at the matching tab. This **MODIFIES** the `mobile-profile` requirement *"Follower and following counts render as static numbers"* — its negative guard ("counts are not tappable, no clickable node, no list screen") inverts to a tappable affordance wired to `FollowListRoute`. The count VALUES are unchanged (still the read snapshot; no local mutation).
- **A single tabbed `FollowListScreen`** (operator-chosen shape, 2026-06-14) with two tabs — **Pengikut** (followers) / **Mengikuti** (following) — via `PrimaryTabRow` + `HorizontalPager` (the shipped feed top-tabs idiom). Reached via a serializable `FollowListRoute(userId, initialTab)` pushed onto the root back stack (the `ProfileRoute` pattern); the tapped count deep-links to its tab via `initialTab`.
- **Each tab is a paginated `LazyColumn`** over its shipped endpoint, consuming the embedded profile summary `{ userId, username, displayName, isPremium, createdAt }` (bare camelCase wire). Each row renders the **identity treatment reused from `mobile-post-card` / `mobile-profile`** (letter avatar + deterministic color + display name + `@username` + Premium badge) and taps through to `ProfileRoute(rowUserId)`.
- **Hidden members are EXCLUDED, not placeheld.** The `/followers` + `/following` endpoints source rows via INNER JOIN `visible_users`, so shadow-banned / soft-deleted edges disappear entirely — there are **no `akun_dihapus` placeholder rows** in these two lists. (Issue #260's text conflates this with the `GET /blocks`-only COALESCE masking from `social-list-profile-summaries`; corrected here. `username`/`displayName` are NOT NULL since V2, so no null-handling is needed either.)
- **Canonical list states** (`mobile-design-system`): separate `isInitialLoad` / `isRefreshing`, skeleton on first load, `PullToRefreshBox` over retained content on refresh, empty / error / not-found rendered inside a scrollable container, cursor-driven load-more on scroll-to-end (stop when `nextCursor` is null). The constant `404 user_not_found` maps to a single NotFound state. All copy via `:shared:resources` (single-language Bahasa Indonesia).
- **Inline follow/unfollow on the list rows is DEFERRED** (rows are navigational only → `ProfileRoute`, where the follow toggle already lives), captured as an explicit deferral requirement + tracked by a `follow-up` issue so a later change has something to MODIFY.

## Capabilities

### New Capabilities
- `mobile-follow-lists`: the `:mobile:app` follower/following member-list surface — `FollowListScreen` (tabbed Pengikut/Mengikuti), `FollowListRoute` NavKey, `FollowListApiClient` + `FollowListRepository`/`FollowListFlow` + `FollowListViewModel`, the per-tab `FollowListUiState` pure projection with keyset pagination over the shipped `/followers` + `/following` endpoints, row → `ProfileRoute` navigation, the canonical loading/refresh/empty/error/not-found contract, Bahasa-Indonesia copy, and the commonTest / Robolectric / iosTest trio. Deferred: inline follow/unfollow on rows; in-list search/filter.

### Modified Capabilities
- `mobile-profile`: the *"Follower and following counts render as static numbers"* requirement changes — the counts become **tappable** controls that navigate to `FollowListRoute(userId, initialTab)` (followers → Pengikut tab, following → Mengikuti tab). All other `mobile-profile` requirements are unchanged.

## Impact

- **Code (`:mobile:app` only)**: new `screens/followlist/` (`FollowListScreen`, tab content, identity row) + `followlist/` data layer (`FollowListApiClient`, `FollowListRepository`, `FollowListFlow`, DTOs, `FollowListUiState` + projection, `FollowListViewModel`); `screens/routing/NavKeys.kt` (`FollowListRoute` + polymorphic `SerializersModule` registration); `appEntryProvider` mapping + the root-stack push wiring (`mobile-home-tab-host`); `di/MobileModule.kt` Koin singletons reusing the shared `HttpClient`; `ProfileScreen` count-area edit (tappable). New `:shared:resources` strings + `SharedStringsCatalogTest` count bump. `mobile/app/build.gradle.kts` Release-variant test-exclude entry for `FollowListScreenTest`.
- **Backend / API / DB**: **none.** No Flyway migration, no new endpoint, no spec change to `follow-system` / `social-list-profile-summaries` — pure consumer of the shipped contract. (A grep of `mobile/` confirms these endpoints have no existing mobile consumer.)
- **Specs/tests**: ADDED `mobile-follow-lists` spec; MODIFIED `mobile-profile` spec (one requirement). New commonTest projection/parse/pagination/nav/serialization tests, a Robolectric `FollowListScreenTest`, an iosTest flow test; the inverted `ProfileScreenTest` counts-tappable assertion.
- **Issues**: **Closes [#260](https://github.com/aditrioka/nearyou-id/issues/260)**; opens follow-up(s) for the deferred inline-follow row action.
- **Mockup**: no dedicated follower/following list frame exists (screens board frame 3 "Profil — profil sendiri" shows the counts entry point only) — the list-row visual reuses the established identity-row idiom; the board gap is recorded as a design Decision.
