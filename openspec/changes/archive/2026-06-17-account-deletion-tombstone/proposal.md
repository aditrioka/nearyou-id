## Why

NearYouID has no account-deletion path today: a user cannot exercise the UU PDP (Indonesia Personal Data Protection law) **right to erasure**, which is a Pre-Launch compliance gate (`docs/08-Roadmap-Risk.md` Pre-Launch security checklist) and a Google Play / App Store store-policy requirement. The `deletion_requests` table that the admin **Hard Delete Queue** (`docs/07` Core Features) and the **Apple S2S account-delete** path (`docs/08` Phase 4 item 7) are specified to build on does not exist yet either. This change ships the user-initiated half — request → 30-day cancellable grace → tombstone+cascade hard-delete — and lays that shared foundation.

## What Changes

- **New `deletion_requests` table** (migration **V23**, next free above the V22 ceiling; the number MAY renumber at rebase since the in-flight `premium-image-upload-pipeline` / `referral-ticket-creation` PRs also eye V23) — created **exactly** per the canonical DDL in `docs/05-Implementation.md` § Deletion Requests Schema (id, user_id `ON DELETE CASCADE`, requested_at, scheduled_hard_delete_at, cancelled_at, executed_at, `source` CHECK over `user`/`apple_s2s_consent_revoked`/`apple_s2s_account_delete`/`admin`) + its two `NOW()`-free partial indexes.
- **New authenticated account-deletion API**: `POST /api/v1/account/deletion-request` (creates a `source = 'user'` row, `scheduled_hard_delete_at = NOW() + 30 days`; idempotent when an un-cancelled un-executed request already exists), cancel/restore within grace (sets `cancelled_at`), and a status read so the mobile banner can show the restore deadline. **The pending-deletion user is NOT session-terminated during grace** — they must be able to log in and restore.
- **New internal hard-delete worker** `/internal/account-hard-delete-worker` (Cloud Scheduler + internal-endpoint-auth OIDC + system-actor audit, mirroring `suspension-unban-worker` / privacy-flip-worker). When grace elapses it runs, **per due row in one transaction**: tombstone the user row (`deleted_at` + NULL the PII set + `username → deleted_user_<uuid_prefix>`), **cascade-delete** ephemeral/relational data, **anonymize-retain** authored content (author/sender renders "Akun Dihapus"), write an append-only deletion-log entry, set `executed_at`. Idempotent on re-run.
- **MODIFY the post-listing read surfaces** so a hard-deleted (tombstoned) author's *retained* content renders as "Akun Dihapus" **instead of vanishing** — the central crux (design **D1**, operator-confirmed): relax the **author-side** `deleted_at IS NULL` exclusion on the feed surfaces only — the `visible_posts` view (Following + counters) **plus** the Nearby/Global raw-`posts` timeline queries, post-detail, and reply-list — keeping the **post-soft-delete, shadow-ban, and bidirectional-block predicates byte-identical** (critical invariants untouched). `visible_users` is deliberately **unchanged**, so profile read stays `404` for a tombstoned target (docs/06:327 allows "404 or placeholder"; 404 is the lower-risk choice) and search/metrics keep excluding deleted users.
- **New append-only `deletion_log` table** (design **D2**) — the canonical destination is R2 (7-year retention) but `:infra:r2` is DESIGN/unbuilt, so the in-scope cut is a DB table now; R2 export deferred (the Pre-Launch backup-reconciliation test depends on a deletion log *existing*).
- **Mobile**: Settings gains a "Hapus Akun" row → confirmation dialog (30-day grace, restore anytime in-window) → request endpoint; a scheduled-deletion banner with "Batalkan" / restore-by date. Strings via Compose Multiplatform Resources. (Deferred from `mobile-settings` design D8.)
- **Account Recovery stays None-by-design** (`docs/03` § Account Recovery): losing the Google/Apple account is final; the 30-day grace is the *only* restore window. No new recovery surface.

**Out of scope (downstream changes that reuse this foundation):** the `apple_s2s_*` and `admin` deletion sources + the Apple S2S immediate-execute path (Phase 4 item 7), the admin Hard Delete Queue UI (`docs/07`), R2 deletion-log export, and Data Export ("Unduh Data Saya", blocked on `:infra:resend` modularisation). The `source` CHECK and the source-agnostic worker design deliberately **do not preclude** them.

## Capabilities

### New Capabilities
- `account-deletion`: user-initiated deletion-request lifecycle — the `deletion_requests` schema, the request / cancel-restore / status endpoints, 30-day grace semantics, idempotency, and the during-grace auth-boundary rule (no session termination on request).
- `account-hard-delete-worker`: the internal worker that, when grace elapses, executes tombstone + cascade-delete + anonymize-retain + deletion-log write in a single transaction per due row, idempotently, under system-actor audit; owns the `deletion_log` schema and the exact per-table tombstone matrix.

### Modified Capabilities
- `visible-posts-view`: the `visible_posts` view **surfaces** a hard-deleted (tombstoned) author's posts with anonymized identity, rather than excluding them on the author-side `u.deleted_at IS NULL`; the post-soft-delete, shadow-ban, and bidirectional-block predicates are unchanged (design D1). The cross-surface "Akun Dihapus" render contract for the raw-`posts` timelines + post-detail is owned by the new `account-hard-delete-worker` capability's scenarios.
- `single-post-read`: a tombstoned author's post detail resolves to `200` anonymized (was `404`) — the "author soft-deleted → 404" clause is removed for the tombstone case (soft-deleted POSTS, shadow-banned authors, auto-hidden posts still `404`).
- `post-creation` / `post-replies` / `reports`: reconcile the now-stale "the hard-delete worker deletes content + row-deletes the author" prose to the **tombstone-retain** model — under a tombstone (`UPDATE`, no row-delete) the `author_id RESTRICT` / `reporter_id` + `user_id CASCADE` FKs never fire, so posts/replies/likes/reports are RETAINED anonymized. The FK-behavior scenarios (raw-`DELETE` guards) are unchanged. This is the cross-cutting reconciliation the shipped specs anticipated under a different (delete-based) deletion model.
- `mobile-settings`: the Settings screen offers account deletion (the previously deferred, non-writing "Hapus Akun" affordance becomes a real request + restore flow with a scheduled-deletion banner).

## Impact

- **Migrations**: `V24__deletion_requests.sql` (+ `deletion_log`), and a `V24` view-replace for `visible_posts` **only** (design D1; `visible_users` untouched). `CREATE OR REPLACE VIEW`, no data backfill.
- **Backend** (`:backend:ktor`): a new `account` package (design D3) — routes + repository + the worker; the worker mounts under the existing `/internal/*` OIDC-gated subtree and writes a system-actor audit row. Touches the tombstone UPDATE on `users` (username-write + privacy-flag allowlist annotations) and the cascade/anonymize statements across `posts`, `post_replies`, `post_likes`, `post_edits`, `chat_messages`, `reports` (design D4 reconciles the reports cascade-vs-retain contradiction between `docs/05:508` and `docs/06:343`), `follows`, `user_blocks`, `user_fcm_tokens`, `notifications`, session/refresh-token tables.
- **Read surfaces** that surface tombstoned authors anonymized: Nearby / Following / Global timelines, post detail, reply lists, chat context cards (verified by `account-hard-delete-worker` + `visible-posts-view` scenarios). **Profile read, search, and active-user metrics deliberately keep excluding** tombstoned users (`visible_users` untouched).
- **Mobile** (`:mobile:app`): `mobile-settings` row + dialog + banner + Ktor client calls + CMP strings.
- **Critical invariants exercised**: username-write allowlist (`// @allow-username-write` for the `deleted_user_` rename), privacy-flag write rules, shadow-ban view safety (`visible_*` predicates preserved), bidirectional block join, internal-endpoint OIDC, `secretKey()` reads, no `NOW()` in partial-index `WHERE` (the new indexes are `NOW()`-free), Compose Multiplatform Resources for all mobile strings.
- **Docs reconciliation** (design D4 + B.3 pass): one of `docs/05:508` (reports `reporter_id ON DELETE CASCADE`) vs `docs/06:343` (reports "retain for audit") must be amended to match the chosen behavior; flagged in design, the loser filed as a `follow-up`/doc-amend note.
