## Why

The UU-PDP data-portability loop is half-built: the user-facing **producer** is shipped (`account-data-export` — `POST`/`GET /api/v1/account/export`, the OIDC `/internal/data-export-worker`, the `data_export_requests` table at V30, R2 ZIP delivery + the durable `data_export_ready` notification + Resend email), but it "adds no `/admin/*` route" (docs/07 § Admin Panel → **Data Export Queue**, explicitly **DEFERRED to [#361](https://github.com/aditrioka/nearyou-id/issues/361)**). Operators today have **no surface** to see who requested an export, what state it's in, or to recover a job the Cloud Scheduler worker failed or stalled on — a gap for both UU-PDP 7-day-SLA accountability and day-to-day support ("where's my export?"). This change ships the deferred admin counterpart-layer (docs/12 cohesion), closing a single-layer gap rather than opening a new one. The canonical visual already exists: admin mockup **frame 16 "DATA EXPORT QUEUE"**.

## What Changes

- **New admin read surface — `GET /admin/data-exports`.** A keyset-paginated, newest-`requested_at`-first list of `data_export_requests` joined to `users` for the requester's username. Columns per frame 16: **User** (username deep-links to `/admin/users?q=`), **Requested (UTC)**, **Status** (the 5 DB statuses surfaced as QUEUED / RUNNING / DELIVERED / EXPIRED / FAILED), **Delivered-via** (`data_export_ready` notification + email, shown once `ready`), and a per-row action cell. Composable parameterized filters: `status` + `q` (username / user-UUID). In-window count summary. HTML-escaped HTMX render with a plain-`GET` fallback. Any authenticated admin role may read. Index-served by the **existing** `data_export_requests_user_recent_idx` (and the pending partial index) — **no new migration**. Mirrors the shipped `admin-hard-delete-queue` (frame 15) and `admin-subscription-grace-monitor` (frame 18) read-surface idioms exactly.
- **Identity-only PII discipline — status, never contents.** The panel surfaces only the request's identity + lifecycle state. It **never** renders `r2_object_key`, the signed download URL, or any export payload (the archive is the user's own data, delivered only to them via a short-lived signed link). "Panel = orkestrasi status saja; isi export tidak pernah tampil" (frame 16).
- **New admin write action — `POST /admin/data-exports/{id}/trigger` ("Trigger job").** For a row the scheduled worker failed or stalled on, an operator re-runs the export. The action is **owner/admin-role + CSRF-gated** (CSRF-checked before the role check), `hx-confirm`-guarded, **requires a reason**, and is **rate-limited on a distinct 10/admin/hour counter** (sourced from the audit-trail-as-ledger limiter — operational/restorative, **not** the shared 20/hour destructive budget; precedent: the hard-delete-queue *expedite* and rejected-identifiers *clear* both use distinct 10/hr counters). It writes **exactly one** immutable `admin_actions_log` row (`action_type = 'data_export_triggered'`, before/after status snapshots) in one transaction.
- **The trigger reuses the existing producer pipeline — one export path, not a fork.** It re-enqueues the row to `pending` (where needed) and drives the worker's per-request processing for that single id, so a stuck job is delivered immediately rather than waiting on a possibly-broken scheduler. The worker's existing private per-request step is promoted to a reusable single-request seam consumed by **both** the batch worker and the admin trigger (anti-patchwork — see design.md Decision 1). The batch worker's behavior is unchanged.
- **Idempotent, structurally-safe rejection.** A trigger on a row that is `processing` or already-`ready` (valid link) is a benign no-op — **no mutation, no audit row** (mirrors hard-delete's "rejected for already-executed / cancelled / already-due / unknown target"). Re-enqueueing to `pending` honors the existing one-active partial UNIQUE index (`data_export_requests_one_active_idx`): a conflicting active row maps to "already active, no-op".
- **No Flyway migration.** The table + indexes ship at V30; `admin_actions_log.action_type` is a free `VARCHAR(64)` (no CHECK enum), so the new action-type string needs no schema change. This change is purely additive admin Kotlin + a Pebble template + tests — footprint disjoint from every in-flight migration claim.

## Capabilities

### New Capabilities

- `admin-data-export-queue`: the admin Data Export Queue surface — the keyset-paginated read list (columns, `status`+`q` filters, count summary, HTML-escaping, plain-`GET` fallback, any-admin-role read, identity-only PII / status-never-contents), and the `POST …/{id}/trigger` write (auth + CSRF-before-role + owner/admin + required reason + distinct 10/admin/hr rate limit + single immutable audit row + idempotent benign rejection + one-active-index-respecting re-enqueue + reuse of the producer's single-request pipeline).

### Modified Capabilities

- `account-data-export`: the export worker exposes a **reusable single-request processing seam** (the existing per-request claim → gather → ZIP → upload → set-`ready` → notify → email pipeline, addressable by a single `request id`) consumed by **both** the batch `/internal/data-export-worker` run and the new admin trigger. No change to the batch worker's scan/claim/fail-soft behavior, the user-facing `/api/v1/account/export` contract, the `data_export_requests` schema, or delivery semantics.
