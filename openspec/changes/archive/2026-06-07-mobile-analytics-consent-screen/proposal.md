## Why

The mobile onboarding chain has exactly one documented gap. Auth (`mobile-auth-google-signin-flow`), the 18+ age gate (`mobile-age-gate-screen`), and the location-permission flow (`mobile-location-permission-flow`) have all shipped, but the **Analytics & Tracking Consent screen** that [`docs/03-UX-Design.md`](../../../docs/03-UX-Design.md) § "Analytics & Tracking Consent Screen (UU PDP)" sequences **"After the age gate, before location permission"** does not exist. Mobile #4 (`mobile-age-gate-screen`) explicitly deferred it: its design Non-Goals state "*the analytics-consent and location-permission onboarding screens that `docs/03-UX-Design.md` sequences after the age gate — those are later changes; Mobile #4 routes a successful signup straight to `HomeScreen`*." **This change is that later change for the consent half.**

It is a **launch-gating legal requirement**, not a nice-to-have: [`docs/08-Roadmap-Risk.md`](../../../docs/08-Roadmap-Risk.md) risk-register line 403 records "*Analytics tracking without consent → UU PDP violation*", mitigated by "*Consent screen at onboarding + `analytics_consent` schema + suppress wrapper*." The schema half shipped in V2 (`users.analytics_consent JSONB`); the suppress-wrapper half is a separate later piece (Amplitude/Sentry/AdMob UMP SDKs are still DESIGN-status). This change ships the **onboarding-screen half** + the persistence endpoint that captures the user's choice — collecting consent *before* any tracking SDK is wired is the correct ordering (the wrapper later reads what this screen stored).

## What Changes

- **NEW: backend `PATCH /api/v1/user/consent`** in a new `user/ConsentRoutes.kt`, mirroring the authed-self pattern of `user/FcmTokenRoutes.kt` (`POST /api/v1/user/fcm-token`). RS256-JWT-authenticated; writes the complete `{analytics, crash, ads_personalization}` triple to `users.analytics_consent` for the JWT-`sub` user only. **NO Flyway migration** — the column shipped in V2 (`V2__auth_foundation.sql:22`, `JSONB NOT NULL DEFAULT '{"analytics": false, "crash": true, "ads_personalization": false}'`).
- **NEW: `ConsentScreen` in `:mobile:app` commonMain** — three Material 3 toggles (Analytics, Crash Reporting, Ads Personalization) defaulting to **analytics OFF / crash ON / ads OFF** (the V2 defaults), per-category explainer copy, and a primary "Lanjutkan" CTA that PATCHes consent and routes to `HomeScreen`. Explicit editing / submitting / error / success states — no generic fallthrough (matching the `mobile-nearby-timeline` six-state discipline).
- **NEW: `ConsentApiClient` + `ConsentRepository` + status-driven outcome seam** in `:mobile:app`, reusing the already-classpathed Ktor KMP client + `Auth { bearer }` interceptor (Mobile #3). New `ConsentRoute` `@Serializable` `NavKey` registered in the iOS-safe polymorphic serializer module.
- **MODIFIED routing**: the signup-success (`201`) terminus moves from "route straight to `HomeScreen`" to "route to `ConsentScreen`, which routes to `HomeScreen` on consent submit." The returning-user sign-in terminus is **unchanged** (returning users already onboarded; consent is first-run only).
- **NEW: Bahasa Indonesia strings** in `:shared:resources` (`composeResources/values/strings.xml`, via `stringResource(Res.string.X)`): screen title, the three category labels + descriptions (verbatim from `docs/03-UX-Design.md`), continue CTA, retry/skip copy. No hardcoded UI string literals.
- **NO new library pins** — Ktor KMP client, Material 3 `Switch`, Navigation 3, and CMP Resources are all already on the classpath and actively used (no pre-implementation library re-check triggered).

## Capabilities

### New Capabilities
- `analytics-consent-update`: the backend `PATCH /api/v1/user/consent` endpoint — RS256-JWT-authenticated, accepts `{analytics, crash, ads_personalization}` (all three booleans), full-object-writes `users.analytics_consent` for the JWT-`sub` user only, returns the stored triple; validation (`400` on malformed/partial body), authz (a user updates only their own row), `401` unauthenticated.
- `mobile-analytics-consent`: the mobile consent onboarding surface — `ConsentScreen` (three toggles + explainers + continue CTA, V2-default initial values), the `ConsentRepository.submitConsent(...)` orchestration against `PATCH /api/v1/user/consent`, the `ConsentOutcome` → explicit-state mapping (success / retryable-error / token-invalid), `ConsentRoute` navigation placement after age-gate signup, and PII discipline (no JWT/UUID logging).

### Modified Capabilities
- `mobile-age-gate`: the "Signup call uses the canonical endpoint…" requirement's **`201` terminus** changes from "a navigation event routing to `HomeScreen`" to "a navigation event routing to `ConsentScreen`" (the consent screen then routes to `HomeScreen`). No other age-gate behavior changes; the DOB-gate, `403`/`409`/`401` mappings, and PII discipline are untouched.
- `shared-resources`: a NEW `Analytics-consent Bahasa Indonesia strings` requirement is added (mirroring the existing `Nearby-timeline Bahasa Indonesia strings` precedent — per-feature string sets get their own requirement, the giant "Foundational" one is not re-MODIFIED) declaring `consent_title`, `consent_explainer`, `consent_analytics_label`/`_desc`, `consent_crash_label`/`_desc`, `consent_ads_label`/`_desc`, `consent_cta_continue`, `consent_error_retryable`, `consent_skip`; no earlier string is altered.

## Impact

- **Code**: NEW `backend/ktor/.../user/ConsentRoutes.kt` + request/response DTOs + the consent repository/service write path + Koin wiring; `:mobile:app` commonMain (`screens/consent/ConsentScreen.kt`, `ConsentUiState.kt`, `ConsentViewModel`, `consent/ConsentApiClient.kt` + `ConsentRepository.kt` + `ConsentFlow`, `ConsentRoute` in `screens/routing/NavKeys.kt` + `AppNavSerialization`, the signup-`201`-terminus swap in `AppEntryProvider.kt` — the `AgeGateScreen(onSignedUp = …)` callback that today calls `replaceAll(HomeRoute)` — and the `ConsentRoute`→`ConsentScreen` mapping there, `di/MobileModule.kt`); `:shared:resources` strings. (`RootRouterScreen` only handles cold-start token-presence routing and is NOT the 201 terminus.)
- **APIs**: NEW `PATCH /api/v1/user/consent` (authenticated). No other endpoint changes.
- **Schema**: none — `users.analytics_consent` JSONB already exists (V2). **Zero Flyway migrations** (no migration-number contention with any in-flight change).
- **Dependencies**: none added.
- **Security surface**: authed own-row write (a user updates only their own `analytics_consent`); no RLS *policy* change (so the RLS-policy-change test invariant does not trigger — but an own-row-authorization test IS included); `analytics_consent` is not on the username/privacy-flag write allowlists, so no `@allow-*-write` annotation is required (confirmed pre-flight); PII discipline (never log the JWT/`sub`/token).
- **FOLLOW_UPS.md**: adds `mobile-analytics-consent-settings-toggle` (the Settings-screen path that re-edits consent post-onboarding — deferred, depends on a Settings screen), `mobile-analytics-consent-persist-hardening` (reliable persist — retry/queue — so a failed PATCH cannot leave a tracking SDK mismatched, relevant only once the suppress-wrappers land), and `mobile-analytics-consent-rootrouter-regate` (re-gate returning token-bearing users on consent-not-completed, deferred — safe-defaults make it unnecessary for correctness in MVP).
- **Out of scope (Non-Goals)**: the consent-aware SDK suppress wrappers (Amplitude/Sentry/AdMob UMP) — collect-and-store only here; `:infra:amplitude` / `:infra:sentry` module scaffolding; the Settings-screen consent toggle; a retroactive consent prompt for accounts created before this screen (they keep the V2 default + use the future Settings toggle); ads; any platform-specific consent SDK (iOS + Android both build via CMP, no native consent dependency).
