# Proposal: mobile-search-screen

## Why

The mobile **Cari** (search) surface is live-menu pick #4 of `openspec/project.md` § Mobile-First to Full-Demo Priority — the last discovery surface the authenticated core loop is missing (sign in → browse → post → detail → like/reply → profile → follow → notifications → chat → **search**). The backend half is already shipped and frozen: the `premium-search` capability exposes `GET /api/v1/search?q=<query>&offset=<n>` (`backend/ktor/src/main/kotlin/id/nearyou/app/search/SearchRoutes.kt`) with the full Premium gate, the `2..100` query-length guard, the `60/hour` rate limit, the `10000` OFFSET cap, the `search_enabled` kill switch, and the canonical `visible_posts JOIN visible_users` block-exclusion/shadow-ban/private-profile query — every server-side concern is enforced and spec'd. The only gap is the **mobile consumer**: there is no `:mobile:app` screen that calls the endpoint. Building it now closes the discovery half of the demo with **zero backend work**, mirroring the proven `mobile-global-timeline` / `mobile-post-detail` data seam.

Per `docs/03-UX-Design.md` § Search UX (Premium) and `docs/02-Product.md` § Search (Premium, Month 1+), search is Premium-gated: Free users see an upsell, Premium users get ranked post + username results (20/page, "Lihat lebih banyak" pagination), an empty state, and a rate-limit modal.

## What Changes

- **A new `Cari` screen reachable from the Home brand app bar.** A Material search icon is added to the Home-section `CenterAlignedTopAppBar` (the brand-logo app bar, Home-section only — mirroring how the composer FAB is Home-only). Tapping it pushes a new parameterless `SearchRoute` onto the **root** back stack (overlaying the section `NavigationBar`, mirroring `PostDetailRoute` / `PostCreationRoute`). `docs/03-UX-Design.md:240` frames search as "a search bar at the top of the Timeline"; the icon-into-pushed-screen idiom is this app's established pattern for a focused full-screen surface.
- **`SearchScreen`** — an M3 search input (back affordance + text field + clear) at the top, and a result list filling the remaining space. The screen is navigation-free (hoisted `onBack` + `onOpenPost`); it renders under `NearYouTheme` with the `mobile-design-system` substrate (single shell-owned Scaffold contract notwithstanding, this is a pushed full-screen route that owns its own minimal top bar, like `PostDetailScreen`).
- **The full state contract the shipped endpoint enforces**, each mapped to exactly one sealed `SearchOutcome` keyed on HTTP status (no generic "load failed" fallthrough): `200` → results (with `next_offset` load-more); `403 premium_required` → a **Free-tier upsell panel** (the reactive Premium gate); `429 rate_limited` → the `docs/03:245` modal "Kamu sudah mencapai batas pencarian. Reset dalam X menit." with a live countdown from `Retry-After`; `503 search_disabled` → a kill-switch state; `400` → a retryable error (shouldn't occur given the client guard, but mapped, never a crash); terminal `401` → `SessionExpired` delegated to the shipped `Auth` plugin (same as the timelines); `5xx`/IO → `NetworkError`.
- **Client-side query discipline**: trim + require `2..100` Unicode code points before issuing a request (matches the backend guard, avoids a guaranteed-`400` round trip); the query fires on a **500 ms** debounce after typing pauses AND on the keyboard submit action (`docs/03:242`). Below the threshold the screen shows a directive **Idle** prompt.
- **Pagination via "Lihat lebih banyak"** (`docs/03:243`) — a load-more button consuming the retained `next_offset`, appending the next page to the results; `next_offset == null` is terminal and hides the button. (NOT infinite scroll.)
- **A search-specific result card** rendering `authorDisplayName` + `@authorUsername` + `content` + the `created_at` date treatment. The shipped search wire carries **no** city, distance, or like/reply engagement state, so this is a lighter card than the feed `PostCard`. PII discipline: the `author_id` UUID and the `rank` score are never rendered; nothing is logged (`HttpClientFactory` stays `LogLevel.HEADERS`).
- **Result tap → `onOpenPost` pushes `PostDetailRoute`** (wired at the `appEntryProvider` call site, not inside `SearchScreen`). Because the search wire lacks `cityName`/`distanceM`/`likedByViewer`/`replyCount`, the pushed route uses documented defaults (`cityName = ""`, `distanceM = null`, `likedByViewer = false`, `replyCount = 0`) with `postId`/`content`/`createdAtIso`/`authorUsername`/`authorDisplayName` from the hit — an explicit, spec'd v1 limitation (no per-viewer like-status or by-id post endpoint exists; the detail screen's `/likes/count` + `/replies` sub-resource fetches are authoritative for counts).

Out of scope (explicit non-goals, each tracked): **username autocomplete/typeahead** (`docs/03:241` — needs a NEW backend autocomplete endpoint; none shipped); **proactive "upsell on tap before typing"** (`docs/03:240` — needs client-held `subscription_status`; the reactive-on-`403` gate is the v1 surface); **routing the upsell CTA to a real paywall** (frame 17 Paywall is Phase 4 / DESIGN-status billing — the v1 panel is informational); **any backend change**; **any change to the `premium-search` query, gate, or limits** (consumed as-is).

## Capabilities

### New Capabilities

- `mobile-search`: the mobile search surface — `SearchRoute` (parameterless serializable NavKey, root-stack push), `SearchScreen` (M3 search input + result list, navigation-free), `SearchApiClient` (`GET /api/v1/search` with `q`/`offset`, shipped snake_case wire), `SearchRepository` behind a `SearchFlow` seam with a sealed `SearchOutcome` (status-keyed), the pure Compose-free `SearchUiState` projection (Idle / Loading / Results / EmptyResults / Error / PremiumGate / RateLimited / Disabled / SessionExpired), the client-side `2..100` query guard + 500 ms debounce, the "Lihat lebih banyak" load-more, the search-result card, Koin wiring, the new Bahasa strings, the test suite, and the explicit deferral requirements.

### Modified Capabilities

- `mobile-home-tab-host`: **MODIFIED** the "Bottom navigation is a top-level section shell" requirement so the Home-section `CenterAlignedTopAppBar` gains a search **action icon** (Home-section only); **ADDED** a separate "The tab host hoists onOpenSearch …" requirement for the `onOpenSearch` hoist wired at the `appEntryProvider` call site to `backStack.add(SearchRoute)` (the same call-site mechanism as `onOpenComposer`/`onOpenPost`). The existing `onOpenPost` hoist requirement is left **unchanged** — the search entry point is added as a new requirement rather than renaming the shared one, so it neither breaks header-matched spec-sync at archive nor collides with the concurrent feed-tab changes that also touch that requirement (#246).

## Impact

- **Code** (`:mobile:app` + `:shared:resources` only): new `screens/search/SearchScreen.kt`, `screens/search/SearchResultCard.kt`; new data seam `data/search/SearchApiClient.kt` + `SearchRepository.kt` + `SearchFlow.kt` (+ `SearchOutcome`); new `ui/search/SearchUiState.kt` (pure projection) + the client-side query guard helper; `screens/routing/NavKeys.kt` (`SearchRoute` + polymorphic registration); `screens/routing/AppEntryProvider.kt` + `screens/shell/AppShellScreen.kt` + `screens/home/HomeScreen.kt` (search-icon + `onOpenSearch` hoist/forward/wiring); `di/MobileModule.kt` (`single<SearchFlow>`); `:shared:resources` strings (search hint, idle prompt, empty-results, premium-gate copy, rate-limit modal, disabled, "Lihat lebih banyak", content descriptions).
- **APIs**: none added or changed — consumes the shipped `GET /api/v1/search` exactly as spec'd in `premium-search`.
- **Dependencies**: none (no `libs.versions.toml` touch).
- **Specs**: 1 ADDED capability (`mobile-search`); `mobile-home-tab-host` gets 1 MODIFIED requirement (app-bar search icon) + 1 ADDED requirement (`onOpenSearch` hoist).
- **Tests**: Robolectric `SearchScreenTest` (each UiState + input + load-more + result-tap, via `FakeSearchFlow`, Release-excluded); commonTest `SearchUiStateTest` (pure projection) + query-guard test + `SearchRoute` serialized round-trip; MockEngine `SearchApiClient`/`SearchRepository` tests (path + `q`/`offset` params, shipped snake_case parse, camelCase negative-guard, `next_offset` parse, `Retry-After` parse on 429, status→outcome); a home-tab-host search-icon + `onOpenSearch` wiring scenario.
- **Risk**: low — UI + state-holder work behind a shipped, fully-spec'd endpoint; the only novel seam (status→`SearchOutcome` plus the upsell/rate-limit/kill-switch states) is isolated and commonTest-covered. The documented PostDetailRoute default-fields limitation is the one behavioral compromise, spec'd explicitly.
