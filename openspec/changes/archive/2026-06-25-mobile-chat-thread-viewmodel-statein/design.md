## Context

`docs/11-Engineering-Standards.md` §2.2 mandates each screen-level ViewModel "**Expose ONE `StateFlow<XxxUiState>` via `stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), initial)`**, collect with `collectAsStateWithLifecycle()`". `mobile-feed-viewmodels-statein` (audit 05-#6, PR #409) aligned the four feed/list VMs; `mobile-chat-settings-viewmodels-statein` (#410, PR #413) aligned the two same-shape forks (`ConversationListViewModel`, `BlockedUsersViewModel`). `ChatThreadViewModel` carries the **identical** fork but was named in neither list (follow-up #414): it exposes raw `historyOutcome` + `isInitialLoad` + `rows` `StateFlow`s and runs the pure projection `chatThreadUiState(historyOutcome, isInitialLoad, rows)` **in the composable** via `remember(historyOutcome, isInitialLoad, rows) { … }`. This change is that follow-up — the same mechanical pass, mirroring the shipped 05-#6 / #410 shape and the `mobile-chat` `ConversationListViewModel` requirement/scenario template.

`ChatThreadViewModel` differs from the #410 VMs in one structural way: its projection takes **three** inputs, not two. `_rows` is the realtime-merged list (the pure `mergeChatMessages` + `chatMessageRows` over REST history + optimistic sends + realtime inbound, id-deduped and ordered by `(createdAt, id)`); `_historyOutcome` is the raw REST history outcome; `initialLoad` is the first-resync flag. The merged `rows` carries no behavior of its own that the fold changes — it is already a hot `MutableStateFlow` recomputed by the VM's `recompute()`; the fold simply moves the *projection* of `(outcome, initialLoad, rows) → ChatThreadUiState` out of the composable and into the VM via `combine(...).stateIn(...)`.

## Goals / Non-Goals

**Goals:**
- `ChatThreadViewModel` exposes exactly one content `uiState: StateFlow<ChatThreadUiState>` via `stateIn(WhileSubscribed(5_000))`, delegating to the existing 3-arg pure projection unchanged.
- `ChatThreadScreen` collects that single `uiState` for rendering (no in-composable `chatThreadUiState(…)` projection).
- Make the convention uniform across the app, closing the third fork #414 tracks.

**Non-Goals:**
- No observable behavior change: identical content states + transitions, identical realtime-merge behavior, identical PII discipline, identical config-change survival.
- No change to the pure projection function (`ChatThreadUiState.kt` — the 3-arg `chatThreadUiState` signature is reused verbatim), the data seams (`historyOutcome` / `rows`), the merge functions, the wire/DTOs, or DI wiring.
- **Not** folding the orthogonal send/report signals into the content `uiState`: the send-bar sub-state (`sendBarState(sendOutcome, sendInFlight)`, an independently-varying input-bar state like #410's `isRefreshing`), `sendOutcome` / `sendInFlight` (the first-send notification-prompt + input-clear `LaunchedEffect` keys), and the report one-shots (`reportTargetMessageId` / `reportMessage`, nullable-state one-shots per §2.2) stay their own flows. The send-bar's in-composable `remember(sendOutcome, sendInFlight) { sendBarState(…) }` is left as-is — it is not the `chatThreadUiState` content projection this finding targets.
- Not the app-wide `koinViewModel()` conversion (audit 05-#7, separate); not the `screens/` package restructure (D6).

## Decisions

**1. Add `uiState` via `combine(_historyOutcome, initialLoad, _rows).stateIn(WhileSubscribed(5_000), Loading)`, reusing the pure projection.** The 3-input combine maps to the existing `chatThreadUiState(outcome, isInitialLoad, rows)` verbatim — the function is reused, not reimplemented (mirrors 05-#6 / #410). `WhileSubscribed(5_000)` and the `collectAsStateWithLifecycle()` collection are mandated by docs/11 §2.2 (not a free choice). Initial value is `ChatThreadUiState.Loading` (the projection returns `Loading` for `isInitialLoad = true` / null outcome). `combine` with three flows is a standard `kotlinx.coroutines.flow.combine` overload — no custom plumbing.

**2. `isInitialLoad` becomes private (`_isInitialLoad`→`initialLoad`); `historyOutcome` + `rows` stay public.** The initial-load flag is fully subsumed by `uiState` (`Loading` ⟺ initial load), so its public accessor is removed. Once private, the `_`-prefixed backing-property name would orphan (ktlint `BackingPropertyNaming`: `_foo` requires a public `foo`); renaming to a plain private `initialLoad` is the fix used by the 05-#6 / #410 VMs. **Both** `historyOutcome` (`StateFlow<ChatThreadOutcome?>`) and `rows` (`StateFlow<List<ChatMessageRow>>`) are kept as the ViewModel's **raw-domain-state seams**: the white-box realtime/merge tests assert on them (`viewModel.rows.value` for the id-dedupe/redaction-in-place/optimistic-reconcile cases; `viewModel.historyOutcome.value` for the REST-only-degrade case). They are distinct domain types (not a `ChatThreadUiState`), so exposing exactly one `ChatThreadUiState` flow (`uiState`) still satisfies "expose ONE `StateFlow<XxxUiState>`".

**3. The independently-varying / one-shot signals stay separate flows.** Per docs/11 §2.2 ("data class when fields vary independently" + "one-shot events are nullable state fields"): the send-bar sub-state, `sendOutcome` / `sendInFlight`, and the report one-shots (`reportTargetMessageId` / `reportMessage`) are orthogonal to the mutually-exclusive message-list content state and remain their own flows. The screen keeps collecting them as before. The send-bar's in-composable `remember { sendBarState(…) }` projection is left untouched — it is an orthogonal input-bar signal, not the content projection the finding targets (the same posture #410 took with `isRefreshing` / `unblockError` / `unblocking`).

**4. `ChatThreadScreen` drops all three subsumed collects.** Unlike `BlockedUsersScreen` (which kept collecting the raw `outcome` for a terminal-401 navigation side-effect), `ChatThreadScreen` reads `rows` / `historyOutcome` / `isInitialLoad` ONLY to compute the in-composable `chatThreadUiState(…)` projection (the session-redirect for `ChatThreadOutcome.SessionExpired` is purely *rendered* as `ChatThreadUiState.SessionRedirect`, with no `onTokenInvalid` callback). So all three collects are removed and replaced by the single `val uiState by viewModel.uiState.collectAsStateWithLifecycle()`. The send/report collects and the `MessageList(uiState.rows, …)` render (which reads the rows off the `Content` state, not the raw `rows` flow) are unaffected.

**5. Test pattern for `WhileSubscribed`.** A `stateIn(WhileSubscribed(5_000))` flow only runs its upstream while collected, so the new VM unit tests start a `backgroundScope.launch { viewModel.uiState.collect {} }` collector (within the suite's existing `runTest` + `UnconfinedTestDispatcher(testScheduler)` Main) before asserting `uiState.value` — the `WhileSubscribed`-activation pattern shipped in `GlobalTimelineViewModelTest` / `ConversationListViewModelTest`, adapted to this suite's `runTest` harness (`backgroundScope` is auto-cancelled at test end, so the realtime re-subscribe loop is torn down cleanly). The config-change scenario is proxied by a second fresh collector observing the retained state on the same VM instance. **No existing `isInitialLoad` read needs migrating** — the VM's `isInitialLoad` is read only by `ChatThreadScreen.kt:140`, which this change removes (the new tests are pure additions for the spec deltas).

## Risks / Trade-offs

- **[Behavior-preserving retrofit of a live, realtime screen]** → Behavior is preserved; the gate (`:mobile:app:testDevDebugUnitTest` + `…testDevReleaseUnitTest`) plus the full existing `ChatThreadViewModelTest` realtime/merge suite (id-dedupe, redaction-in-place, optimistic reconcile, resubscribe-resync, REST-only degrade — all reading the retained `rows` / `historyOutcome` seams) and the Robolectric `ChatThreadScreenTest` (same rendered states) are the safety net. The pure-projection unit tests (`ChatThreadUiStateTest`) are untouched (function reused).
- **[3-input `combine` recomputes the projection on every realtime row change]** → Intended and cheap: `chatThreadUiState` is a pure `when` over the outcome that wraps the already-merged `rows` list (no copy of the list, just a `Content(rows)` wrapper); it ran on every recomposition before (keyed on the same three inputs via `remember`), so moving it to `combine` is equal-or-fewer evaluations, and `stateIn` de-dups equal emissions.
- **[`historyOutcome` + `rows` staying public could read as "multiple state flows"]** → Documented here + in the spec delta as the raw-domain-state seams (distinct types `StateFlow<ChatThreadOutcome?>` / `StateFlow<List<ChatMessageRow>>`, distinct purpose: the white-box merge/realtime test seams the spec's merge requirement pins); there is exactly one `ChatThreadUiState` flow.
- **[K/N compile — VM is commonMain]** → Covered by `:mobile:app:iosSimulatorArm64Test` (the commonTest VM tests run on Native; the existing `ChatThreadReportFlowIosTest` exercises the chat iOS path). Any pre-existing `*FlowIosTest` DI-drift failures (#348) are unrelated — iOS is never CI-gated and this change touches no DI.

## Migration Plan

Pure refactor, no runtime/data migration. Introduce `uiState`, rename the initial-load flag private, leave `historyOutcome` + `rows` + the send/report flows; switch the screen to collect `uiState` (drop the three subsumed collects + the in-composable projection); add the single-`uiState` + config-change scenarios to `ChatThreadViewModelTest`. Rollback = revert the PR (no schema/wire/state-persistence surface).

## Open Questions

None. The shape (`uiState` via 3-input `stateIn`, `isInitialLoad` private, `historyOutcome` + `rows` retained as the raw-state seams, send/report signals separate, the send-bar projection left untouched) is settled against docs/11 §2.2 + the shipped 05-#6 / #410 precedent.
