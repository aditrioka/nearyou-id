## Why

The mobile app can sign in, browse all three feeds, create a post, open a post detail, and like/reply — but **there is no way to message anyone**. 1:1 chat is the second half of the social loop and an explicit milestone in the demo flow (`openspec/project.md` § Mobile-First to Full-Demo Priority → "*1:1 chat*"). It is live-menu pick **#3** ("the messaging half of the demo").

The backend chat data plane is **fully shipped and stable** (V15 migration; capabilities `chat-conversations`, `chat-realtime-broadcast`, `auth-realtime`): create-or-return a conversation, list conversations, list/send messages (with bidirectional block enforcement, shadow-ban invisible-actor semantics, redaction, the 2000-char guard, notification emit, and a post-commit Supabase Realtime Broadcast publish), plus the `GET /api/v1/realtime/token` HS256 companion-token endpoint. **No backend is missing** — chat is purely a mobile-client gap. This change ships the consumer: two screens (conversation list + thread), the send path, and a **live realtime subscribe** so two devices see messages appear without a manual refresh (the compelling chat demo).

## What Changes

- **NEW: `ConversationListScreen`** (mockup Frame 2 "*Pesan — daftar percakapan*") — calls `GET /api/v1/conversations` (cursor-paginated, ordered `last_message_at DESC NULLS LAST, created_at DESC`). Each row renders the OTHER participant's display identity (`username`/`displayName`, `isPremium` badge) + the relative `last_message_at`, with the `'Akun Dihapus'` / `'akun_dihapus'` placeholder the backend already `COALESCE`s for a shadow-banned/deleted partner. Loading / empty / error states per the `mobile-design-system` canonical list-loading contract; pull-to-refresh.
- **NEW: `ChatThreadScreen`** (mockup Frame 5 "*Ruang chat 1:1*") — calls `GET /api/v1/chat/{conversation_id}/messages` (cursor pagination, 50/page, `created_at DESC, id DESC`; load-older on scroll-up). Renders own-vs-other message alignment; a **redacted** message (`content: null`, `redacted_at` set — `redaction_reason` is never on the wire) renders a neutral "*pesan dihapus*" placeholder. Shadow-ban filtering stays server-authoritative (the client carries no viewer-ban signal — it is invisible to the banned user); any own-message echo that arrives via realtime is reconciled by the id-keyed dedupe, not a client ban-gate (design D6).
- **NEW: send path** — `POST /api/v1/chat/{conversation_id}/messages { content }` with a client-side 1–2000-char guard and empty/whitespace rejection; optimistic append reconciled by message `id`. A `403 { "error": "Tidak dapat mengirim pesan ke user ini" }` (block in either direction) renders as a user-facing send-blocked state, not a crash. `embedded_*` fields are NOT sent (deferred to `chat-embedded-posts`).
- **NEW: create-or-return** — `POST /api/v1/conversations { recipient_user_id }` (201 new / 200 existing / 403 block / 400 self / 404 unknown) opens or resumes a thread with a given user, returning the `conversation_id` the thread screen needs.
- **NEW: Supabase Realtime live-append** — subscribe to channel `realtime:conversation:<lowercase-uuid>` authenticated with an HS256 token from `GET /api/v1/realtime/token` (TTL 1h, refreshed on expiry). Incoming broadcast payloads (the 9-key snake_case schema owned by `chat-realtime-broadcast`, `redaction_reason` absent, `content: null` when redacted) are appended to the thread, **deduplicated by message `id`** against REST-loaded + optimistic messages. REST resync on (re)subscribe / reconnect recovers any broadcast missed during a disconnect (the backend has no outbox by design). The subscription is torn down on leaving the thread.
- **NEW: subscribe-side realtime seam** — a vendor-SDK-free `ChatRealtimeSubscriber` interface in `:core:domain` and its supabase-kt implementation in a new KMP-targeted `:infra:supabase-realtime` module (the vendor SDK import stays inside `:infra:*` per the critical invariant). First realtime *consumer* on mobile — registered as a new Pattern-Registry entry.
- **NEW: first-send notification-permission prompt** — the platform notification-permission rationale (`docs/03-UX-Design.md` § Notification Permission) is shown the first time a user sends a message, so chat replies can later surface as push. Independent of FCM token registration (that cross-cutting wiring stays pending).
- **NEW: navigation + entry point** — `ConversationListRoute` (parameterless) + `ChatThreadRoute(conversationId, partnerUsername, partnerDisplayName)` as `@Serializable` root-stack `NavKey`s (mirroring `PostDetailRoute`). A "Pesan" icon action on the Home brand app bar opens `ConversationListRoute` — this **MODIFIES `mobile-home-tab-host`** (the app-bar action set).
- **NEW: Bahasa Indonesia strings** in `:shared:resources` for all chat copy (conversation list, thread, send, redacted/blocked states, permission rationale).
- **NEW: supabase-kt Realtime library pin** in `gradle/libs.versions.toml` (the only substrate addition; Ktor 3.x prerequisite is already satisfied — the repo is on Ktor 3.4.3).
- **NO Flyway migration, NO backend business-logic change** — the chat REST + realtime publish side is shipped; this is a mobile consumer plus one shared domain interface + one infra module.

## Impact

- **Code**: `:mobile:app` commonMain (two screens + two routes + two ViewModels + two UiState projections + three API clients + two repositories/flows + outcomes + the `ChatRealtimeSubscriber` consumption + the notification-permission prompt + Koin wiring); `:core:domain` (the `ChatRealtimeSubscriber` interface + `ChatMessageInbound` model, vendor-SDK-free); a NEW `:infra:supabase-realtime` KMP module (Android + iOS) holding the supabase-kt implementation; `:shared:resources` strings; `gradle/libs.versions.toml` (+ `settings.gradle.kts` + `dev/module-descriptions.txt` + `sync-readme.sh --write` for the new module).
- **APIs consumed** (all shipped): `GET /api/v1/conversations`, `POST /api/v1/conversations`, `GET /api/v1/chat/{id}/messages`, `POST /api/v1/chat/{id}/messages`, `GET /api/v1/realtime/token`; Supabase Realtime channel `realtime:conversation:<uuid>`. Mobile DTOs mirror the SHIPPED wire field-for-field (verified in design § Reconciliation), NOT the spec JSON examples where they differ.
- **Dependencies**: adds the supabase-kt Realtime module to `gradle/libs.versions.toml` (KMP; requires Ktor 3.x — satisfied at 3.4.3; okhttp/darwin engines support WebSockets). A Phase-1 pre-implementation version re-check pins the exact current stable build.
- **Security surface**: the HS256 realtime token is fetched per-subscription and never persisted to disk; the Supabase publishable/anon key + project URL are non-secret client config (matches the existing slot-names-in-source posture) but flow through the env/flavor config, not hard-coded literals; the vendor Supabase SDK import is fenced to `:infra:supabase-realtime` (invariant #16); redaction is honored at render on the client (`content: null` → placeholder); shadow-ban filtering is server-authoritative (the client does not gate on ban state, which is invisible to the banned user); no message content or tokens are logged.
- **Out of scope (each tracked as a `follow-up` issue)**: the embedded-post context card (`chat-embedded-posts`); post-edit-history navigation from an embed (blocked on `post-edit-history`); the profile-screen "Kirim pesan" entry-point wiring (behind PR #245 merge); the per-conversation unread badge / `last_read_at` write (the shipped `GET /api/v1/conversations` contract does not expose an unread count — see design); FCM token registration + push delivery of chat notifications (cross-cutting wiring); the post-swap Ktor-WebSocket realtime transport (Month 15+).
