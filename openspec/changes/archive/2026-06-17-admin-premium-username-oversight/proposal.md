## Why

The premium username customization backend shipped (`premium-username-customization`, [#301](https://github.com/aditrioka/nearyou-id/pull/301), 2026-06-14): it inserts a standing `moderation_queue` row (`trigger = 'username_flagged'`) whenever a candidate handle hits the profanity / UU-ITE pipeline, and holds every relinquished handle in `username_history` for 30 days (anti-impersonation). But there is **no admin surface** to triage those flags, **no way for the operator to override a false-positive flag** (e.g. a legitimate Indonesian word that matches the UU-ITE list in an unrelated sense — `docs/06` § Premium Username Customization Moderation), and no way to force-release a held handle for an impersonation complaint. `docs/05` § Premium Customization Endpoint and the shipped `premium-username-customization` spec both explicitly deferred "the admin username-change oversight (`username_history` viewer, borderline-candidate override, manual handle release)" to a separate follow-on — this change is that follow-on, delivered **end-to-end**: the admin's "accept" actually lets the approved candidate through on re-submit (`docs/07`: "override — candidate passes on re-submit").

## What Changes

- New **`GET /admin/username-oversight`** admin page (admin mockup frame 22), inside the existing `authenticate(ADMIN_AUTH_NAME)` block, with three sections:
  - **Flagged-candidate queue** — `moderation_queue` rows with `trigger = 'username_flagged'` and `status = 'pending'`, newest-first; each row shows the flagged **candidate** (now persisted in `moderation_queue.notes`, see below) and deep-links the user to `/admin/users?q=<user>`.
  - **Read-only `username_history` viewer** — search by old/new handle, keyset-paginated; strictly read-only (no direct username editing).
  - **30-day-hold list** — `username_history` rows still under hold (`released_at > NOW()`), each with a "Release now" control.
- New **`POST /admin/username-oversight/flags/{queue_id}/resolve`** — `resolution ∈ {accept_flagged_username, reject_flagged_username}`. **Accept** resolves the queue row AND inserts a **per-candidate approval** into the new `username_flag_overrides` table (the override that gives the user a one-shot pass for that exact handle). **Reject** resolves the queue row (confirms the block, no approval). One `username_flag_resolved` audit row; rate-limited **10/hour per admin**; conditional on `status = 'pending'` (idempotent).
- New **`POST /admin/username-oversight/holds/{history_id}/release`** — force-releases a held handle (`username_history.released_at = NOW()`); one `username_hold_released` audit row; idempotent; rate-limited **5/hour per admin**.
- **NEW Flyway migration `V23__username_flag_overrides.sql`** — `username_flag_overrides (id, user_id → users ON DELETE CASCADE, candidate, approved_by → admin_users ON DELETE SET NULL, approved_at, consumed_at, UNIQUE(user_id, candidate))`. The one-shot per-candidate approval store, keyed by the **normalized (lowercased) candidate** so an override is scoped to exactly the handle the admin approved — never a blanket per-user moderation bypass.
- **MODIFIES the live `PATCH /api/v1/user/username` moderation gate** (`premium-username-customization`):
  - The `username_flagged` insert now **persists the candidate** in `moderation_queue.notes` and switches from `ON CONFLICT DO NOTHING` to `ON CONFLICT … DO UPDATE` that **re-opens** the standing row (`status → 'pending'`, `resolution`/`resolved_by`/`resolved_at → NULL`, `notes`/`created_at` refreshed) — so the latest flagged candidate is always visible and actionable, and a resolved flag does not silently swallow a new attempt.
  - Before rejecting on a moderation hit, the gate **consults `username_flag_overrides`** for a non-consumed `(user_id, candidate)` approval; on a match it **SKIPS the moderation rejection** (pre-approved) and **consumes** the override (`consumed_at = NOW()`) within the successful-change transaction. All OTHER gates (reserved, release-hold, uniqueness, 30-day cooldown, charset) still apply.
- All state-changing routes are **CSRF-validated then write-role-gated** (CSRF first), **atomic**, and **idempotent**.
- This capability **owns the `accept_flagged_username` / `reject_flagged_username` resolution values** that `admin-report-queue`'s moderation-queue endpoint rejects as out-of-scope.

## Capabilities

### New Capabilities

- `admin-premium-username-oversight`: the admin Premium Username Change Oversight surface — flagged-candidate triage (accept → write a per-candidate override; reject → confirm the block), a read-only `username_history` viewer, and 30-day-hold manual release; introduces the `username_flag_overrides` table (V23); every write CSRF- + write-role-gated, per-admin rate-limited via the audit-log-COUNT pattern, and immutably audit-logged.

### Modified Capabilities

- `premium-username-customization`: the live `PATCH /api/v1/user/username` moderation gate now (a) persists the flagged candidate and re-opens the standing `username_flagged` row on each flagged attempt, and (b) honors a non-consumed admin `username_flag_overrides` approval by skipping the moderation rejection for that exact candidate and consuming it (conditional, rows-affected-gated, inside the `FOR UPDATE` change transaction) on a successful change. No new endpoint; the capability stays backend-only (two endpoints). Its `Backend-only scope (…admin oversight…deferred)` requirement is **RENAMED + MODIFIED** to retire the now-fulfilled admin-oversight/override deferral (the mobile-UI + anomaly-score deferrals are retained), so the archived canonical spec is not self-contradicting.

## Impact

- **Migration:** new `V23__username_flag_overrides.sql` (one table; FKs to `users` + `admin_users`). **Operational grant:** add `username_flag_overrides` to the `admin_app` per-table grants in `dev/scripts/provision-admin-app-staging.sh` (SELECT/INSERT/UPDATE — admin writes approvals; the main API role consumes them). Out-of-band like every other `admin_app` grant (`docs/07` § Data Access Pattern).
- **Code:** new `:backend:ktor` admin package `id.nearyou.app.admin.usernameoversight` (route + service + repository, Routes → Service → Repository); a new Pebble template + nav entry; reuse of `AdminRoleGate.requireWriteRole`, the CSRF gate, the `admin_actions_log` writer, and the per-admin audit-log-COUNT rate-limit pattern. **Modified:** the premium-username change service (`id.nearyou.app.user.UsernameChangeService`) moderation gate (consult + conditional-consume the override) + the `:data` `ModerationQueueRepository.upsertUsernameFlaggedRow` signature (gains the candidate arg + switches `ON CONFLICT DO NOTHING` → `DO UPDATE`).
- **New `admin_actions_log.action_type` values:** `username_flag_resolved`, `username_hold_released` (the column is unconstrained `VARCHAR(64)`; no CHECK/migration needed; `admin_actions_type_idx` backs the rate-limit COUNT).
- **Docs:** visual target = admin mockup frame 22 (`GET /admin/username-oversight`); spec source = `docs/07-Operations.md` § Premium Username Change Oversight + `docs/06` § Premium Username Customization Moderation + `docs/08` Phase 3.5 #24.
- **No mobile / public-API surface change** (the PATCH path’s contract is unchanged for callers — a previously-flagged candidate may now succeed if pre-approved). **No dependency changes** (does not touch `gradle/libs.versions.toml`).
