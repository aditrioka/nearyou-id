## Context

The referral funnel ships in three already-merged pieces: `referral-ticket-creation` (signup inserts a `pending_activity` ticket), `referral-grant-worker` (the daily `/internal/referral-activity-check` evaluates the activity gate and, on pass, dispatches a 1-week promotional Premium grant via the RevenueCat v1 API and records a `granted_entitlements` ledger row), and `subscription-billing-webhook` (the RevenueCat webhook handler, `SubscriptionService`, which on the `GRANT` echo records a `subscription_events(source='referral')` row **and activates `users.subscription_status`**). The mobile invite flow (#426) is in flight.

The gap: when the automated activity gate **false-negatives** a legitimate referral, there is no operator remedy. [Open Decision #15](../../../docs/08-Roadmap-Risk.md) resolves it as "include a **minimal path** in Phase 3.5 — critical for user trust." The admin board froze the surface visually as **frame 19** (`GET/POST /admin/referral-grants`, "*jalur perbaikan untuk tiket support, bukan aksi sistem*").

Key shipped facts this design builds on (verified against the tree):
- `ReferralEntitlementGranter` (`:infra:revenuecat-api`) is **referral-agnostic** — `GrantRequest(appUserId, entitlementId, endTimeMs, dedupKey)` carries no ticket. It is the reusable RC v1 promotional-grant port; `NoOpReferralEntitlementGranter` is the fail-soft binding when no secret key is configured. Stacking math is the caller's: `endTimeMs = GREATEST(current_entitlement_end, NOW()) + 7d`.
- `SubscriptionService` GRANT echo: `"GRANT" -> … source = SOURCE_REFERRAL ("referral")`, idempotent via `subscription_events.revenuecat_event_id` UNIQUE (`insertEventIfNew … ON CONFLICT (revenuecat_event_id) DO NOTHING`), and it owns `users.subscription_status`. A promotional grant dispatched through the v1 API **does** fire this echo (the worker relies on exactly this).
- `subscription_events` (V21) reserves `source IN ('paid','referral','manual_admin')` + `event_type IN (…, 'grant', …)` — `'manual_admin'` is reserved **but unused**, "until the [manual-admin grant] system change."
- `granted_entitlements` (V32) is **not** a viable target: no `source` column; `grant_role` CHECK is `IN ('invitee','inviter')`; `referral_ticket_id NOT NULL`; `UNIQUE(referral_ticket_id, user_id)` + inviter-once partial index. A ticket-less support grant cannot be expressed here, and writing it would pollute the lifetime-cap accounting.
- Established admin patterns to clone: the **read-only-viewer** (`SubscriptionGraceRepository` / `AdminPrivacyFlipsRepository`: keyset pagination + lenient parameterized filters + HTML-escaped HTMX render + plain-`GET` fallback) and the **audit-ledger rate-limiter** (`GraceExpediteActionRateLimiter`, `DeletionQueueExpediteRateLimiter`, `RejectedIdentifierClearRateLimiter` — a distinct per-admin-per-hour cap sourced from `admin_actions_log` COUNT, separate from the 20/hr destructive budget).

## Goals / Non-Goals

**Goals:**
- A CSRF- + `owner/admin`-gated `/admin/referral-grants` surface: lookup a user, see premium/subscription + referral context, issue a manual 1-week promotional Premium grant, and read past manual grants.
- Reuse the shipped RC port + the existing webhook echo + the established admin patterns — **no migration**, no new vendor surface.
- One immutable, attributable `admin_actions_log` record per grant; a distinct restorative rate-limit; required support-ticket reason.
- Preserve every admin invariant: CSRF, role gate, audit immutability (enforced by the out-of-Flyway `admin_app` role grant per V16), no vendor SDK leak, Pebble+HTMX+escape+plain-GET fallback. (The "admin-FK `ON DELETE SET NULL`" invariant is n/a — this change adds **no** operational table; the only admin FK touched is `admin_actions_log.admin_id`, which is intentionally restrictive, not SET-NULL, so the audit log blocks admin hard-delete.)

**Non-Goals:**
- Writing `granted_entitlements` (deliberately excluded — keeps the inviter 5-referral lifetime track + single lifetime inviter reward untouched; this is "not a referral-system action").
- Revoking / shortening a grant, or any bulk grant. One user, one 7-day grant per action.
- Changing the `subscription_status` ownership model (the webhook echo stays the sole writer).
- The mobile/user-facing side of referral (the invite flow is #426).

## Decisions

### D1 — Ledger target: NOT `granted_entitlements`; reconcile docs/07
The grant is recorded in `admin_actions_log` (authoritative, see D3) and — when RC is configured — in `subscription_events` via the existing webhook echo. It is **never** written to `granted_entitlements`. docs/07 § Referral Manual Grant Path ("writes `granted_entitlements` with `source='manual_admin'` + `grant_role='manual_admin'`") is **stale** against the shipped V32 schema and is reconciled via a `follow-up` issue. *Alternative considered:* extend `granted_entitlements` with a nullable `referral_ticket_id` + a `'manual_admin'` `grant_role` (a V36 migration). Rejected — it overloads the referral-funnel cap ledger with a non-referral action, mutates a shipped UNIQUE's semantics (nullable ticket), and adds a migration with no benefit over `subscription_events` + `admin_actions_log`.

### D2 — RC dispatch reuses `ReferralEntitlementGranter`; 7-day stacking
The grant dispatches through the existing `ReferralEntitlementGranter.grant(GrantRequest(...))` port. `appUserId` = the user UUID string (the worker dispatches `recipientId.toString()`); `entitlementId` = the `premium` entitlement id (the worker uses a hardcoded `const ENTITLEMENT_ID = "premium"`, not a config object — reuse the same constant/source); `endTimeMs = GREATEST(current_entitlement_end, NOW()) + 7d` (extend-if-active / fresh-if-free, identical to the worker; the `GREATEST` floor means an already-expired entitlement grants fresh, not stacked onto a stale end); `dedupKey` = a synthetic manual sentinel (`manual_admin:<random UUID>` — the audit row does not exist yet at dispatch time, so it cannot carry the row id; the key is persisted in the audit row's `after_state.dedup_key` instead, keeping the dispatch correlatable), our-side idempotency only. A **soft-deleted target is rejected pre-dispatch** (nothing dispatched, nothing written; the lookup panel renders the grant form disabled) — a promotional grant to a tombstoned account is a support-desk mistake, not a remedy. `:backend:ktor` imports only the port interface (no RC/HTTP symbol — `VendorSdkLeakageScan`). Fail-soft: `isConfigured()==false` ⇒ `GrantResult.NotConfigured`, the audit row is still written, and the action reports "recorded, dispatch skipped (RC unconfigured)". *Alternative considered:* a new general-purpose `PromotionalGranter` port. Rejected — `GrantRequest` is already referral-agnostic; a rename/duplication earns nothing.

### D3 — Attribution + activation: mirror the worker (audit-log authoritative; echo owns `subscription_events` + `subscription_status`)  ⟵ **the one scope decision**
**Primary:** the admin path writes exactly one immutable `admin_actions_log` row (`action_type = 'referral_manual_grant'`, `target_type='user'`, `target_id=<user>`, `reason=<ticket ref>`, before/after subscription snapshot) — this is the authoritative "a human granted this" record — and dispatches the RC promotional grant. Premium **activation** and the `subscription_events` row remain owned by the existing GRANT webhook echo (`source='referral'`, idempotent on `revenuecat_event_id`). The admin path does **not** write `users.subscription_status` or `subscription_events` directly. This preserves the shipped invariant ("`users.subscription_status` is owned by the `subscription-billing-webhook` GRANT echo, never written by the worker") and keeps **exactly one** `subscription_events` row per grant — no double-count.

*Why not write `subscription_events(source='manual_admin')` directly (the docs/07 + V21-reserved-vocab intent)?* Because the RC promotional grant **also** fires the GRANT echo, which inserts a `source='referral'` row keyed on `revenuecat_event_id`. A directly-written `manual_admin` row (which has no real `revenuecat_event_id`) would not collide with the echo's row ⇒ **two** `subscription_events` rows for one grant, one mis-counted. Suppressing/relabelling the echo would require matching the dispatched grant to the inbound webhook, but RevenueCat's promotional-grant webhook **does not echo our attribution** (no custom field, no `dedup_key`) — so any match is racy `(user_id, ~timestamp)` heuristics and a `subscription-billing-webhook` modification. For a "minimal path critical for user trust," the robust call is to keep attribution where it is reliable (the admin audit log) and leave `subscription_events.source = 'manual_admin'` reserved-but-unused (forward-compatible). **Consequence:** the operational-dashboard "subscription source breakdown" counts manual grants under `referral`, not a distinct `manual_admin` bucket — an acceptable loss for the minimal remedy; revisitable if a future RC capability lets the echo attribute reliably.

*Alternative (surfaced to the operator):* if the dashboard `manual_admin` distinction is required, adopt the direct-write variant — the admin path writes `subscription_events(source='manual_admin', event_type='grant')` + activates `users.subscription_status` in-transaction (annotated, docs-amended), and `subscription-billing-webhook` is **MODIFIED** to dedup/suppress its echo for manual grants via a short-lived coordination marker. This is the "complete" interpretation; it costs a modified capability + a verified-non-racy coordination mechanism (an apply-time dated RC-webhook-payload check gates the exact key). Recorded as an Open Question.

### D4 — Distinct restorative rate-limiter
A new `ReferralGrantActionRateLimiter` (admin/ratelimit), ~**10 grants/admin/hour**, sourced from `admin_actions_log` COUNT over the trailing hour for `action_type='referral_manual_grant'` (the audit-ledger-as-limiter pattern), on a counter **independent** of the 20/hr destructive budget and the other distinct restorative caps — granting Premium is restorative, not user-punitive. Mirrors `GraceExpediteActionRateLimiter` exactly, including its **soft-cap posture**: the count is read before the audit row is written and there is no `FOR UPDATE` row-lock, so the cap is a documented ±1 soft bound (two concurrent grants in the same instant could both pass), not an authorization boundary — sufficient given CSRF + role + required reason + the immutable trail. Over-cap (a pre-flight rejection) ⇒ no dispatch and no audit row, an `ExpediteOutcome.RateLimited`-style outcome surfaced in the HTMX response. Because the audit row is the counted unit, a `Failed`/`NotConfigured` dispatch (which still writes its row, D3) correctly counts against the cap.

### D5 — Read viewer over `admin_actions_log`
The "past manual grants" list is the Nth instance of the read-only-admin-viewer pattern, reading `admin_actions_log WHERE action_type = 'referral_manual_grant'` (JOIN `admin_users` for the acting-admin display name; JOIN `users` for the grantee handle, tolerating a soft-deleted/tombstoned target). Keyset-paginated newest-first over `(created_at, id)`; composable `q` (grantee username/UUID) + UTC-date filters; HTML-escaped HTMX render + plain-`GET` fallback; any authenticated admin role reads. Reading the audit log (not `subscription_events`) keeps the viewer aligned with D3's authoritative record.

### D6 — No migration
`admin_actions_log` takes a new `action_type` string value (`'referral_manual_grant'`) — no schema/CHECK change (the column is free-text per the shipped schema; confirm at apply there is no enumerated CHECK). `subscription_events`/`users` are untouched by the admin path. Zero Flyway version claimed ⇒ no parallel-session collision.

### D7 — Auth, CSRF, routing, templates
`role IN ('owner','admin')` for the write (read is any admin role); `X-CSRF-Token` mandatory on POST (mismatch ⇒ 403 + `admin_csrf_violation`); `hx-confirm` guard + required non-empty reason on the grant form. Routes mount in `AdminModule.kt`/`Application.kt`; a sidebar entry is added. Pebble templates + HTMX, HTML-escaped, with a plain-`GET` fallback, translated from admin board **frame 19** per docs/11 §3.6 (render + measurement annex at apply).

## Risks / Trade-offs

- **[Lost `manual_admin` dashboard attribution]** → D3 primary records manual grants as `source='referral'` in `subscription_events`; the distinct count lives only in `admin_actions_log`. Mitigation: the audit-log viewer (D5) + the dashboard can add an `admin_actions_log`-sourced "manual grants" widget later; the operator can choose the direct-write alternative now (Open Question).
- **[Activation depends on the webhook echo]** → in RC-configured envs Premium activates only when the GRANT webhook is delivered (async, normally seconds); in unconfigured envs (staging/dev) the grant is audit-only (no activation), consistent with the whole referral funnel's fail-soft posture. Mitigation: the success UI states "grant recorded; Premium activates on RevenueCat confirmation" and, when `isConfigured()==false`, "dispatch skipped — RevenueCat not configured."
- **[Double-grant within the hour]** → the synthetic `dedupKey` is our-side only and the RC v1 promotional endpoint has no dedup param, so two clicks could extend twice. Mitigation: `hx-confirm` + the 10/hr cap bound it; the stacking math means a duplicate only adds 7 days (recoverable), not a runaway.
- **[Privileged action abuse]** → a phished admin session could mass-grant Premium. Mitigation: CSRF, owner/admin gate, the 10/hr cap, the required ticket reason, and the immutable audit trail (same posture as every other admin write).
- **[`appUserId` mismatch]** → if the RC app-user id is not the user UUID, the grant lands on no subscriber. Mitigation: confirm the id convention against the worker's dispatch at apply (a tasks.md verification item).
- **[Dispatched-but-unrecorded window]** → the RC dispatch runs BEFORE the audit insert (the append-only `admin_actions_log` row must carry the dispatch outcome in `after_state`; `admin_app` has no `UPDATE` grant for a post-hoc stamp, and a two-row shape breaks the spec's one-immutable-row contract). If the audit insert fails AFTER a successful dispatch (DB blip, pool exhaustion), the grant is live-but-unrecorded and uncounted by the cap. Accepted for this 10/hr surface: the admin sees the error, and a retry writes its own row while stacking at most +7d (bounded, recoverable — same math as the double-grant risk above). A persist-first outbox was considered and rejected as over-scoped for the minimal remedy.

## Migration Plan

No DB migration. Deploy is a standard admin-surface addition: ship the routes/repository/templates/limiter behind the existing admin auth; the RC dispatch is fail-soft so an unconfigured staging deploy is safe. Rollback = revert the change (no schema to undo). Pre-archive smoke: a staging branch deploy + an admin-panel walk of `/admin/referral-grants` (lookup → grant → audit-row appears in the viewer; with RC unconfigured the dispatch-skipped path is exercised).
