## CRITICAL

## HIGH

### 1. moderation/Layer3DispatcherScope.kt:93 + post/CreatePostService.kt:140 + engagement/ReplyService.kt:201 — fire-and-forget Layer 3 dispatch is re-parented to the request Job; shutdown-drain is dead code in production
`dispatch(parentContext, block)` does `scope.launch(parentContext + Dispatchers.IO)`. The production call sites pass `coroutineContext` (the Ktor request context, which carries the **request's `Job`**). In `scope.launch(ctx)` the rightmost `Job` element wins as the new coroutine's parent, so each Layer 3 dispatch becomes a child of the **request coroutine**, NOT the scope's `SupervisorJob`. Consequences: (a) `Layer3DispatcherScope.shutdown(drainMillis)` counts + `cancelAndJoin`s `scope.coroutineContext[Job].children` — which is permanently empty, so the entire drain mechanism (the class's main reason to exist) is a no-op; at SIGTERM in-flight auto-hide writes are abandoned mid-transaction, not drained. (b) A client disconnect right after POST cancels the user's own post's Layer 3 dispatch (request-Job cancellation propagates to the child). (c) the `SupervisorJob` sibling-isolation is bypassed (parent is now the request Job). Every `Layer3DispatcherScopeTest` drain/shutdown case calls `dispatch(EmptyCoroutineContext)`, so the production reparenting path is untested. Softened by Layer 3's fail-open posture (a dropped dispatch ⇒ `NoAction`), so user impact is "post silently skips Layer 3", not data loss. Fix: strip the Job — `scope.launch(parentContext.minusKey(Job) + Dispatchers.IO)` — so OTel context still flows but the dispatch stays a child of the scope; add a drain test that passes a real parent Job. Confidence: high (coroutine Job-precedence is well-established; verified call sites + tests).

### 2. moderation/TextModerator.kt:48 + moderation/ModerationListLoader.kt:71-129 — synchronous Layer 1/2 moderation runs blocking Redis + Firebase Remote Config + Secret Manager I/O on the request dispatcher
`textModerator.moderate(content)` is non-suspending and is called directly on the request coroutine in `CreatePostService.create` (:81), `ReplyService` (:145), and `ChatService` (:238). On a Redis cache hit it does a blocking Lettuce `GET`; on a miss it does a **blocking Firebase Remote Config SDK round-trip** (`getServerTemplate()` network call) and potentially a **blocking GCP Secret Manager fetch**, then a blocking Redis `SET` — all on the Ktor/Netty call dispatcher. `RedisStringCache`'s own KDoc says callers "SHOULD wrap each call in `withContext(Dispatchers.IO)`"; `moderate()` wraps nothing. docs/11 §3.2: "never the Netty event loop". First-traffic-after-deploy (cold cache, 5-min TTL) is the worst case — every post/reply/chat write blocks on a cross-region Firebase call. (The 01-backend-core finding #2 notes the same call site from the JDBC angle; this entry is the moderation-internal root cause: the loader is non-suspending by design.) Fix: make `ModerationListLoader.load`/`loadThreshold` suspend and hop to the shared bounded IO dispatcher, or wrap the `moderate()` call at each service boundary in `withContext(dbDispatcher)`. Confidence: high.

## MEDIUM

### 3. moderation/Layer3ConfigLoader.kt:64-95 — kill-switch caches the static default `true` into Redis on Remote-Config-unset, masking a later operator toggle for up to 5 min
When Remote Config returns null (param never set), `isEnabled()` writes `"true"` to the Redis cache with the 5-min TTL (line 83) and returns true. If an operator then sets `perspective_api_enabled=false` in Firebase to kill Layer 3 (the documented no-deploy kill switch), the cached `"true"` shadows it for up to 5 minutes — the kill switch appears not to work. Threshold reads have the same cache-the-default behavior (:144), but those are less operationally urgent than the kill switch. The fail-open intent is correct; caching the *fallback* (vs. only caching real RC values) is the issue. Fix: on RC-unset, return the default WITHOUT caching it (let each call re-check RC until a real value exists), or use a short TTL for default-derived cache entries. Confidence: medium (depends on operator relying on <5-min kill-switch latency; spec says 5-min cache is the contract, so this may be accepted — flag as QUESTION if so).

### 4. moderation/ReportService.kt:71-76 + :104-152 — report auto-hide path opens three sequential connections and the threshold COUNT runs without the auto-hide UPDATE in a serializable boundary
`submit()` opens one connection for `targetExists` (:71), closes it, then opens a second for the INSERT→COUNT→UPDATE transaction (:83). The target-existence check is TOCTOU-racy against the INSERT tx (target can be deleted between), though the FK + `ON CONFLICT` downstream make it benign. More notable: `countDistinctAgedReporters` + the conditional `flipIsAutoHidden` run at the default READ COMMITTED isolation, so two concurrent reporters both crossing the 3rd-reporter boundary can both read count≥3; correctness is preserved only because `moderation_queue`'s `ON CONFLICT DO NOTHING` + the `insertedQueue && flipped==1` gate make the notification fire exactly once (well-reasoned in the :116-128 comment). No bug, but the per-submit connection-acquire count (2 on the happy path, plus rate-limiter Redis) is heavier than needed under the small Hikari pool (docs/11 §3.2). Fix sketch: fold `targetExists` into the tx (SELECT … FOR UPDATE on the target) to drop one connection-acquire and close the TOCTOU window. Confidence: medium (no correctness defect; perf + robustness observation).

### 5. infra/fcm/FcmDispatcher.kt:139-143 — unbounded per-token `launch` fan-out onto the shared 8-slot FCM scope; one fat recipient can starve all other notifications
`runDispatch` does `for (row in snapshot.tokens) { dispatcherScope.launch { sendOne(...) } }` with no cap on token count. `activeTokens` is not bounded in the reader, so a user with N registered device tokens enqueues N blocking `FirebaseMessaging.send()` calls onto the `limitedParallelism(8)` pool shared by ALL recipients' dispatches. A burst of multi-device recipients (or a token-spam abuse vector) saturates the 8 slots and delays every other user's push. FCM also offers `sendEach`/multicast (≤500 tokens/call) which would collapse N round-trips to one. Fix: cap tokens-per-user at the reader (e.g. most-recent K), and/or batch via `sendEachForMulticast`. Confidence: medium (real under load; benign at pre-launch volume).

### 6. infra/openai-moderation/OpenAiModerationClient.kt:72-77 — one fresh Apache5 HttpClient per `OpenAiModerationClient`; verify it is a singleton, not per-dispatch
The client builds its own `HttpClient(Apache5)` in the constructor (its own connection pool + threads). This is correct IF the client is a process singleton. It is `AutoCloseable`; if any future wiring constructs it per-request (or per-dispatch) the Apache pool leaks. Wiring in `Application.kt` constructs it once (single Koin binding) today — OK — but there is no guard against per-call construction, and `close()` is only meaningful for the singleton. Note also: the KDoc still says CIO timeouts ("Ktor CIO's connect path") while the engine is Apache5 — stale comment. Fix: none required if singleton-bound (document the invariant on the class); correct the CIO→Apache5 comment drift. Confidence: medium (latent; depends on wiring discipline).

### 7. infra/fcm/PayloadBuilders.kt:115-181 — APNs clamp truncates only the single longest `body_data` field; the post-truncation overhead budget can still be exceeded by a many-small-fields payload
`clampBodyFullForApns` budgets `4096 − 256 overhead − title − body`, then shrinks ONLY the longest string field. If the JSON is many medium fields (no single dominant one), `truncateLongestStringFieldUtf8Safe` returns null and the push is dropped as `payload_too_large` (correct, documented). But the 256-byte `APNS_NOTIFICATION_OVERHEAD_BYTES` is a fixed guess; FCM's APNs envelope (aps keys, `mutable-content`, FCM `fcm_options`) can exceed 256 for some notification types, so a payload that passes the local budget can still be rejected by APNs at 4 KB at send time — surfacing as a transient `INVALID_ARGUMENT` (which the dispatcher treats as transient → no prune, retried-never). Low likelihood given current small `body_data` catalogs. Fix: lower the budget margin or compute envelope size from the actual built `Message`. Confidence: medium.

### 8. infra/otel/ForbiddenAttributeStripper.kt:41-58 — IP/PII strip is applied per-exported-span at export time on EVERY span (CPU on the hot path); and the strip only covers an enumerated key set
Each span export rebuilds an `Attributes` map if any forbidden key is present (`FORBIDDEN_KEYS.none { … }` scan over the set, then a full attribute copy). At production 10% sampling this is bounded, but at dev/staging `alwaysOn` (100%) every span pays the scan + copy. Functionally correct and the enumerated-list rationale is sound (wrong-positives worse than wrong-negatives), but a future instrumentation that emits a peer-IP under a *new* semconv key (the set already had to be extended once for the old→new migration, per the :80-87 comment) silently leaks until the list is updated. The value-scan sentinel tests catch value-leaks but not key-name drift. No action required (config sanity = acceptable); noting the maintenance coupling. Confidence: high on mechanics, low on impact.

## LOW

### 9. moderation/ReportRateLimiter.kt:39 — default constructor binds the in-memory limiter; a misconfigured prod wiring silently gives per-instance (not global) report rate-limiting
The default `rateLimiter = InMemoryRateLimiter()` exists for test ergonomics, but it means a `ReportRateLimiter()` constructed without the Redis-backed limiter silently degrades the 10/hour/user report cap to per-Cloud-Run-instance (so N instances ⇒ 10N/hour). Production wiring passes the Redis limiter, so this is latent; the risk is a future wiring change defaulting the arg. Fix: consider requiring the limiter explicitly in the production binding (no default), mirroring how other limiters are wired. Confidence: medium on the footgun, low on current exposure.

### 10. infra/remote-config/RemoteConfigClient.kt:80-114 — every Remote Config read does a full `getServerTemplate()` download + JSON parse; no template caching beyond the callers' Redis layer
`fetchRawString` calls `FirebaseRemoteConfig.getInstance(app).getServerTemplate(emptyDefaults)` and `template.toJson()` on EVERY call — a network round-trip + full-template serialize per parameter read. The moderation loaders front this with a 5-min Redis cache so steady-state is fine, but the boot-prime + any cache-miss storm (Redis down) hammers the Firebase SDK with one full template download per parameter per call. The SDK can cache server templates; this code re-fetches unconditionally. Fix: cache the `ServerTemplate` in-process with a short TTL, or fetch once and read multiple params from the one template. Confidence: medium on the redundant fetch, low on impact (Redis cache absorbs it normally).

### 11. moderation/ModerationListLoader.kt:131-175 + Layer3ConfigLoader.kt:101-146 — threshold/flag reads cache the static default into Redis, so a Remote Config correction is shadowed for up to 5 min (same shape as #3, lower urgency)
Both loaders write the default value to the Redis cache on RC-unset/out-of-range (`ModerationListLoader.kt:144` doesn't, but `Layer3ConfigLoader.kt:139,144` and the threshold path do cache defaults). A later operator fix to a threshold takes up to 5 min to take effect. Thresholds change rarely, so this is low-urgency; listed for completeness alongside #3. Confidence: medium.

### 12. infra/otel/CloudRegionProbe.kt:27-59 — metadata probe uses a blocking `HttpURLConnection` at `OtelBootstrap.start` on the boot thread (500ms × 2 timeouts) with no async offload
`fetch()` is called synchronously inside `wireSdk` during `Application.module()` bootstrap. On a non-GCP JVM (local dev / CI) the connect path funnels to the catch after `connectTimeout`+`readTimeout` (up to ~1s) on the main boot thread before the app starts serving. One-shot + cached, so negligible in prod (metadata server is local + fast), but it does add up-to-1s to local/CI boot. Fix: none needed (acceptable one-shot); could default to "unknown" immediately when `KTOR_ENV` ∉ {staging,production}. Confidence: high on behavior, low on impact.

### 13. dev/AdminBootstrapMain.kt + dev/MintDevJwt.kt — confirmed NOT route-exposed (no prod-exposure risk)
Both are standalone `fun main()` CLI entry points invoked via Gradle tasks (`adminBootstrap`, `mintDevJwt`), not Ktor routes — they cannot be reached over HTTP in any environment. `MintDevJwt` signs with the real `KTOR_RSA_PRIVATE_KEY` so a leaked dev `.env` would let an operator mint arbitrary user tokens, but that is an env-secret-handling concern, not a code-exposure one. No action. Confidence: high (verified no route registration references either `main`).
