# 06 — Mobile Features + Data Layer (commonMain)

Scope: timeline screens, post create/detail, notifications, consent, networking/repos, location. Rubric: docs/11 §2 (state §2.2, perf §2.4, data §2.6) + `openspec/specs/mobile-design-system/spec.md`. Excludes findings already filed by the shell/nav/DI agent (nested Scaffold on Notifications, single-inFlight refresh teardown, non-scrollable empty/error, plain-`remember` screen state, 3-raw-MutableStateFlow VMs, Koin-invisible VMs, `collectAsState`, remember'd LocationGate, double-submit dispatch race, ~150-line Nearby/Global state-composable duplication).

**DTO wire-truth sweep (top-priority hunt): CLEAN.** Field-by-field diff of every mobile DTO against the shipped backend serialization found zero mismatches: `NearbyPostDto`/`GlobalPostDto` + camelCase `nextCursor` + `UpsellDto` (vs `TimelineRoutes.kt`/`Upsell.kt`), `NotificationDto` (snake fields, bare `id`/`type`), `next_cursor`, `UnreadCountDto.count`, `marked_read` (vs `NotificationRoutes.kt`), `ReplyDto`/`ReplyListResponse` snake + `next_cursor` (vs `ReplyRoutes.kt`), `LikesCountResponse` (vs `LikeRoutes.kt`), `CreatePostRequestDto` bare camelCase + minimal `CreatedPostDto` (vs `PostRoutes.kt` manual `buildJsonObject`), consent triple incl. `ads_personalization` (vs `ConsentUpdateRequest.kt`), sign-in/sign-up/refresh DTOs (vs `AuthRoutes.kt`/`SignupRoutes.kt`), notification `type` wire strings + `body_data` excerpt keys (`post_excerpt`/`reply_excerpt`/`preview` vs `LikeService`/`ReplyService`/`ChatService` producers), and create-post 400 codes (`content_empty`/`content_too_long`/`location_out_of_bounds`/`content_moderated_profanity` vs `Application.kt` StatusPages). `expires_in` Long→Int narrowing is safe (seconds-scale).

## HIGH

- mobile/app/src/commonMain/kotlin/id/nearyou/app/network/HttpClientFactory.kt:105 — **No HttpTimeout plugin (and no engine-level timeouts): hung requests are engine-default-dependent**
  The shared client installs ContentNegotiation/Auth/Logging only; `PlatformHttp.kt` actuals are bare `OkHttp.create()` / `Darwin.create()`. A stalled response hangs ~10s on Android (OkHttp read default) but up to 60s on iOS (NSURLSession request default) — divergent UX, and every in-flight flag (`isRefreshing`, `likeInFlight`, composer `inFlight`) spins for that whole window with no app-controlled bound. Fix: `install(HttpTimeout) { connectTimeoutMillis/requestTimeoutMillis/socketTimeoutMillis }` with explicit values (location acquisition already has a deliberate 12s ceiling in `LocationTuning` — HTTP deserves the same treatment). Confidence: high.

- mobile/app/src/commonMain/kotlin/id/nearyou/app/screens/post/PostDetailScreen.kt:329-356 — **Like/reply affordances are brand-tinted placeholder dots, contradicting mobile-design-system**
  `LikeRow` renders the like toggle and the reply-count indicator as `Box(...).background(..., CircleShape)` dots; the `mobile-design-system` spec ("Material 3 icons are the canonical … card affordance") supersedes the dot idiom for like/reply/location/time affordances, and the feed cards were migrated (`ic_post_like`/`ic_post_like_filled`/`ic_post_reply` already ship in `:shared:resources` and are used at NearbyTimelineScreen.kt:465-484). The KDoc still says "the interactive analogue of the read-only card dot" — stale: the card dot no longer exists. Cross-change incoherence (post-detail landed parallel to the design-system migration and was never reconciled). Fix: swap dots for the existing painterResources (filled/outlined heart + reply glyph), keep the testTags. Confidence: high.

- mobile/app/src/commonMain/kotlin/id/nearyou/app/notifications/NotificationsFlow.kt:40-56 — **Terminal-401 outcome fork: notifications (+ post ops) render the connectivity copy where timelines render the session-redirect placeholder**
  `NotificationsOutcome` has no `SessionExpired` member — `NotificationsRepository.kt:47-50` maps a terminal 401 (one that survived the Auth-plugin refresh) into the retryable `NetworkError`, so during the pre-re-route window the Notifikasi section shows "network error" + a retry control. `mobile-session-expiry-and-proactive-refresh` D4 fixed exactly this for Nearby/Global (`NearbyTimelineFlow.kt:51` / `GlobalTimelineFlow.kt:51` map 401 → `SessionExpired` → neutral redirect copy, NO retry). Same fork in `PostDetailRepository.kt:69-94` (401 → `NetworkError` for like/reply) and `CreatePostRepository.kt:94-97`. Per docs/11 §Pattern Registry this is an undeclared second pattern for an already-registered concern. Fix: add `SessionExpired` to `NotificationsOutcome` (+ a neutral-redirect projection) and branch 401 ahead of the fallback, mirroring the timelines; for the post-op repos either map 401 or amend the spec note. Confidence: high (mechanism), medium (severity — window is brief).

- mobile/app/src/commonMain/kotlin/id/nearyou/app/screens/post/PostDetailScreen.kt:217-227 — **Scaffold topBar/bottomBar are bare Row/Column: status-bar overlap + IME occlusion of the reply composer**
  PostDetail renders as a root NavDisplay entry (its own Scaffold is legitimate — it does not nest inside the shell), but M3 `Scaffold` does not inset its `topBar`/`bottomBar` slots: `BackBar` is a plain `Row` (no `TopAppBar`/`windowInsets`) so "Tutup" draws under the status bar edge-to-edge, and `ReplyComposer` is a plain `Column` (no `navigationBars`/`ime` padding) so the gesture bar overlaps it and the keyboard covers the field while typing. Contrast: `PostCreationScreen.kt:130` correctly uses `safeContentPadding()`; `NotificationsScreen` uses a real `TopAppBar`. Fix: `Modifier.windowInsetsPadding(WindowInsets.statusBars)` on BackBar, `WindowInsets.safeDrawing.union(WindowInsets.ime)` (or `imePadding().navigationBarsPadding()`) on ReplyComposer. Verify on device per docs/11 §5.3. Confidence: medium-high (standard M3 slot behavior; needs a device screenshot to confirm magnitude).

## MEDIUM

- mobile/app/src/commonMain/kotlin/id/nearyou/app/network/HttpClientFactory.kt:105 — **No `HttpRequestRetry` on idempotent GETs (docs/11 §2.6 contract)**
  §2.6: "Retries: Ktor client `HttpRequestRetry` with `exponentialDelay()` where idempotent — no hand-rolled retry loops." No client-side retry exists anywhere; every transient 5xx/IO blip on timeline/notifications/likes-count GETs surfaces straight to the error state and a manual retry tap. Fix: `install(HttpRequestRetry) { retryOnExceptionOrServerErrors(maxRetries = 2); exponentialDelay(); modifyRequest/retryIf gated to HttpMethod.Get }` so POST/PATCH/DELETE are never replayed. Confidence: high (it's the written baseline; gap predates the baseline doc).

- mobile/app/src/commonMain/kotlin/id/nearyou/app/screens/timeline/NearbyTimelineScreen.kt:168 — **UI-state projection (incl. `posts.map { it.toUi() }`) recomputed inline on every recomposition**
  `nearbyTimelineUiState(outcome, isInitialLoad)` is called in the composable body (same at GlobalTimelineScreen.kt:98 and NotificationsScreen.kt:87); each call re-maps the whole DTO list into fresh `List<NearbyTimelinePost>` instances, so any unrelated state read (e.g. `isRefreshing` flips during pull-to-refresh) re-allocates and hands `PostList` a new unstable `List` — defeating strong skipping for the entire card list. docs/11 §2.4: "never compute derived list state inline per recomposition" + list-bearing UiState should be `ImmutableList`/stable. Fix: project inside the VM (`combine(...).stateIn(...)` exposing one `StateFlow<UiState>` per §2.2 — dovetails with the already-filed 3-raw-StateFlow finding) or at minimum `remember(outcome, isInitialLoad) { ... }`. Confidence: high.

- mobile/app/src/commonMain/kotlin/id/nearyou/app/screens/timeline/NearbyTimelineViewModel.kt:59-79 — **Unguarded reload reentrancy: first completion clears `isRefreshing` while a second reload is still in flight**
  `reload()` launches unconditionally (same at GlobalTimelineViewModel.kt:53-69, NotificationsViewModel.kt:47-62): pull-to-refresh + retry tap (or two quick pulls) run two concurrent `loadFirstPage()`s; the first `finally` clears `isRefreshing`/`isInitialLoad` while the second is mid-flight (spinner disappears early), `_outcome` is last-writer-wins, and the backend sees doubled reads (which also burn the timeline soft-cap budget). Contrast: `AuthRepository`/`ConsentRepository` guard with `Mutex.tryLock` — a third in-repo pattern variance for the same concern. Fix: bail out of `load()` when a load is active (track the `Job` or an in-flight flag checked inside the VM, not the composable). Confidence: high.

- mobile/app/src/commonMain/kotlin/id/nearyou/app/screens/post/PostDetailScreen.kt:191-199 — **201 reply append goes to the END of a newest-first list; submitting from the Error state hides all other replies**
  The replies wire is keyset `(created_at DESC, id DESC)` (core/data `PostReplyRepository` canonical query) — newest FIRST — but the local append does `current.replies + outcome.reply`, placing the user's brand-new reply at the bottom as if oldest; on next screen entry the same reply renders at the top (inconsistent placement; the spec says "appended" without fixing position — spec wording needs the same amendment). Worse: when `repliesOutcome` is `NetworkError` (list failed to load) the else-branch fabricates `Loaded(listOf(reply))` — the error + retry control vanish and the post's other N replies become unreachable without leaving the screen. Fix: prepend (`listOf(outcome.reply) + current.replies`) and, from a non-Loaded state, keep the outcome and trigger `reloadReplies()` instead of fabricating Loaded. Confidence: high.

- mobile/app/src/commonMain/kotlin/id/nearyou/app/timeline/NearbyTimelineRepository.kt:26 — **Location exceptions escape the repository into the ViewModel; VM blanket-catch masks real bugs with zero diagnostics**
  `locationProvider.current()` is called un-caught, so `LocationUnavailableException` (and any platform throwable) crosses the repository boundary — docs/11 §2.6: "exceptions don't cross into ViewModels". The compensating `catch (_: Throwable)` in NearbyTimelineViewModel.kt:69-72 (and GlobalTimelineViewModel.kt:61-64, NotificationsViewModel.kt:55-57 — where the repo genuinely never throws) maps EVERY throwable (NPE, serialization config bug) to `NetworkError` silently, bypassing the repository's `diagnosticLog`. Contrast: `CreatePostRepository.kt:52-61 ` catches the location failure at the repo and maps it to an outcome. Fix: catch in the repo → existing retryable outcome + `diagnosticLog("nearby_location_unavailable: <type>")`; narrow the VM catch (or drop it). Confidence: high.

- mobile/app/src/commonMain/kotlin/id/nearyou/app/di/MobileModule.kt:147 — **DiagnosticSink wiring drift: notifications/post-creation/post-detail/consent repos keep the no-op default**
  Nearby/Global get `diagnosticLog = get<DiagnosticSink>()::log` (lines 127, 137) per session-expiry D6, but `NotificationsRepository(get())` (147), `CreatePostRepository(get(), get(), get())` (157), `ConsentRepository(get())` (164) and `PostDetailRepository(get(), get())` (174) are constructed without it — all their carefully-built diagnostic strings (`notifications_server_error: status=...`, reply-400 diagnostics, unknown create-post 400 codes) go nowhere, even in debug. Fix: pass the sink (PostDetail/CreatePost need a small `(status, code)` adapter). Confidence: high.

- mobile/app/src/commonMain/kotlin/id/nearyou/app/screens/timeline/NearbyTimelineScreen.kt:371 — **No `contentType` on any feed/list `items()`**
  docs/11 §2.4 requires stable `key` + `contentType` on every `items()` over domain lists. Keys are present, contentType absent at all four sites: NearbyTimelineScreen.kt:371, GlobalTimelineScreen.kt:238, NotificationsScreen.kt:211, PostDetailScreen.kt:260 — and the timeline/detail lists are heterogeneous (banner item / header / like-row / state items share the default null type with cards), so recycled compositions cross item shapes. Fix: `contentType = { "post_card" }` etc. per item family. Confidence: high (contract), medium (visible impact at MVP list sizes).

## LOW

- mobile/app/src/commonMain/kotlin/id/nearyou/app/consent/ConsentRepository.kt:59 — **Logs `result.cause.message` — pattern fork from the type-only diagnostic convention**
  Nearby/Global deliberately log only the exception class ("a timeout exception's message can embed the request URL"; NearbyTimelineRepository.kt:42-47) and the consent KDoc itself promises "only a status / transport-cause envelope", but the code interpolates the raw message. No coordinate travels on this route, so it's a consistency/PII-hygiene nit, not a leak. Fix: `${result.cause::class.simpleName}`. Confidence: high.

- mobile/app/src/commonMain/kotlin/id/nearyou/app/screens/home/HomeScreen.kt:113 — **Pager keeps `beyondViewportPageCount` default (0): adjacent feed mounts mid-swipe**
  The neighbor page composes from scratch during the swipe gesture (its first-ever swipe also kicks off the VM's init load), so the user can watch a skeleton flash mid-drag. `beyondViewportPageCount = 1` pre-mounts neighbors and starts the Global load early; VM-store retention already makes this cheap on re-visits. Suggestion-grade. Confidence: medium.

- mobile/app/src/commonMain/kotlin/id/nearyou/app/screens/home/HomeScreen.kt:136 — **Composer FAB overlays the last feed card with no list bottom clearance**
  The FAB sits in a bottom-end overlay while `PostList` uses `contentPadding = PaddingValues(vertical = 8.dp)` (NearbyTimelineScreen.kt:364, GlobalTimelineScreen.kt:231) — the final card's like/reply row (and its tap target) can sit under the FAB at scroll end. Fix: bottom contentPadding ≈ 88.dp on the feed lists (FAB 56 + 16 margin + breathing room). Confidence: medium-high.

- mobile/app/src/commonMain/kotlin/id/nearyou/app/screens/post/PostDetailScreen.kt:117 — **Like flip / reply count never propagate back to the retained feed VM**
  The detail screen mutates `liked`/counts locally, but on back the feed renders the HomeRoute-scoped VM's retained `Loaded` outcome — the tapped card still shows the pre-flip heart/`reply_count` until the next manual refresh. Sister-gap to the documented composer-deferral (`mobile-post-creation-refresh-nearby-on-return`); no equivalent deferral is written for detail→feed. Fix sketch: piggyback on the planned refresh-on-return follow-up or a shared per-post overlay store; at minimum record the deferral. Confidence: high (behavior), low (whether operator considers it in-scope debt).
